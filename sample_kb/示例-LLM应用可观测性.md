# 示例笔记：LLM 应用可观测性

> 本文件是仓库自带的示例文档，内容为公开常识，仅用于演示上传与检索，不包含任何个人资料。

## 为什么需要链路追踪

一次 RAG 问答至少包含改写、检索、生成三个环节。只看最终答案，无法判断问题出在哪里：

- 答案不对，可能是检索没召回到正确片段，也可能是召回了但模型没用好
- 响应慢，可能慢在向量化、慢在检索，也可能慢在模型生成

把每个环节单独记录，才能把「感觉不太好」变成「第几步耗时多少、输入输出是什么」。

## 三个层级

| 层级 | 含义 | 用途 |
|---|---|---|
| Trace | 一次完整请求 | 定位单次问答为什么慢或为什么答错 |
| Span / Run | 请求中的一个环节 | 统计某个环节的耗时分布 |
| Thread / Session | 一轮多次对话 | 观察多轮体验是否连贯 |

三者是包含关系：一个 Thread 含多个 Trace，一个 Trace 含多个 Span。

## 流式响应的坑

如果接口是流式返回的，真正的生成逻辑会在响应对象返回之后才执行，往往还在另一个线程上。
此时追踪上下文容易断掉，一次问答会被记录成几条互不关联的记录。

解决办法是手工创建根节点并保持打开，直到流结束再关闭，同时把子环节显式挂到这个根节点上。

## 该记什么元数据

至少记录模型名、关键参数（如 TOP_K）和会话标识。有了这些才能做对比分析，
例如换模型前后的延迟对比，或者按会话聚合查看多轮表现。

## 观测不能影响主流程

追踪是辅助功能，追踪服务不可用时主流程必须照常工作。
所有上报逻辑都应当包在异常捕获里，失败只记日志，不向上抛。

同理，未开启追踪时不应产生任何网络请求——有些 SDK 在构造对象时就会尝试上报。

## 先量，再改，再验证

有了基线数据才能判断优化是否有效。常见的误区是凭直觉优化：
以为检索慢，花力气调参数，实测却发现九成时间花在模型生成上。
