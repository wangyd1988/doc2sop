# 示例笔记：大模型推理性能

> 本文件是仓库自带的示例文档，内容为公开常识，仅用于演示上传与检索，不包含任何个人资料。

## 两个阶段，两种瓶颈

大模型推理分成两个阶段，瓶颈完全不同：

- **Prefill（处理提示词）**：整段提示一次性并行计算，吃的是算力
- **Decode（逐字生成）**：每生成一个 token 都要把整个模型权重从显存读一遍，吃的是显存带宽

关键结论是 decode 阶段算力大量闲置，卡在搬数据上。

这一条能解释一串现象：为什么加大 batch 几乎是「免费」提升吞吐；为什么量化能加速；
为什么长提示词拖慢的是首字延迟，而不是后续的吐字速度。

## 两个必须分开看的指标

- **TTFT**（Time To First Token）：首字延迟，由提示词长度和排队情况决定
- **TPOT**（Time Per Output Token）：每字延迟，基本恒定

只看总耗时会掩盖问题。首字慢而吐字正常，说明瓶颈在 prefill；吐字慢则要看显存带宽和批处理策略。

## KV Cache

生成过程中，前面 token 算出的中间结果会被缓存复用，避免每生成一个字就重算整段上下文。
代价是显存占用随对话长度线性增长，这也是长对话越来越吃显存的原因。

## Continuous Batching

传统批处理要等一整批请求全部生成完才能开始下一批，短请求被长请求拖住。

Continuous Batching 把调度粒度细化到每一步 token 生成：谁生成完谁就走，空出的位置立刻补进新请求。
吞吐通常能提升数倍。

## Prefix Caching

多个请求如果共享相同的前缀（例如同一段系统提示词），前缀的计算结果可以复用，不必每次重算。

这意味着提示词的拼接顺序会直接影响性能：固定内容放前面、变化内容放后面，缓存命中率才高。
顺序一旦颠倒，缓存就失效了。

## 推理模型的陷阱

带思考能力的推理模型在正式回答前会先输出一段推理内容。对需要快速响应的问答场景，
这会让首字延迟变得很不稳定，而且思考部分照样计费。

部分网关提供了关闭思考的参数，但要实测验证：有些实现只是不再把思考单独返回，
模型照样在思考，推理内容反而混进了正式答案里。

## 吞吐与延迟是跷跷板

几乎所有推理调度的取舍都围绕这一条：调大批次提升吞吐，但单个请求的延迟会变差。
在线对话优先保延迟，离线批处理优先保吞吐。
