# 五分钟演示：一条命令跑起 doc2sop，看到工具 + SOP 的效果

这份文档是「照着做一定能复现」的步骤表，也是录演示 GIF 的脚本：精确到点哪里、问什么、预期看到什么。
全程不需要 k8s、docker socket 或自托管模型——只要 Docker 和一把模型 key。

## 0. 准备（2 分钟）

| 需要 | 说明 |
|---|---|
| Docker | Docker Desktop（Windows / macOS）或 Docker Engine + Compose v2（Linux）；2 核 2 GB 的小主机够用 |
| 一把硅基流动 API key | 到 [cloud.siliconflow.cn](https://cloud.siliconflow.cn) 注册 → 「API 密钥」→ 新建。推荐它的原因只有一个：**同一把 key 同时提供对话模型和向量模型**（`BAAI/bge-m3`），不用再找第二家 |

别家也行（DeepSeek、百炼、任何 OpenAI 兼容地址 + 一个向量模型地址），见 README「正式部署」。
只是演示二里「账户余额」那个工具查的是硅基流动的接口，换厂商会返回 404——Agent 会如实说明，不影响其他部分。

## 1. 启动（1 条命令）

```bash
git clone https://github.com/wangyd1988/doc2sop.git && cd doc2sop
cp .env.example .env
# 用任意编辑器改两处：WEB_PASSWORD（登录密码）、LLM_API_KEY（刚申请的 key）。
# 建议顺手把 OPS_TOKEN 也换成一串随机字符。文件必须保持 LF 换行、无 BOM。
docker compose up -d --build
```

`.env.example` 里预置了 `COMPOSE_PROFILES=demo`，所以这条 `up` 等价于 `docker compose --profile demo up -d --build`，
会起三个容器：

| 容器 | 干什么 | 内存上限 |
|---|---|---|
| `kb-app` | 知识库应用，监听 `127.0.0.1:8765` | 900 MB |
| `kb-ops` | 只读工具 sidecar：跑 `deploy/ops_readonly.py`，工具定义来自 `packs/` 里的场景包；端口不对外发布 | 128 MB |
| `kb-host` | 演示主机：sshd + 受控模式的执行器，只开放磁盘、内存、负载三个工具，给 sidecar 演示多机巡检；端口不对外发布 | 64 MB |

首次构建要下载 Python 依赖和两个 Debian 包（sshd、ssh 客户端），视网络 1–3 分钟。然后核对：

```bash
docker compose ps                 # 三个容器都 running / healthy
docker compose logs kb-ops        # 看到「可用工具 10 个：asset_lookup, asset_tickets, assets_warranty_expiring, date_info, gateway_balance, gateway_models, holiday_calendar, host_disk, host_resources, host_uptime」
                                  # 下一行「暂不可用：container_stats, list_containers」是正常的：这两个要读 docker，演示里没有
```

> 用户在这一步做的事：改 2 个值 + 敲 1 条命令。

## 2. 登录，等场景包自动就位（约 30 秒）

打开 http://127.0.0.1:8765 ，用户名 `admin`，密码是 `.env` 里的 `WEB_PASSWORD`。

欢迎页的引导卡会先显示：

> ⏳ 正在导入演示场景包「leave-planning」：休假管理制度.md：向量化 2 个片段

这是应用在后台把 `packs/leave-planning`、`packs/model-selfcheck` 和 `packs/it-assets` 三个场景包导进来：文档入库、随包附带的 SOP 直接加载
（不用现场抽取）。几十秒后引导卡变成：

> ✓ 已有 3 个文档　✓ 已有 2 个 SOP 生效，10 个工具可用　3 问一句

欢迎页下方的示例问题也换成了场景包里的（点一下就发送）。

想看细节：顶栏「管理」→「工具」：可用 10 个；管理面板列出 12 个（标题是「10 个可用 · 共 12 个」），其中「容器清单」「容器资源占用」
两个要读 docker——sidecar 里没有 docker，演示主机也没开放它们——在演示里不可用，卡片上标着 ⚠ 和原因。
每个工具的卡片都能看到命令 / 接口地址 / SQL（key 不可见），磁盘、内存、负载三个工具的卡片上逐台标着
`local ✓ demo-host ✓`；「SOP」里《休假管理制度.md》分组下有《请假拼假核对》，《IT资产管理规范.md》分组下有《设备报修核对》，每一步后面引着文档原句。

## 3. 演示一：照着 SOP 办事（行政 · 请假拼假）

**点**欢迎页第一个示例问题，或在输入框输入：

> 国庆想连休到 10 月 11 日要请几天年假

问题故意不带年份：Agent 按「下一个国庆所在的年份」查（今天在 10 月 7 日之前就是今年，过了就是明年），
规则写在工具说明和 SOP 检查点里。

**预期看到**（措辞每次略有不同，要点不变）：

1. 回答上方出现两张工具调用卡片：🔧 `holiday_calendar`（year=下一个国庆所在的年份）、🔧 `date_info`（10 月 8 日起逐日，可能调用多次）。点开能看到原始返回。
2. 回答第一行：**「按 SOP《请假拼假核对》执行」**，然后是一张「步骤 | 查看 | 实际数据 | 结论」表：
   - 第 1 步 · 那一年的法定节假日安排 → 国庆放假从哪天到哪天；**前后哪个周六或周日要补班**
   - 第 2 步 · 10 月 8 日到 11 日各是星期几 → 周六、周日不算，补班日虽在周末也算工作日
3. 结论：**请 N 天年假（列出具体哪几天），可从 10 月 1 日连休到 10 月 11 日。**
   并引用《休假管理制度》：补班日虽在周末也计入请假天数；与法定节假日连休需至少提前 10 个工作日申请，3 天以内由部门负责人审批。

这一问的价值在「补班日」这个坑：凭直觉只数周一到周五，按 SOP 一查数据，补班的那个周末也要请假，往往要多请一天。
N 是几取决于那一年的安排，所以这里不写死。

如果下一个国庆所在的年份国务院还没公布安排（通常前一年 11–12 月才公布），数据源会返回空的 `days`（或 404），
工具输出里会写明「该年安排尚未公布」，Agent 如实说明，并按法定假日天数和往年调休规律给出推算、注明是推算——不会以报错收场。

## 4. 演示二：SOP 从实践里长出来（研发 · 模型调用自查）

研发场景包**故意没有带 SOP**，这一段演示它怎么长出来。

**问**（点「新对话」后输入，或点示例问题）：

> 我这把 key 能用哪些模型？余额还剩多少？

**预期看到**：

1. 两张工具卡片：🔧 `gateway_models`、🔧 `gateway_balance`。
2. 回答列出这把 key 能调用的对话模型（硅基流动会返回几十个，Agent 会归纳），以及账户状态与余额；
   对照《模型服务自查手册》说明「模型名要和列表完全一致」「余额为 0 会被拒绝」。
3. **回答结束后 5–30 秒**（后台让模型整理轨迹），回答下方出现一张 💡 卡片：

   > 💡 这次用 2 个工具、2 步得出结论，沉淀为 SOP《模型调用自查》？
   > 适用：…　[查看步骤]　**保存**　忽略

   「查看步骤」能展开：`gateway_models` → `gateway_balance`，每步有检查点，依据写着「第 1 次调用 gateway_models 的返回：…」。
4. **点「保存」** → 卡片变成「✅ 已保存到 SOP《模型调用自查》（默认停用，去 SOP 页核对后启用）」。
5. **点顶栏「SOP」**，在「从实践沉淀」分组里找到它，**点「已停用」**把它切成「已启用」（这就是「人确认」那一步）。
6. **再问一遍同类问题**（新对话）：

   > 帮新同事看看他的 key 能用什么模型、余额够不够

   这次回答第一行是 **「按 SOP《模型调用自查》执行」**——上一轮的自由排查，已经变成团队的标准做法。

SOP 名字由模型起，可能叫《模型调用自查》也可能叫《模型 key 可用性与余额核对》；都对。

## 4½. 演示三（可选）：多机巡检（运维）

sidecar 自己算一台主机（`local`），演示主机 `demo-host` 经 SSH 受控模式巡检，两台合成分组 `demo`。**问**（新对话）：

> 看看所有主机的磁盘、内存和负载

**预期看到**：

1. 三张工具卡片：🔧 `host_disk`、🔧 `host_resources`、🔧 `host_uptime`，参数都是 `target=@all`（或 `@demo`）。
   点开返回，每张都按主机分段：`== local（成功）==`、`== demo-host（成功）==`，末尾一行「共 2 台，成功 2 台，失败 0 台」。
2. 回答按主机分别说磁盘、内存、负载，指出哪台偏高。
3. 只问一台（「demo-host 的磁盘还够吗」）时 `target=demo-host`；不提主机时 `target` 不填，就是 `local`。

背后：演示主机上的执行器只认它自己白名单里的三个工具（root 所有），sidecar 那边就算被攻破，在它上面也只能跑这三个只读命令。
「管理」→「工具」的分组栏底下有主机清单，标着 `demo-host 受控 · 在线`。

## 4¾. 演示四（可选）：查数据库（IT · 设备报修）

`it-assets` 场景包的三个工具是 **SQL 工具**：工具服务按写好的查询模板查一个只读数据库，模型只填参数（资产编号、天数），
参数由数据库驱动绑定，模型改不了 SQL。演示站用随包的 `demo/assets.sql` 建了一个 sqlite 假库（日期按今天推算，哪天演示结论都一样），
连接 `it_assets` 由 sidecar 自动建好。**问**（新对话，或点欢迎页最后一个示例问题）：

> 笔记本 NB-0042 键盘又坏了，还在保修期吗？该怎么处理？

**预期看到**：

1. 两张工具卡片：🔧 `asset_lookup`、🔧 `asset_tickets`，参数都是 `tag=NB-0042`。点开返回是一张表（`tag | kind | model | …`），末尾「（共 N 行）」。
2. 回答第一行 **「按 SOP《设备报修核对》执行」**：
   - 第 1 步：使用人王敏（研发部），保修大约 55 天后到期 → 走厂商保修，不得自行拆机；
   - 第 2 步：6 天前开了一单「键盘又有按键失灵」，75 天前同一问题转过厂商 → 90 天内第二次报修，**直接进入换机评估**；笔记本是 P2，1 个工作日内响应。
3. 再问「最近 60 天有哪些设备要过保？」：🔧 `assets_warranty_expiring`（days=60），列出 PC-0007、NB-0042 两台（打印机 PRN-0003 要 80 天后才到期，不在里面），
   并引用规范「保修到期前 60 天汇总续保或换新计划」。

「管理」→「工具」→「IT 资产」分组里，卡片标着 `SQL` 和 `连接 it_assets`：查询原文可见，库的位置和账号不可见。
换成真实资产库（只读账号、装驱动、在主配置里建同名连接）见 [`工具.md`](工具.md#sql-工具按模板查只读数据库)。

## 5. 收尾

```bash
docker compose down          # 停掉，保留 ./data（知识库）和 ops-state 卷
docker compose down -v       # 连同数据一起清掉，下次 up 从零开始（场景包会重新自动导入）
```

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| `up` 卡在拉取 `python:3.12-slim`，或报 Docker Hub 连接超时 | 国内网络到不了 Docker Hub。`.env` 里打开 `BASE_IMAGE=docker.m.daocloud.io/library/python:3.12-slim` 这一行，再 `docker compose up -d --build`；三个镜像都会改用它 |
| 构建卡在 `apt-get`（装 sshd、ssh 客户端） | `.env` 里打开 `DEBIAN_MIRROR=http://mirrors.aliyun.com` 再构建 |
| 磁盘、内存、负载三个工具在 `demo-host` 上提示「host key 还没登记」或连不上 | `kb-host` 没起来，或 sidecar 启动时没等到它交出 host 公钥：`docker compose logs kb-host`，然后 `docker compose restart kb-ops` |
| `up` 时报 `required variable OPS_TOKEN is missing a value` | `.env` 里 `OPS_TOKEN` 被删空了，填任意一串随机字符 |
| 引导卡一直显示「等待导入：…（还没有配置模型）」 | `.env` 里 `LLM_API_KEY` 没填，或改完 `.env` 没有重建容器（`docker compose up -d`，`restart` 不重读 env） |
| 引导卡显示「等待工具上线：holiday_calendar、date_info…」 | `kb-ops` 还没起来或起不来：`docker compose logs kb-ops`；确认 `OPS_URL=http://kb-ops:8799`、`COMPOSE_PROFILES=demo` |
| 引导卡显示「休假管理制度.md 入库失败：向量化失败」 | key 无效或余额为 0；到「管理 → 模型设置」点「测试连接」看具体报错。修好后会自动重试 |
| 演示二的两个工具提示「宿主机没有配置 OPS_SECRET_GATEWAY_URL」 | 模型是在页面上填的，没写进 `.env`。页面上填的凭据不会传给工具容器（这是既定边界）；把地址和 key 写进 `.env` 再 `docker compose up -d` |
| `gateway_balance` 返回 404 | 不是硅基流动的端点，没有 `/v1/user/info`；Agent 会说明，去厂商控制台看余额即可。想换接口，改 `packs/model-selfcheck/tools.yaml` 后 `docker compose restart kb-ops` |
| 只导入了两个场景包，没有「IT 资产」（演示四） | `.env` 是从旧版 `.env.example` 拷的，`DEMO_PACKS` 里没有 `it-assets`：补上后 `docker compose up -d` |
| 演示二没有出现 💡 卡片 | 看回答是否真的调了 2 个不同工具、是否有结论；一天最多提 `SOP_PROPOSALS_PER_DAY` 条；同样路径「忽略」过 30 天内不再提；`docker compose logs kb-app` 里有 `no SOP proposal for …: 原因` |
| 每个值都不对 / 密码登不进 | `.env` 带了 `\r`（CRLF）或 BOM，用编辑器改成 LF 后重建容器 |
| 8765 端口被占 | 改 `.env` 的 `APP_PORT`（宿主机侧端口，如 `APP_PORT=8766`）再 `docker compose up -d`；容器内仍是 8765，不用动 `PORT` |
| 想在同一台机器再跑一套（比如正式站旁边起个演示站） | 在另一个目录 clone，那份 `.env` 里改 `APP_CONTAINER` `OPS_CONTAINER` `APP_IMAGE` `OPS_IMAGE` `APP_PORT`（`.env.example` 里有现成的注释行），compose 项目名跟目录走，网络和卷互不干扰。正式站本身的部署方式见 [`正式部署.md`](正式部署.md) |

## 录制 GIF

`deploy/demo/record.js` 把上面两段做成了可重复的无头录制：对着一个跑起来的演示站走两幕，抓无损画面帧，按关键时刻剪辑后用
ffmpeg 两遍法（palettegen → paletteuse）转 GIF。不需要屏幕，Windows / macOS / Linux 都能跑。

**依赖**：Node ≥ 18；`playwright-core` 和它配套的 Chromium；PATH 里有 `ffmpeg` 与 `ffprobe`。

```bash
# 在仓库根目录。node_modules/ 已在 .gitignore 里
npm i --no-save --no-package-lock playwright-core
npx playwright-core install chromium          # 国内下载慢可先 export PLAYWRIGHT_DOWNLOAD_HOST=https://registry.npmmirror.com/-/binary/playwright
```

机器上已有别的 playwright-core（比如 `npx` 缓存里的）时不用再装，把 `PWCORE` 指向那个目录即可；Chromium 版本要和它配套。

**环境变量**：脚本只从环境变量读演示站地址和登录信息，不读任何文件、不打印到日志。

| 变量 | 说明 |
|---|---|
| `DEMO_URL` | 演示站地址，如 `http://127.0.0.1:8765`（远端机器就先开 SSH 隧道把端口映射到本机） |
| `DEMO_USER` / `DEMO_PASSWORD` | 页面的 Basic 登录，即 `admin` 和 `.env` 里的 `WEB_PASSWORD` |
| `PWCORE` | 可选，playwright-core 的安装目录；不设就 `require('playwright-core')` |

**运行**：

```bash
# bash
DEMO_URL=http://127.0.0.1:8765 DEMO_USER=admin DEMO_PASSWORD='…' node deploy/demo/record.js --scene all
```

```powershell
# PowerShell
$env:DEMO_URL='http://127.0.0.1:8765'; $env:DEMO_USER='admin'; $env:DEMO_PASSWORD='…'
node deploy\demo\record.js --scene all
```

| 参数 | 说明 |
|---|---|
| `--scene sop\|grow\|all` | 录哪一幕，默认 `all`（先 sop 后 grow） |
| `--out 目录` | 输出目录，默认 `docs/media`；GIF 落在这里，中间产物在 `raw/` 子目录（已 gitignore） |
| `--sidebar` | 把左侧文档栏也录进去（默认用注入的 CSS 隐藏，不改产品代码） |
| `--reuse` | 不重录，用 `raw/` 里上次的素材和时刻记录只重做剪辑与 GIF，调时长、体积参数时用 |

脚本会先等 `/api/packs` 里自动导入的场景包全部 `imported`（刚 `up` 完直接跑也行，最多等 3 分钟），再逐幕录制。
每一幕都有断言，不满足就退出码 1 且不产出 GIF：第一幕回答要同时含「SOP」和「请 N 天」这个模式（N 不钉死，取决于那一年的补班安排）并出现粗体结论；第二幕 💡 卡片要在 90 秒内出现
（超时会再查一次 `/api/proposals` 告诉你是没生成还是生成太晚）。参数 / 环境 / 演示站状态问题退出码 2。
产出的 GIF 超过 4 MB 时按 1280@12 → 1280@10 → 960@12 → 960@10 的阶梯自动降档。

**重录第二幕前要重置演示数据**：保存过一次后，再问同样的问题不会再出 💡 卡片（会和已有 SOP——含停用的——比相似度）。
脚本在录第二幕前会检查，已经有「从实践沉淀」的 SOP 就直接报错退出。重置：

```bash
docker compose down && rm -rf data && docker compose up -d     # 回到第 2 节「场景包自动就位」之前的状态
```
