## 1. 产品定位

**一句话**：把团队文档变成 Agent 的 SOP——它照着文档里写的做法，用你批准过的只读工具查真实数据，对照后给结论。

**解决的两个矛盾**

| 矛盾 | 现在怎么解 |
|---|---|
| 规则在文档里、数据在系统里，中间靠人对照 | 知识库 → SOP → 工具 三层打通，文档里的步骤和阈值直接变成执行顺序和判断标准 |
| 想让 AI 动手，又怕它乱动 | Agent 永远拿不到 shell 和凭据，只能提交「工具名 + 结构化参数」，执行什么由管理员在宿主机定义 |

**不限岗位**：换一批文档和工具就是换一个场景。当前内置三个示例：运维巡检、研发模型自查、行政请假核对。

**目标用户**：有一批内部文档、有几个内部系统想查、但不敢给 AI 执行权限的小团队。单机 2C2G 可跑。

## 3. 核心概念：知识库 → SOP → 工具

```
📄 知识库（文档）          📋 SOP（步骤）              🔧 工具（执行）
《休假管理制度》         →  1. 查当年节假日     ───────→  holiday_calendar
  先查节假日和补班、         2. 逐日确认星期几   ───────→  date_info
  再逐日看是不是工作日       3. 算要请几天
  人写的规则                 从文档自动抽取、页面可调     管理员审过的只读能力
```

| 层 | 回答什么 | 谁能改 | 存在哪 |
|---|---|---|---|
| 知识库 | 规定是什么、应该怎么做 | 任何能上传文档的人 | Chroma + uploads/ |
| SOP | 按什么顺序、调哪个工具、每步看什么 | 页面可编辑、启停 | `data/playbooks.json` |
| 工具 | 实际执行哪条命令、调哪个接口 | 只有宿主机管理员 | 宿主机 `deploy/ops_tools.yaml` |

关键约束：**SOP 只能引用已有工具，不能定义新命令**。文档被投毒也变不成执行能力。

## 4. 一次提问的完整流程

```
用户提问（可选：选模型、开关联网）
  │
  ├─ 1. 改写：多轮时补全指代（rewriter 模型，首轮跳过）
  ├─ 2. 检索：向量化 → Chroma Top-8 → 低于阈值丢弃
  ├─ 3. 拉工具定义：每次从宿主机 /tools 拉取，动态生成 pydantic 签名
  ├─ 4. 组装 prompt：知识库片段（只进当轮，不入记忆）+ 已启用 SOP + 工具列表 + 联网规则
  │
  └─ 5. LangGraph 循环（模型 ⇄ 工具，最多 N 轮）
        ├─ 模型判断：片段相关？直接答
        │            需要查？调工具（ops_readonly 执行，返回截断 20000 字）
        │            答不了且允许联网？web_search（screen() 拦截 → 网关 /v1/search）
        └─ 每步事件流式推给页面：tool_call / tool_result / web_source / delta
  │
  ├─ 6. 整理来源：实际引用的 [n] 排前，未采用的折叠
  ├─ 7. 保存：conversations（文字 + 模型）、LangGraph checkpoint（整轮过程含工具原始结果）
  └─ 8. LangSmith trace
```

实测耗时：5～12 秒完成 2～7 次工具调用；瓶颈 >85% 在模型生成。

## 5. 系统架构

```
浏览器
  │ HTTP Basic
  ▼
┌─ 云 A（国内 2C2G）────────────────────────────────────────┐
│  kb-app 容器（FastAPI + LangChain + LangGraph）             │
│    Chroma 向量库 · SQLite（会话 / 检查点）· uploads/       │
│    无 docker.sock，无宿主机权限，不持有任何工具凭据         │
│         │ 127.0.0.1:8766 + 令牌                            │
│  ops-readonly.service（宿主机 systemd）                     │
│    ops_tools.yaml 加载校验 → 固定 argv / URL 模板执行       │
│    凭据只在 /etc/ops-readonly.env（OPS_SECRET_*）           │
└───────────────────────────────┬───────────────────────────┘
                                │ OpenAI 兼容
┌─ 云 B（腾讯 2C4G，可出海）─────▼───────────────────────────┐
│  LiteLLM 网关                                              │
│    聊天模型路由 · /v1/search（Tavily ×7 key 分流）          │
│    websearch_interception（仅 github_copilot/*）           │
│         │ SSH 隧道                                         │
└─────────┼─────────────────────────────────────────────────┘
┌─ 云 C（阿里 2C2G，国内不通）──▼───────────────────────────┐
│  kb-embedding：bge-base-zh-v1.5（FastEmbed/ONNX，~800MB） │
└───────────────────────────────────────────────────────────┘
```

为什么这么分：A 机内存放不下向量模型；C 机国内访问不到但 B 能到，所以 C 只服务 B；所有模型调用统一走 B，换模型只改网关配置。

**工具接口三种类型**

| 类型 | 定义方式 | 安全机制 |
|---|---|---|
| 命令型 | `binary` + `argv` 模板，参数独占槽位 | shell=False、参数正则白名单、解释器黑名单、写动词黑名单 |
| 脚本型 | 引用 `/opt/ops/scripts/` 下的脚本 | 只有管理员能放脚本；批准时登记 SHA-256，内容改了自动停用 |
| 接口型 | `url` 模板 + 可选 header | 仅 GET、主机名写死、参数 URL 编码、凭据只能引用 `OPS_SECRET_*`、返回脱敏、不跟随跳转 |

**文件分权**

| 文件 | 谁写 | 作用 |
|---|---|---|
| `ops_tools.yaml` | root 手写 | 唯一真相源 |
| `ops_tools.overrides.yaml` | 页面 | 只能改 enabled / desc / label |
| `ops_tools.pending.yaml` | 页面 | 待审队列，永不加载 |
| `ops_tools.trust.yaml` | 宿主机 CLI | 脚本哈希登记 |

## 6. 安全边界（十条）

1. Agent 拿不到 shell，也拿不到凭据——只能提交工具名和结构化参数
2. 参数先过正则白名单再执行，`kb-app; rm -rf /` 在执行前被拒
3. 禁止配置解释器：bash / sh / python / env / xargs / find / ssh 一律不能当工具
4. 接口只读且去向固定：仅 GET、主机名写死、不跟随跳转、返回脱敏
5. 写操作双重拦截：加载时查模板，执行前再比对
6. 页面能做什么靠文件权限划定：启停、改名、改说明、提申请；批准必须在宿主机
7. SOP 不扩权：只能引用已有工具
8. 脚本哈希锁定
9. 隔离与限流：工具接口仅 127.0.0.1 + 令牌；容器不挂 docker.sock；输出截断、超时
10. 联网不外泄、不污染：搜索词代码层拦截；网络内容标注未核实、其中指令忽略；只有人能存入知识库

**网关地址与 API key 永不进页面**（这是上次拒绝「页面填大模型」的依据）。

| C4 | **线上镜像早期烘焙了密钥** | 重建基础镜像，密钥只走 env |
| C5 | **Tavily 7 个 key 在聊天记录出现过** | 赛后轮换 |
| C6 | **可观测依赖 LangSmith（外部）** | 自托管 Langfuse |

### D. 产品层面值得想清楚的问题

1. **「小知」这个名字和「SOP」的关系够不够直白？** 评委 30 秒内能否理解「文档 → SOP → 工具」？一页纸里的 ASCII 图是关键，演示时第一句话就该说它。
2. **三个场景是否过于分散？** 运维 / 研发 / 行政各一个，证明了通用性，但每个都浅。要不要把一个场景做深（比如巡检：周报趋势、异常追踪），另两个作为「换场景只需换文档」的佐证？
3. **SOP 的「执行」是否应该有独立入口？** 现在只能在对话里问一句触发。一个「▶ 执行此 SOP」按钮（本质是预填问题）会让「可执行」这个卖点更直观。
4. **知识库和联网存回的边界**：存回的《网络补充-…》文档和人写的文档混在一起，要不要在检索结果里区分标注「来自网络」？

## 9. 附：与同类方案的差异

| 方案 | 知识库 | 文档自动生成 SOP | 工具与权限 | 部署 |
|---|---|---|---|---|
| HolmesGPT（CNCF） | runbook | 手写 | YAML shell 模板 | 偏 K8s |
| kagent（CNCF） | 自建 | 无 | MCP | K8s |
| Dify / FastGPT / MaxKB | 完善 | 无，手工编排 | HTTP 插件，无统一只读审批 | 中等 |
| **小知** | 有，多模态 | **有** | **只读三类 + 文件分权 + 审批** | **单机 2C2G** |

四点取舍：SOP 从文档自动学会；安全靠结构不靠转义；一套安全模型覆盖所有岗位；知道自己不知道（判断 → 联网 → 人确认存回）。
