# 场景包：文档 + 工具 + SOP 的最小分发单元

doc2sop 的能力来自三样东西：知识库里的**文档**（人写的做法）、**工具**（宿主机批准的只读取数原语）、
**SOP**（把文档里的做法编排成对工具的有序调用）。一个岗位要用起来，三样都得有。
场景包就是把这三样按岗位打成一个目录，谁都能拿走就用、改了就能贡献回来。

仓库自带三个包，放在 [`packs/`](../packs/)：

| 目录 | 包名 | 工具 | SOP | 数据从哪来 |
|---|---|---|---|---|
| `leave-planning` | 行政-请假拼假 | `holiday_calendar`（公网 HTTP）、`date_info`（内置函数） | 《请假拼假核对》 | 公网 CDN 上的节假日数据集；星期由工具服务内置计算 |
| `model-selfcheck` | 研发-模型调用自查 | `gateway_models`、`gateway_balance`（HTTP，用 `.env` 里的模型地址与 key） | 故意不带，演示 SOP 从实践里长出来 | 你自己的模型服务（`.env` 填 `LLM_BASE_URL` / `LLM_API_KEY`）；余额接口是硅基流动的 |
| `ops-inspection` | 运维-日常巡检 | `host_disk` / `host_resources` / `host_uptime` / `list_containers` / `container_stats`（命令型，`os: linux`） | 《日常巡检》 | 至少一台能读 docker 的 Linux 主机：工具服务所在的宿主机，或主机清单里的远程主机（按 `target` 远程跑，`@组` 就是多机巡检） |

前两个不依赖工具服务所在机器装了什么，是 `docker compose` 一键演示（`DEMO_PACKS`）的默认内容；第三个要查真实主机，不进 `DEMO_PACKS`——
演示站只拿它的磁盘、内存、负载三个工具（`DEMO_HOST_PACKS`）演示多机巡检，因为演示主机上没有 docker。

## 目录格式

```
packs/<id>/
├── pack.yaml      元信息
├── docs/          要入库的文档：.md .txt .pdf .docx .pptx 或图片，和页面上传的限制一样
├── tools.yaml     工具定义，与 deploy/ops_tools.yaml 完全同格式的 tools: 列表
└── sops.json      预先整理好的 SOP（可以是空数组 []）
```

`<id>` 只能用小写字母、数字和连字符（它要出现在 `DEMO_PACKS` 和接口路径里）；中文名写在 `pack.yaml` 里。

### pack.yaml

```yaml
id: leave-planning            # 必须和目录名一致
name: 行政-请假拼假             # 显示名
version: 1                    # 改了内容就 +1；导入器据此判断「已导入的是不是旧版」
summary: 一句话说明它解决什么问题   # 必填
roles: [行政, 人事, 全员]        # 适用岗位
requires:                     # 数据从哪来：公网接口、你自己的服务、某类主机……给人读
  - 节假日数据来自公网：jsdelivr CDN 上的 holiday-cn 数据集
category: 行政制度             # 文档入库时的分类，省掉一次模型判断
examples:                     # 示例问题，导入后出现在欢迎页上，点一下就问；最多 6 条。别写死年份，让 Agent 按今天的日期定
  - 国庆想连休到 10 月 11 日要请几天年假
```

`requires` 写**数据从哪来**，不写「工具服务所在机器要装什么」：纯计算用内置函数，不需要任何命令；命令型工具用 `os`
声明适用的系统；接口型工具要访问的网络、要用的连接和凭据，在这里写明。

### tools.yaml

就是 [`deploy/ops_tools.yaml`](../deploy/ops_tools.yaml) 的一个子集，字段、工具类型与安全约定见那个文件头部的注释。
几点额外约束：

- **只允许内置、命令型、接口型和 MCP 型**，老写法和 `impl` 新写法都行（见 [`工具.md`](工具.md)「能力与实现分开写」）。
  脚本型工具要宿主机 root 把脚本放进 `scripts/` 并 `trust`，不是一个目录能自带的东西。
- 命令型工具写明 `os`（运维巡检包是 `os: linux`）：主机不是这个系统时，它们显示「不适用」，而不是「缺命令」。
- **包里不能声明 `hosts`**（会被忽略并报出来）：主机清单和私钥只能由宿主机管理员写在主文件里。配了主机清单后，包里的命令型工具
  自动多一个 `target` 参数，在哪台主机上跑由管理员的清单决定，包不用改。
- 接口型工具的凭据只能按名字引用（`${名字}` 即环境变量 `OPS_SECRET_名字`，或老写法 `${OPS_SECRET_xxx}`），由部署工具服务的人提供；包里永远不含任何 key。
- **包里不能声明 `connections`**（会被忽略，自检也会报出来）：连接只能由宿主机管理员写在主文件里。包里的接口工具可以用 `conn:`
  引用管理员建好的连接，在 `requires` 里写明需要哪个连接。被 include 的文件仍和主文件同等可信，包里的接口工具也能直接写凭据引用，
  所以启用别人的包之前，先读一遍它的 `tools.yaml`。
- MCP 型条目只是「允许调用某个 server 上的某个工具」的引用；**包里不能声明 `mcp_servers`**（会被忽略），
  server 必须由宿主机管理员在主文件里声明。[`deploy/mcp/holiday_tools.yaml`](../deploy/mcp/holiday_tools.yaml) 是把拼假包两个工具换成 MCP 来源的例子。

应用**只读这个文件里的工具名**，不会把工具定义送到任何地方执行——工具由谁加载，见下面「启用一个包的工具」。

### sops.json

```json
[
  {
    "name": "请假拼假核对",
    "trigger": "什么时候用它：一句话",
    "source": "休假管理制度.md",
    "enabled": true,
    "steps": [
      {"tool": "holiday_calendar", "args": {"year": ""},
       "checkpoint": "这一步看什么、怎么判断",
       "evidence": "支撑这一步的文档原句（可选，供人核对）"}
    ]
  }
]
```

- `steps[].tool` **只能引用本包 `tools.yaml` 里的工具**——包必须自洽，别人装了它才跑得起来。
- `args` 里要用户使用时再填的值写空字符串。
- `source` 可选，默认是包里第一篇文档的文件名。SOP 面板按它分组；删除那篇文档会连带删掉 SOP，和「从文档抽取」的行为一致。
- `enabled` 可选，默认 `true`。

这就是 `GET /api/playbooks/{id}` 返回的形状去掉 `id / updated_at`；导出接口（见下）直接产出这个格式。

## 导入一个包会发生什么

1. `docs/` 里的文档逐个走和页面上传完全相同的入库流程（解析、切块、向量化），分类用 `pack.yaml` 的 `category`。
2. `sops.json` 里的 SOP 逐个走 `playbooks.save()`——**必经 `validate()`：步骤只能引用此刻真实可用的工具**。
   所以导入一个包不会凭空多出任何执行权限，这条线和「从文档抽取」「从实践沉淀」是同一条。
3. 记到 `data/packs.json`：包 id、版本、导入时间。再次启动不重导；包升级了也不自动重导（会重置人改过的启停状态）。

一个包所需的工具没有上线，就**整个包等着**（状态里写明缺哪些），不会先导文档、留下半个包。

SOP 的 id 由 `sha1("pack:<包id>:<SOP 名>")` 推导，重导是覆盖，不是再长一份。

### 自动导入

`.env` 里 `DEMO_PACKS=leave-planning,model-selfcheck`：应用启动后起一个后台线程，等到模型配好（`.env` 或页面）、
且包里的工具都在线，就依次导入，然后退出。欢迎页的引导卡会显示进度和卡在什么上。留空则不自动导入。

### 手动导入 / 查看 / 导出

```bash
# 所有包的状态：元信息、是否导入过、缺哪些工具、格式问题
curl -u admin:密码 http://127.0.0.1:8765/api/packs

# 导入一个包（同步；同版本已导入则 skipped=true；?force=1 重导）
curl -u admin:密码 -X POST 'http://127.0.0.1:8765/api/packs/ops-inspection/import'
#   409 = 条件未就绪（模型没配 / 工具没上线，响应里写明）；400 = 包内容不合法

# 把库里某个来源下的 SOP 按 sops.json 的格式导出——现场长出来、核对过的 SOP 就这样进包
curl -u admin:密码 'http://127.0.0.1:8765/api/packs/export?source=从实践沉淀' > sops.json
```

## 启用一个包的工具

工具定义只在宿主机那一份文件里维护（见 [`工具.md`](工具.md)「加一个工具」）。`ops_readonly.py` 支持顶层 `include:`，
启用一个包就是加一行：

```yaml
# deploy/ops_tools.yaml（宿主机）
include:
  - ../packs/leave-planning/tools.yaml        # 相对本文件目录
  - /opt/doc2sop/packs/*/tools.yaml           # 也可以 glob
tools:
  - ...
```

被包含的文件和主文件同等可信（它们是管理员亲手写进主文件的路径），同样只能由 root 维护，自己不能再 include。
改动被包含的文件同样即时生效，不用重启。接口型工具需要的 `OPS_SECRET_*` 写进工具服务的 `EnvironmentFile`。

一键演示里的 sidecar（`kb-ops`）就是这么工作的：它的入口脚本按 `DEMO_PACKS` 生成 `include` 列表——导入哪些包，就只提供哪些包的工具。

## 贡献一个包

1. 在 `packs/` 下新建目录，照上面的格式放四样东西。文档要是通用示例内容，不要带真实公司信息。
2. 自检：`python -m unittest tests.test_packs`——它会校验仓库里每个包：`pack.yaml` 字段齐全、工具定义能被
   `ops_readonly.py` 零问题加载、SOP 只引用本包工具、演示包不依赖宿主机能力。
3. 真跑一遍：把包 id 加进 `.env` 的 `DEMO_PACKS`（工具需要宿主机能力的包除外），`docker compose up -d`，
   按 `pack.yaml` 里的 `examples` 问一遍，确认 Agent 的回答对照了文档、调对了工具。
4. 提 PR。README 的「场景包」表里加一行。

SOP 不必手写：先只放文档和工具，用「从文档抽取」或让 Agent 自由排查后「沉淀为 SOP」，核对、启用，
再用导出接口生成 `sops.json`。
