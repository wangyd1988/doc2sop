# 正式部署：宿主机 host 网络 + `deploy/release.sh`

一键演示（`docker compose up`）是给陌生人五分钟跑通用的单机形态。正式用时推荐这份文档的形态：
应用容器跑在 **host 网络**，工具服务 `deploy/ops_readonly.py` 以 systemd 跑在宿主机上、只监听 `127.0.0.1`，
模型网关（LiteLLM）或到网关的 SSH 隧道同样只绑 `127.0.0.1`——容器用 host 网络才能直接访问它们，所以这条路径**不走 compose**，
用 `deploy/release.sh` 构建、切换、校验、回滚。

| | 一键演示（compose） | 正式部署（本文） |
|---|---|---|
| 网络 | bridge；应用发布到 `127.0.0.1:APP_PORT`，工具是 sidecar 容器 | host；应用监听 `PORT`（默认 8765），工具和网关都在宿主机 `127.0.0.1` 上 |
| 构建 | `docker compose up --build`，依赖每次走构建缓存 | 依赖预烘焙成 `kb-app:base-<哈希>`，发版只 COPY 代码，几秒钟 |
| 切换 | compose 重建容器 | 停旧 → 起新 → 等就绪 → **比对片段总数** → 不一致自动回滚 |
| 工具 | 来自场景包，`OPS_URL=http://kb-ops:8799` | 宿主机 `ops_readonly.py`，`OPS_URL=http://127.0.0.1:8799`，`include` 场景包的 tools.yaml |
| 配置文件 | 仓库目录里的 `.env` | 任意位置，例如 `/opt/kb-app/.env`，用 `ENV_FILE=` 指给脚本 |

两种形态跑的是同一份代码和同一个 `Dockerfile`（compose 构建它的末尾 `app` 阶段，发版脚本单独用 `base` 阶段）。

## 宿主机布局（推荐）

```
/opt/doc2sop/                 代码：git clone，升级就是 git pull；脚本、文档、场景包都在这里
/opt/kb-app/.env              应用配置（含密钥，0600）；容器的 --env-file
/opt/kb-app/data/             知识库数据：向量库、SQLite、原件；挂到容器 /data
/opt/kb-app/backups/          每日备份包（deploy/backup.sh）
/opt/ops/ops_readonly.py      工具服务（deploy/ 下同名文件的拷贝）
/opt/ops/ops_exec.py          执行核心（deploy/ 下同名文件的拷贝），必须和 ops_readonly.py 放在同一个目录
/opt/ops/ops_tools.yaml       工具定义的唯一真相源；旁路文件 overrides / pending / trust / mcp / known_hosts 在同目录
/opt/ops/mcp/                 可选：MCP server（如 holiday_mcp.py）
/opt/ops/vendor/              可选：数据库驱动（pip install --target），属 root、组和其他用户不可写，见下文「接数据库」
/etc/ops-readonly.env         工具服务的环境：OPS_TOKEN、OPS_SECRET_*、KUBECONFIG（0600）
/etc/ops-readonly/            可选：连远程主机的私钥、K8s 只读账号的 kubeconfig / 令牌 / CA（0600，属工具服务的运行账号；ProtectHome=yes 时不能放 /root）
/opt/doc2sop-sandbox/         可选：计算沙箱服务（deploy/sandbox/ 下同名文件的拷贝），见下文「计算沙箱」
/etc/doc2sop-sandbox.env      沙箱服务的令牌 SANDBOX_TOKEN（0600）
```

目录名随意，脚本全部参数化；下面的命令按这个布局写。

## 首次安装

```bash
git clone https://github.com/wangyd1988/doc2sop.git /opt/doc2sop
mkdir -p /opt/kb-app/data && cp /opt/doc2sop/.env.example /opt/kb-app/.env && chmod 600 /opt/kb-app/.env
# 编辑 /opt/kb-app/.env：WEB_PASSWORD、模型地址与 key；COMPOSE_PROFILES 留空；
# OPS_URL=http://127.0.0.1:8799、OPS_TOKEN 与下面 /etc/ops-readonly.env 里的一致。文件保持 LF、无 BOM。
```

工具服务（systemd，模板见 [`deploy/ops-readonly.service.example`](../deploy/ops-readonly.service.example)）：

```bash
mkdir -p /opt/ops && cp /opt/doc2sop/deploy/ops_readonly.py /opt/doc2sop/deploy/ops_exec.py /opt/doc2sop/deploy/ops_tools.yaml /opt/ops/
printf 'OPS_TOKEN=%s\n' "$(openssl rand -hex 24)" > /etc/ops-readonly.env && chmod 600 /etc/ops-readonly.env
# 需要「模型网关」组工具就再加 OPS_SECRET_GATEWAY_URL / OPS_SECRET_GATEWAY_KEY；K8s 工具加 KUBECONFIG（用只读账号，见下文「K8s 只读账号」）
cp /opt/doc2sop/deploy/ops-readonly.service.example /etc/systemd/system/ops-readonly.service   # 核对 ExecStart 里的路径
systemctl daemon-reload && systemctl enable --now ops-readonly
curl -s -H "X-Ops-Token: $(sed -n 's/^OPS_TOKEN=//p' /etc/ops-readonly.env)" http://127.0.0.1:8799/health
```

要用场景包的工具，在 `/opt/ops/ops_tools.yaml` 顶层加一行 `include: [/opt/doc2sop/packs/leave-planning/tools.yaml]`，改完即时生效。

页面上批准工具要另输的**审批口令**由你自己在宿主机上设（不设也能用，只是页面上只能看、能拒绝，批准走命令行），见下文「页面审批：审批口令」：

```bash
python3 /opt/ops/ops_readonly.py set-approval-passphrase      # root；交互输入两次，不回显，至少 12 个字符
```

发版（第一次会先构建依赖镜像，2 核机器约 10 分钟；之后每次只 COPY 代码）：

```bash
cd /opt/doc2sop
ENV_FILE=/opt/kb-app/.env DATA_DIR=/opt/kb-app/data bash deploy/release.sh
```

国内网络：Docker Hub 不通就 `BASE_IMAGE=docker.m.daocloud.io/library/python:3.12-slim`，PyPI 慢就
`PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple`——两者都可以写进 `/opt/kb-app/.env`（脚本会读），也可以当环境变量传。

脚本结束会打印运行中的镜像、切换前后片段数和回滚命令。核对：

```bash
docker ps --filter name=kb-app --format '{{.Names}} {{.Image}} {{.Status}}'
curl -s -u admin:'密码' http://127.0.0.1:8765/api/tools | head -c 300     # 列出宿主机工具
```

## 脚本参数

`bash deploy/release.sh --help` 有全文。要点：

| 变量 / 选项 | 含义 | 默认 |
|---|---|---|
| `ENV_FILE` | 容器的 `--env-file`，也从这里读 `PORT`、`WEB_USER`、`WEB_PASSWORD` 和下面的 `APP_*` | `<仓库>/.env` |
| `DATA_DIR` | 挂到容器 `/data` | `<仓库>/data` |
| `APP_CONTAINER` | 容器名；container-guard、监控引用的就是它 | `kb-app` |
| `APP_IMAGE` | 镜像名；冒号前作为仓库名，时间戳 tag 与 `base-<哈希>` 都打在它上 | `kb-app:latest` |
| `APP_MEM_LIMIT` / `APP_CPUS` | `--memory` / `--cpus` | `900m` / `1.5` |
| `APP_PORT` | 探活端口；host 网络下等于 `.env` 的 `PORT` | `.env` 的 `PORT`，再默认 8765 |
| `BASE_IMAGE` / `PIP_INDEX_URL` | 构建依赖镜像用的基础镜像 / pip 源 | `python:3.12-slim` / 官方源 |
| `KEEP_IMAGES` / `START_TIMEOUT` | 保留几个时间戳镜像 / 等新容器就绪多少秒 | `2` / `120` |
| `--image kb-app:<tag>` | 不构建，直接切到一个已有镜像（回滚） | |
| `--rebuild-base` | 强制重建依赖镜像 | |
| `--backup` | 切换前先跑 `deploy/backup.sh`（备份目录 `BACKUP_DIR`，默认 `<DATA_DIR 上级>/backups`） | |
| `--print-config` | 只打印解析后的配置，不碰 docker | |

优先级：环境变量 > `ENV_FILE` 里的同名键 > 默认值。密钥只从环境文件读进内存，探活用的 Basic 凭据经 curl 的 stdin 配置传入，不进命令行，也不打印。
默认值适合「在仓库 clone 目录里直接跑」：`bash deploy/release.sh` 就用 `./.env` 和 `./data`。在仓库任意路径下调用都行，脚本按自己的位置找仓库根。

## 升级

```bash
cd /opt/doc2sop && git pull && ENV_FILE=/opt/kb-app/.env DATA_DIR=/opt/kb-app/data bash deploy/release.sh
```

把 `ENV_FILE`、`DATA_DIR` 写进 `/opt/kb-app/.env`？不行——它们决定去哪儿找这个文件；但 `APP_*`、`BASE_IMAGE`、`PIP_INDEX_URL` 可以写在里面，命令就短成 `ENV_FILE=/opt/kb-app/.env DATA_DIR=/opt/kb-app/data bash deploy/release.sh`。

脚本做的事和失败时的行为：

1. `requirements.txt`、`Dockerfile` 的 base 阶段、`BASE_IMAGE`、`PIP_INDEX_URL` 一起算哈希；`kb-app:base-<哈希>` 不存在才 `docker build --target base`。
2. 用 [`deploy/Dockerfile.release`](../deploy/Dockerfile.release) 在 base 上只 COPY `app/` `packs/`，打 `kb-app:<yyyymmddHHMMSS>`，带 `doc2sop.commit` 标签（`docker inspect` 能看到跑的是哪个提交）。
3. 记下当前片段总数（`/api/documents`）→ `docker stop -t 60` → 改名为 `kb-app-prev` → `docker run -d --network host --env-file … -v DATA_DIR:/data --memory --cpus`。
4. 等 `/api/documents` 返回 200（最多 `START_TIMEOUT` 秒）→ 再读片段总数 → **和切换前不一致、起不来或超时：打印新容器最后 40 行日志，删掉它，把 `kb-app-prev` 改回 `kb-app` 并启动**，退出码 1。
5. 成功：删 `kb-app-prev`，只保留最近 `KEEP_IMAGES` 个时间戳镜像和当前 base，打印回滚命令。

中断约 30–60 秒（停旧容器 + 新容器加载向量库）。如果发现 `kb-app-prev` 残留（上次发版中途被杀），脚本会拒绝开始并给出两条收尾命令。

ops 服务不在镜像里，升级它要单独做（改了 `deploy/ops_readonly.py` 或 `deploy/ops_exec.py` 才需要）。两个文件一起换、一起备份——
`ops_readonly.py` 启动时加载同目录的 `ops_exec.py`，缺了它服务起不来：

```bash
STAMP=$(date +%Y%m%d%H%M%S)
for f in ops_readonly.py ops_exec.py; do
  cmp -s /opt/doc2sop/deploy/$f /opt/ops/$f && continue
  [ -f /opt/ops/$f ] && cp -a /opt/ops/$f /opt/ops/$f.bak-$STAMP
  cp /opt/doc2sop/deploy/$f /opt/ops/ && CHANGED=1
done
[ -n "${CHANGED:-}" ] && systemctl restart ops-readonly && sleep 2 && \
  curl -s -H "X-Ops-Token: $(sed -n 's/^OPS_TOKEN=//p' /etc/ops-readonly.env)" http://127.0.0.1:8799/health
```

`/health` 返回的工具数应与升级前一致；`/opt/ops/ops_tools.yaml` 是你的配置，升级不会动它。回滚：把 `.bak-$STAMP` 两个文件拷回去再重启。
接入了远程主机（受控模式）时，`ops_exec.py` 有改动还要 `ops_readonly.py push` 一遍，主机上的执行器跟着换。
页面审批要新版工具服务：应用已经升级、工具服务还是旧的时，「待审批」里能看、能拒绝，批准按钮不可用并写明「工具服务版本较旧」。

**场景包和工具服务要一起升级。** 场景包的 `tools.yaml` 会用到工具服务新支持的写法（比如 `impl: {type: builtin}`）。
如果 `/opt/ops/ops_tools.yaml` 直接 include 了 `/opt/doc2sop/packs/...`，`git pull` 之后旧版工具服务会热加载到新写法的条目，
把它们当坏条目跳过（日志里有原因），直到按上面的命令换上新的 `ops_readonly.py`。所以 `git pull` 之后紧接着升级工具服务。

## 备份

[`deploy/backup.sh`](../deploy/backup.sh)：SQLite（会话、SOP、图谱、Agent 记忆、对外接入的令牌与审计）在线一致性复制 + 向量库 + 原件 + `/opt/ops/ops_tools*.yaml` 打成一个 tgz，保留最近 7 份。

```bash
echo '30 3 * * * root KB_DATA=/opt/kb-app/data bash /opt/doc2sop/deploy/backup.sh /opt/kb-app/backups >> /var/log/kb-backup.log 2>&1' > /etc/cron.d/kb-backup
KB_DATA=/opt/kb-app/data bash /opt/doc2sop/deploy/backup.sh /opt/kb-app/backups      # 手动跑一次确认产出
```

恢复：`docker stop kb-app` → 把包里的 `data/` 解到 `/opt/kb-app/data`（`ops/` 下的工具配置按需放回 `/opt/ops`）→ `docker start kb-app`。

## 内存看护（可选）

2 GB 的机器上应用容器长时间运行后内存会缓慢爬升。[`deploy/container-guard.sh`](../deploy/container-guard.sh) 只在用量超过阈值时重启容器，配一个 systemd timer 每天凌晨跑一次：

```ini
# /etc/systemd/system/container-guard.service
[Unit]
Description=Restart kb-app when its memory creeps up
After=docker.service
Requires=docker.service
[Service]
Type=oneshot
ExecStart=/opt/doc2sop/deploy/container-guard.sh kb-app 600

# /etc/systemd/system/container-guard.timer
[Unit]
Description=Daily memory check for kb-app
[Timer]
OnCalendar=*-*-* 04:50:00
Persistent=true
RandomizedDelaySec=120
[Install]
WantedBy=timers.target
```

`systemctl enable --now container-guard.timer`。它引用的是容器名，所以发版脚本的 `APP_CONTAINER` 要和这里一致。

## 对外接入（MCP）

让同事的 Claude Code、GitHub Copilot、Cursor 接进来查知识库、按 SOP 排查（能开放什么、令牌、审计见
[`工具.md` 的「对外 MCP 出口」](工具.md#对外-mcp-出口让-claude-codecopilotcursor-用上知识库和-sop)）。默认关，打开分三步：

1. **打开出口**：`/opt/kb-app/.env` 里 `MCP_ENABLED=true`，照常发版。验证：
   `curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8765/mcp` 返回 401（关着时是 404）。
2. **签发令牌**：左侧导航「对外接入」→ 签发，每个客户端一枚；明文只显示一次，页面同时给出 Claude Code、VS Code、Cursor 的配置片段。
   要开放数据工具，先在 `/opt/ops/ops_tools.yaml` 里标 `export`（见上面链接），工具服务热加载，不用重启。
3. **网络**：应用直接在 `0.0.0.0:PORT` 上跑明文 HTTP，令牌和返回内容都是明文。按使用范围选一种：
   - **只在本机或经 SSH 隧道用**（最省事，不用域名和证书）：`.env` 里设 `MCP_CLIENTS=127.0.0.1,::1`，发版；
     使用的人开 `ssh -N -L 8765:127.0.0.1:8765 用户@宿主机`，客户端连 `http://127.0.0.1:8765/mcp`，
     令牌也在隧道开着时从 `http://127.0.0.1:8765` 打开「对外接入」页签发（页面给的接入地址取自浏览器地址栏）。
     `MCP_CLIENTS` 查的是 TCP 对端地址：经隧道进来的连接对端是本机，公网来的一律 403，带着有效令牌也一样，令牌库都不碰。
     只有在应用端口前面没有本机的转发程序（realm、haproxy、nginx……）转到它时才成立，否则转发进来的连接对端也是本机。
   - **对内网开放：前面放反向代理和 TLS**，应用端口只对代理开放。`/mcp` 用 SSE 推流，代理要关缓冲、放长读超时，并单独限流：

```nginx
limit_req_zone $binary_remote_addr zone=mcp:10m rate=5r/s;
server {
    listen 443 ssl;
    server_name kb.example.com;
    ssl_certificate     /etc/ssl/kb.example.com.pem;
    ssl_certificate_key /etc/ssl/kb.example.com.key;
    location /mcp {
        limit_req zone=mcp burst=20 nodelay;
        proxy_pass http://127.0.0.1:8765;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_buffering off;              # SSE：事件要立刻推给客户端
        proxy_read_timeout 3600s;         # 2025 版客户端的通知流是长连接
    }
    location / { proxy_pass http://127.0.0.1:8765; proxy_set_header Host $host; }
}
```

   代理后面想再加一道，就在 `.env` 里设 `MCP_ALLOWED_HOSTS=kb.example.com`：Host 头不在名单里的请求一律 421。
   客户端连 `https://kb.example.com/mcp`。

**Host 检查不是访问控制。** `MCP_ALLOWED_HOSTS` 防的是 DNS 重绑定（恶意网页借浏览器打本机端口）和客户端误填地址；
Host 头由客户端随便写，拿到令牌的人带上 `Host: 127.0.0.1:8765` 照样能从公网连。要限制谁能连，用 `MCP_CLIENTS`
（来源 IP 或网段）、安全组或反向代理。代理在本机时，uvicorn 默认信任 `127.0.0.1`、`::1` 发来的 `X-Forwarded-For`，
`MCP_CLIENTS` 看到的就是真实客户端的地址，按客户端的网段填；公网来的连接不受信任，伪造 `X-Forwarded-For` 改不了对端地址。
别把 `FORWARDED_ALLOW_IPS` 设成 `*`，否则谁都能用这个头冒充本机。

令牌丢了就在页面上吊销重签（库里只存哈希，找不回明文）。吊销后下一个请求就失败，它还连着的通知流当场断开、开着的会话一并关掉。

## 页面审批：审批口令

工具申请可以在页面「工具 → 待审批」里批准（能看到什么、风险提示怎么定的，见 [`工具.md` 的「审批」](工具.md#审批在页面上审批口令或在宿主机命令行上)）。
批准时要另输一个**审批口令**：它和网页登录密码无关，只以加盐的慢哈希存在工具服务这台机器上、由工具服务核对，网页密码泄露、
应用被攻破都加不了工具。**口令由管理员自己设**，发版脚本不替你设，也不生成：

```bash
# 设置或重置（root；交互输入两次，不回显，至少 12 个字符）。正在运行的工具服务不用重启
python3 /opt/ops/ops_readonly.py set-approval-passphrase
ls -l /etc/ops-readonly/approval.hash        # -rw------- root root
# 从自己的电脑上远程设：ssh -t 才能交互输入
ssh -t root@宿主机 "python3 /opt/ops/ops_readonly.py set-approval-passphrase"
```

- 没设之前，页面上的批准按钮不可用，并写明在宿主机上怎么设；拒绝照常，命令行审批（`pending` / `approve` / `reject` / `trust`）照常。
- 文件要求：普通文件、不是符号链接、属 root、组和其他用户不能读写（`chmod 600`）。不满足就当作没设，`journalctl -u ops-readonly`
  里有一行 `[approval]` 写明原因，页面上也写着。位置可以用环境变量 `OPS_APPROVAL_FILE` 改（写进 `/etc/ops-readonly.env`）。
- 忘了口令就用同一个命令重设；不想再用页面审批就删掉这个文件。
- **锁定**：连续输错 5 次，页面审批锁 15 分钟（批准、重新确认脚本、提交并立即批准共用这个计数）。锁在内存里，急用就
  `systemctl restart ops-readonly`；锁定期间命令行审批照常。
- 每次尝试在工具服务的日志里记一行，只有结果和来源：`[approval] 批准 nginx_errors（a1b2c3d4）：口令错误（连续第 2 次） caller=web user=admin ip=…`。

**残余风险：口令经明文 HTTP 传输。** 应用在 `0.0.0.0:PORT` 上跑明文 HTTP，网页密码和审批口令在网络上都是明文。审批口令挡住的是
「只拿到了网页密码」的人；能在路上抓包的人两个都拿得到。所以审批尽量从本机地址打开页面：`ssh -N -L 8765:127.0.0.1:8765 root@宿主机`，
浏览器开 `http://127.0.0.1:8765`（不是从本机地址打开时，输口令的对话框里会提示一句）；长期对内网开放就按上面「对外接入」的写法，
前面放反向代理和 TLS。

**防跨站请求伪造。** 页面用 Basic 认证，浏览器会自动带上凭据，所以应用拒绝别的网站发起的修改请求：`/api/` 下除 GET、HEAD 以外的请求，
Origin（没有就看 Referer）的主机和端口跟请求的 Host 对不上就 403。前面有反向代理时要原样转发 Host（`proxy_set_header Host $host;`，
上面的 nginx 片段已经写了），否则页面上的修改都会被当成跨站请求拒绝。curl、评测脚本不带这两个头，不受影响。

## 计算沙箱（python_exec）

让模型写一段 Python 把统计、比对算准（能读什么、返回什么、各项限制见 [`工具.md` 的「计算类与沙箱」](工具.md#计算类与沙箱python_exec)）。
应用不挂 `docker.sock`：起容器的是宿主机上的沙箱服务（systemd，只监听 `127.0.0.1:8797`），每次执行一个用完即弃的 gVisor 容器。
默认不装、应用里 `SANDBOX_URL` 留空。分三步，前两步不影响线上；第三步才让应用用上它。

**1. 装 gVisor（runsc）：只 reload docker，不要 restart。** `runtimes` 是 dockerd 收到 SIGHUP 就重新加载的配置项，
reload 不重启 daemon、不碰正在跑的容器；restart 会让所有容器重启（没开 live-restore 时）。

```bash
V=20261026.0; URL=https://storage.googleapis.com/gvisor/releases/release/$V/$(uname -m)
mkdir -p /root/gvisor-$V && cd /root/gvisor-$V
curl -fsSLO "$URL/gvisor.tar.zstd" && curl -fsSLO "$URL/gvisor.tar.zstd.sha512"
sha512sum -c gvisor.tar.zstd.sha512       # 再和 GitHub release 页的 SHA512SUMS 对一遍；宿主机下不动就在别处下好、核对后 scp 过来
tar --zstd -xf gvisor.tar.zstd -C /usr/local/bin     # runsc、containerd-shim-runsc-v1、gvisor-bin/（要和 runsc 放在一起）
/usr/local/bin/runsc --version

# daemon.json 只加 runtimes 这一项；先校验再换上，换之前留备份（原来没有这个文件就记下「没有」）
test -f /etc/docker/daemon.json && cp -a /etc/docker/daemon.json /etc/docker/daemon.json.bak-$(date +%Y%m%d%H%M%S)
python3 -c 'import json, os; p = "/etc/docker/daemon.json"; c = json.load(open(p)) if os.path.exists(p) else {}
c.setdefault("runtimes", {})["runsc"] = {"path": "/usr/local/bin/runsc"}; json.dump(c, open(p + ".new", "w"), indent=2)'
dockerd --validate --config-file /etc/docker/daemon.json.new && mv /etc/docker/daemon.json.new /etc/docker/daemon.json
docker inspect -f '{{.Name}} {{.State.StartedAt}}' $(docker ps -q) > /root/started-before-reload.txt
systemctl reload docker
docker info --format '{{json .Runtimes}}'                # 里面有 runsc
docker inspect -f '{{.Name}} {{.State.StartedAt}}' $(docker ps -q) | diff /root/started-before-reload.txt - && echo 没有容器被重启
docker run --rm --runtime=runsc --network=none --pull=never python:3.12-slim cat /proc/version   # gVisor 报的内核，不是宿主机的
```

**2. 构建镜像、装沙箱服务**（模板 [`deploy/sandbox/doc2sop-sandbox.service.example`](../deploy/sandbox/doc2sop-sandbox.service.example)）：

```bash
cd /opt/doc2sop
docker build --build-arg PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple \
  -t doc2sop-sandbox:$(git rev-parse --short HEAD) -t doc2sop-sandbox:latest deploy/sandbox
useradd --system --no-create-home --shell /usr/sbin/nologin doc2sop-sandbox    # docker 组只由单元文件给这个进程
install -d -m 755 /opt/doc2sop-sandbox
install -m 644 deploy/sandbox/sandbox_service.py deploy/sandbox/security_check.py /opt/doc2sop-sandbox/
(umask 077; printf 'SANDBOX_TOKEN=%s\n' "$(openssl rand -hex 24)" > /etc/doc2sop-sandbox.env)
cp deploy/sandbox/doc2sop-sandbox.service.example /etc/systemd/system/doc2sop-sandbox.service
systemctl daemon-reload && systemctl enable --now doc2sop-sandbox
curl -s http://127.0.0.1:8797/health
python3 /opt/doc2sop-sandbox/security_check.py      # 真实环境的安全用例：全部 PASS 才继续，有一条 FAIL 就按下面撤销
```

服务启动时自检：连不上 docker、没注册 `runsc`、本机没有镜像，都会直接退出并说明原因（`journalctl -u doc2sop-sandbox`）。
它只认 `SANDBOX_IMAGE`（默认 `doc2sop-sandbox:latest`）、`SANDBOX_CONCURRENCY`（默认 1，最多 2）、`SANDBOX_QUEUE_SECONDS`（默认 10），
都写在 `/etc/doc2sop-sandbox.env`；限制本身写死在代码里。内存：服务常驻约 20MB；每次执行时多出一个 `docker run` 客户端、
一个 containerd shim 和 gVisor 的沙箱进程，容器（含 gVisor 自己）封顶 256MB——2 核 2GB 的机器上并发保持 1。
发版脚本只清理 `kb-app` 的镜像，不碰 `doc2sop-sandbox`。

**3. 让应用用上它**：把令牌原样放进应用的 `.env`（不打印），再按当前镜像重启应用。

```bash
printf 'SANDBOX_URL=http://127.0.0.1:8797\n%s\n' "$(grep '^SANDBOX_TOKEN=' /etc/doc2sop-sandbox.env)" >> /opt/kb-app/.env
cd /opt/doc2sop && ENV_FILE=/opt/kb-app/.env DATA_DIR=/opt/kb-app/data bash deploy/release.sh \
  --image "$(docker inspect kb-app --format '{{.Config.Image}}')"
```

关掉：从 `.env` 删掉这两行，同样按当前镜像重启，`python_exec` 就不再绑定。

**升级**：`deploy/sandbox/sandbox_service.py` 改了才换（`cmp` → 备份 → 拷贝 → `systemctl restart doc2sop-sandbox`）；
`deploy/sandbox/Dockerfile`、`requirements.txt` 改了就按第 2 步重新构建，下一次执行起就用新镜像，不用重启服务。

**撤销**（全部拆掉，倒着来）：

```bash
# 先关掉应用侧（上面「关掉」），再停服务、清容器、删镜像和文件
systemctl disable --now doc2sop-sandbox && rm -f /etc/systemd/system/doc2sop-sandbox.service && systemctl daemon-reload
docker ps -aq --filter label=doc2sop.sandbox | xargs -r docker rm -f
docker images doc2sop-sandbox --format '{{.Repository}}:{{.Tag}}' | xargs -r docker rmi
rm -rf /opt/doc2sop-sandbox /var/lib/doc2sop-sandbox /etc/doc2sop-sandbox.env && userdel doc2sop-sandbox
# 去掉 runsc：daemon.json 换回第 1 步的备份（原来没有这个文件就直接删掉），再 reload，不要 restart
#   原来有：cp -a /etc/docker/daemon.json.bak-<时间> /etc/docker/daemon.json && dockerd --validate --config-file /etc/docker/daemon.json
#   原来没有：rm /etc/docker/daemon.json
systemctl reload docker
docker info --format '{{json .Runtimes}}'                # 没有 runsc 了
rm -rf /usr/local/bin/runsc /usr/local/bin/containerd-shim-runsc-v1 /usr/local/bin/gvisor-bin
```

## 接入一台主机（远程主机，受控模式）

工具服务所在的机器（下称 A）经 SSH 去另一台 Linux 主机（下称 B）上跑只读工具。不配 `hosts` 时什么都不变；配置与原理见
[`工具.md`](工具.md)「远程主机」。B 上要放的东西都归 root，执行账号只能启动执行器、只能跑白名单里的工具。

1. **A：给工具服务一把专用私钥**（不设口令，靠文件权限保护；systemd 开了 `ProtectHome=yes` 时不能放在 `/root`）：

   ```bash
   install -d -m 0700 /etc/ops-readonly
   ssh-keygen -q -t ed25519 -N '' -C doc2sop-ops -f /etc/ops-readonly/id_ed25519      # 0600，属 root（工具服务的运行账号）
   echo 'OPS_SECRET_SSH_KEY=/etc/ops-readonly/id_ed25519' >> /etc/ops-readonly.env
   ```

2. **A：在 `/opt/ops/ops_tools.yaml` 顶层写主机清单**（改完即时生效；不写 `default` 时 `target` 不填就是 A 本机，现有工具和 SOP 照常）：

   ```yaml
   hosts:
     list:
       - {name: b, address: 150.109.244.82, user: opsread, key: "${ssh_key}", os: linux,
          tools: [list_containers, container_logs, container_stats, container_inspect, host_uptime, host_resources, host_disk]}
   ```

   `tools` 列出这台开放哪些工具；不写就是所有适用的命令型工具。

3. **A：登记 B 的 host key**。在 B 的控制台（不要经过这条网络）上看指纹：`for f in /etc/ssh/ssh_host_*_key.pub; do ssh-keygen -lf "$f"; done`，
   然后在 A 上：

   ```bash
   python3 /opt/ops/ops_readonly.py enroll b --from <A 连 B 的出口 IP> --env-file /etc/ops-readonly.env
   ```

   它列出 B 报上来的 host key，要你粘贴核对过的指纹，对上了才写进 `/opt/ops/ops_tools.known_hosts`，再打印 B 上要执行的安装片段。

4. **B：以 root 执行安装片段**：建执行账号（普通账号，不进 sudo；家目录也归 root、它写不了——家目录的主人能给 `~/.ssh` 改名、
   另放一把不带限制的公钥）、建 `/opt/ops-readonly`、写 `authorized_keys`
   （`restrict,from=…,command="/usr/bin/python3 -I /opt/ops-readonly/ops_exec.py --stdio"`，文件归 root，执行账号自己改不了；
   `-I` 是 Python 的隔离模式，不加载执行账号能写的 `~/.local`、不认 `PYTHON*` 环境变量，漏了它执行器拒绝启动）。
   要查容器，执行账号还要能读 docker，做法有三种：

   | 做法 | 好处 | 代价 |
   |---|---|---|
   | 把执行账号加进 `docker` 组 | 一行命令，现有容器工具原样可用 | docker 组约等于 root：一旦强制命令被绕开（比如有人给这个账号另放了一把不带限制的公钥），就是整台机器的 root。受控模式下账号只能启动执行器，风险收在白名单里 |
   | sudoers 只放行几条精确的 docker 命令 | 权限最小 | 执行器不支持 sudo（`sudo` 在解释器黑名单里），要另做改造；带参数的命令（容器名、行数）在 sudoers 里写不精确，通配符本身就是口子 |
   | 只读的 docker socket 代理（如 docker-socket-proxy，只放行 GET） | 账号拿不到写接口，绕开强制命令也写不了 | 主机上多一个常驻容器；工具模板要加 `-H unix:///…` 指向代理 |

5. **A：下发执行器和白名单**（用你自己的 SSH 身份，工具服务进程不持有能写 B 的凭据），然后核对：

   ```bash
   python3 /opt/ops/ops_readonly.py push --target b                   # 不能直接登录 B 的 root 时：--admin-user 你的账号 --sudo
   python3 /opt/ops/ops_readonly.py status --target b --env-file /etc/ops-readonly.env
   ```

   要走变更流程的，用 `push --target b --print --out /tmp/push` 导出 `allowlist.json`、`ops_exec.py`、`install.sh`，交给 Ansible 等去装。
   以后在 A 上改了工具定义、或升级了 `ops_exec.py`，再 `push` 一遍；没 push 之前，B 上对不上的工具会拒绝执行并提示「需要 push」。

**撤销一台主机**：

```bash
# B 上（root）：删账号的家目录（连同公钥）和执行器、再删账号。家目录归 root，userdel -r 不会删它
rm -r ~opsread /opt/ops-readonly && userdel opsread
# A 上：从 /opt/ops/ops_tools.yaml 的 hosts.list 删掉 b（即时生效），再删掉登记的 host key
sed -i '/^b /d' /opt/ops/ops_tools.known_hosts
```

只想暂停、不删东西：B 上把 `authorized_keys` 那一行注释掉即可，A 这边 b 会显示连不上。

**直连模式**（`mode: direct`）只要一个低权限账号和一行不带 `command=` 的公钥，不用 push；但「只读」完全靠账号权限，账号能做的事模型都能做，
页面上会标明。只在账号本身就只读、又装不了执行器的主机上用。

## 接数据库（SQL 工具）

SQL 工具的写法和三层只读见 [`工具.md` 的「SQL 工具」](工具.md#sql-工具按模板查只读数据库)。部署要做三件事：

1. **建只读账号**，只给要查的视图（SQL 见 `工具.md`）。密码只放工具服务的环境：在 `/etc/ops-readonly.env`（保持 0600）里加一行
   `OPS_SECRET_CMDB_PASSWORD=…`，配置里写 `${cmdb_password}`。
2. **装驱动**（sqlite 不用装）。不往系统 Python 里装——Debian 12、Ubuntu 23.04 起系统 pip 会报 `externally-managed-environment`（PEP 668），
   也不该为它动系统包。装进工具服务旁边的 `vendor/`，用到这种连接时才导入：

   ```bash
   python3 -m pip install --target /opt/ops/vendor 'psycopg[binary]>=3.1,<4'     # PostgreSQL
   python3 -m pip install --target /opt/ops/vendor 'PyMySQL>=1.1,<2'             # MySQL / MariaDB
   # 国内加 -i https://pypi.tuna.tsinghua.edu.cn/simple；--target 不受 PEP 668 限制
   chown -R root:root /opt/ops/vendor && chmod -R go-w /opt/ops/vendor
   ```

   `vendor/` 里的代码会以工具服务的身份导入，所以它必须是目录（不能是符号链接）、属于工具服务的运行账号、组和其他用户不可写，
   否则整个目录不用，工具页写明原因；位置可以用环境变量 `OPS_VENDOR_DIR` 改。机器上没有 pip 就先装 `python3-pip`（只用它的 `--target`）。
   工具服务的 Python 换了大版本，`psycopg[binary]` 要重装一遍。
3. **在 `/opt/ops/ops_tools.yaml` 建连接、写工具**，然后 `systemctl restart ops-readonly`（新装的驱动重启后才导入；之后只改配置不用重启）：

   ```yaml
   connections:
     - {name: cmdb, type: postgres, host: 10.0.0.12, database: cmdb, user: doc2sop_ro, password: "${cmdb_password}", tls: require}
   ```

核对：「工具 → 主机与数据源」页的连接表里有 `cmdb`（PostgreSQL，`10.0.0.12:5432/cmdb`），没有标「缺驱动」；用只读账号手工试一次写，
比如 `psql -h 10.0.0.12 -U doc2sop_ro cmdb -c 'create table t(x int)'`，应该报权限错误。
撤销：删掉配置里的工具和连接（即时生效），`/etc/ops-readonly.env` 里删掉密码，数据库里 `DROP ROLE doc2sop_ro`；不再用驱动就删掉 `/opt/ops/vendor` 再重启。

### 例：LiteLLM 网关的用量

[`deploy/templates/litellm-usage.sql`](../deploy/templates/litellm-usage.sql) 在 LiteLLM 自己的 Postgres 里建两个角色、schema `doc2sop`
和三个函数；[`litellm-usage.yaml`](../deploy/templates/litellm-usage.yaml) 是调它们的三个工具（`gateway_usage_by_model`、
`gateway_usage_by_key`、`gateway_recent_failures`，「模型网关」组）。函数只返回汇总：不含 key、请求和回答的正文，报错只给状态码和
错误类型。花费是 LiteLLM 按它的价格表估算的，没配价格的模型记为 0、不代表免费；两个用量工具的说明里写了这一点，回答花费问题时
模型会列出这些模型、说明实际花费不知道。用函数不用视图，是因为 LiteLLM 每次启动都跑 Prisma 迁移，视图会挡住它以后删列、改类型（详见 SQL 文件头）。
下面 A 是工具服务那台，B 是网关机；库在 B 的容器里，5432 没有发布到 B 的宿主机。

1. **B：建角色和函数。** 先查 LiteLLM 在用的库名（升级换过库的话不一定是 `POSTGRES_DB`），再以库的超级用户执行模板。
   `dbname` 必须和 `-d` 一致，对不上就什么都不改；等不到锁（5 秒）整个回滚，报出来就好，不要反复重试。可以重复执行：

   ```bash
   docker exec <LiteLLM 容器> sh -c 'echo "${DATABASE_URL##*/}"'        # 只打印库名，不打印密码
   docker exec -i <Postgres 容器> psql -X -v ON_ERROR_STOP=1 -v dbname=<库名> -U <超级用户> -d <库名> < litellm-usage.sql
   ```

2. **设密码，明文只在 A 上。** A 上生成密码写进 `/etc/ops-readonly.env`（先备份），只把 SCRAM-SHA-256 校验值交给 B：

   ```bash
   # A：追加 OPS_SECRET_LITELLM_DB_PASSWORD（不打印），只打印校验值（算法和 PostgreSQL 一样：PBKDF2-SHA256，4096 轮）
   python3 - <<'EOF'
   import base64, hashlib, hmac, os, secrets
   pw, salt = secrets.token_urlsafe(24), os.urandom(16)
   with open("/etc/ops-readonly.env", "a") as env:
       env.write(f"\nOPS_SECRET_LITELLM_DB_PASSWORD={pw}\n")
   salted = hashlib.pbkdf2_hmac("sha256", pw.encode(), salt, 4096)
   mac = lambda key: hmac.new(salted, key, hashlib.sha256).digest()
   b64 = lambda raw: base64.b64encode(raw).decode()
   print(f"SCRAM-SHA-256$4096:{b64(salt)}${b64(hashlib.sha256(mac(b'Client Key')).digest())}:{b64(mac(b'Server Key'))}")
   EOF
   # B：校验值经 stdin 交给 psql
   docker exec -i <Postgres 容器> psql -X -v ON_ERROR_STOP=1 -U <超级用户> -d <库名> <<'EOF'
   ALTER ROLE doc2sop_ro PASSWORD 'SCRAM-SHA-256$4096:…';
   EOF
   ```

3. **专用 SSH 隧道：A → B 上容器的 5432。** 不复用别的隧道，两头都用专用账号：
   - B：建一个只能转发的账号（nologin、没有密码；家目录、`.ssh`、`authorized_keys` 都归 root，同「接入一台主机」），公钥一行：
     `restrict,port-forwarding,permitopen="<容器 IP>:5432",permitlisten="127.0.0.1:1",from="<A 的出口 IP>",command="/bin/false" <公钥>`。
     只能转发到这一个地址；`permitlisten` 指向一个用不上的端口，等于不许反向转发；拿不到 shell。
     容器 IP：`docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}' <Postgres 容器>`。
   - A：建一个系统账号跑隧道，给它新生成一把 ed25519 密钥；`known_hosts` 只放核对过的 B 的 host key。systemd 单元的要点
     （目标地址放在 `/etc/default/<隧道服务>`：`PG_TARGET=<容器 IP>:5432`）：

     ```ini
     [Service]
     User=<隧道账号>
     EnvironmentFile=/etc/default/<隧道服务>
     ExecStart=/usr/bin/ssh -N -i <私钥> -o IdentitiesOnly=yes -o BatchMode=yes -o ExitOnForwardFailure=yes \
       -o StrictHostKeyChecking=yes -o UserKnownHostsFile=<known_hosts> -o ServerAliveInterval=30 \
       -L 127.0.0.1:15432:${PG_TARGET} <B 上的转发账号>@<B 的地址>
     Restart=always
     RestartSec=10
     ```

   连容器 IP，是因为把 5432 发布到宿主机要重建 Postgres 容器。**容器 IP 变了**（Postgres 容器重建、docker 重启之后可能变）：
   隧道照样连得上 B，但转发被 `permitopen` 拒绝，工具报「连不上数据库」。查出新 IP，改 B 上那一行的 `permitopen` 和 A 上的
   `PG_TARGET`，只重启这条隧道；LiteLLM 和别的隧道都不用动。

4. **工具服务。** 装 psycopg（见上面「接数据库」的第 2 步）；主配置按 yaml 文件头建连接 `litellm_db`，include 模板或把三个工具抄进主配置；
   `systemctl restart ops-readonly`。

核对：经隧道用 `doc2sop_ro` 连上去（A 上没有 psql 就用 vendor 里的 psycopg）试写（`create table t(x int)`）、直接读表
（`select count(*) from "LiteLLM_SpendLogs"`），都应该报权限错误；工具页里三个工具各试一次。

**LiteLLM 升级之后：**原地迁移不用管，迁移看不到这几个函数；迁移改了函数用到的列，工具会报「查询失败」，照新表结构改函数、
重新执行这份 SQL（函数返回的列变了，先 `DROP FUNCTION`）。**换了库**（新建一个库、迁移好再切过去）：角色是整个实例共用的，
还在；在新库里再执行一遍这份 SQL（`-v dbname=<新库> -d <新库>`），再把连接的 `database` 改成新库（即时生效）。

**撤销：**

```bash
# A：停掉并删除隧道；删掉主配置里的连接和三个工具、env 里的密码，重启工具服务
systemctl disable --now <隧道服务> && rm /etc/systemd/system/<隧道服务>.service /etc/default/<隧道服务> && systemctl daemon-reload
userdel <隧道账号> && rm -r <隧道账号的目录>
systemctl restart ops-readonly
# B：删转发账号（家目录归 root，userdel -r 不会删它）；在执行过 SQL 的每个库里删函数和授权，最后删角色
rm -r /home/<转发账号> && userdel <转发账号>
docker exec -i <Postgres 容器> psql -X -v ON_ERROR_STOP=1 -U <超级用户> -d <库名> <<'EOF'
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE usename = 'doc2sop_ro';
DROP SCHEMA doc2sop CASCADE;
DROP OWNED BY doc2sop_ro, doc2sop_definer;
DROP ROLE doc2sop_ro;
DROP ROLE doc2sop_definer;
EOF
```

## K8s 只读账号

工具服务查 K8s（kubectl 版的 `kube_*`，或 K8s API 模板）要用**只读的 ServiceAccount**，不用集群管理员的 kubeconfig：
凭据落在工具服务那台机器上，管理员证书一旦泄露就是整个集群。[`deploy/k8s-readonly.yaml`](../deploy/k8s-readonly.yaml) 是现成的 RBAC：

| 对象 | 作用 |
|---|---|
| 命名空间 `doc2sop`、ServiceAccount `ops-readonly` | 身份；`automountServiceAccountToken: false`，不挂进任何 Pod |
| ClusterRoleBinding → 内置的 `view` | 各命名空间里常见资源只读：Pod、Service、Ingress、EndpointSlice、事件、Pod 日志……**读不了 Secret**，也看不到 Role / RoleBinding |
| ClusterRole `doc2sop-ops-readonly-extra` | `view` 不含的集群级只读：节点、PV、StorageClass、IngressClass、CRD、Lease、Gateway API 各资源；Higress 的 WasmPlugin 只给 `list` |

WasmPlugin 只给 `list`：巡检 SOP 用 `kube_list`（`-o wide` 只出几列）看插件在不在、启没启用就够了；不给 `get`，`kube_yaml`、`kube_describe`
就读不到插件配置——那里面常有第三方服务的 key。集群里还有别的 CRD 要查，照样往 `extra` 里加；里面有凭据的资源只给 `list` 或干脆不给。

```bash
kubectl apply -f /opt/doc2sop/deploy/k8s-readonly.yaml          # 用管理员身份，在能管集群的机器上
kubectl auth can-i get secrets -A --as=system:serviceaccount:doc2sop:ops-readonly    # no
kubectl auth can-i list pods -A --as=system:serviceaccount:doc2sop:ops-readonly      # yes
```

**kubectl 版**（`deploy/ops_tools.yaml` 里的 `kube_*`）：签一个令牌，写一份只含它的 kubeconfig，`KUBECONFIG` 指过去：

```bash
umask 077
SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
CA=$(kubectl config view --minify --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}')
TOKEN=$(kubectl -n doc2sop create token ops-readonly --duration=2160h)       # 90 天
cat > /etc/ops-readonly/kubeconfig-readonly <<EOF
apiVersion: v1
kind: Config
clusters: [{name: cluster, cluster: {server: $SERVER, certificate-authority-data: $CA}}]
users: [{name: ops-readonly, user: {token: $TOKEN}}]
contexts: [{name: ops-readonly, context: {cluster: cluster, user: ops-readonly}}]
current-context: ops-readonly
EOF
unset TOKEN
cp -a /etc/ops-readonly.env /etc/ops-readonly.env.bak-$(date +%Y%m%d%H%M%S)
sed -i 's#^KUBECONFIG=.*#KUBECONFIG=/etc/ops-readonly/kubeconfig-readonly#' /etc/ops-readonly.env    # 没有这一行就追加
systemctl restart ops-readonly
```

管理员的 kubeconfig 不要留在工具服务读得到的地方（`/etc/ops-readonly/` 下原来那份移走）。

**API 模板**（[`deploy/templates/k8s-api.yaml`](../deploy/templates/k8s-api.yaml)）不需要 kubectl：令牌和 CA 各放一个文件，连接里用 `bearer_file`、`ca`：

```bash
umask 077
kubectl -n doc2sop create token ops-readonly --duration=2160h > /etc/ops-readonly/k8s-token
kubectl config view --minify --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d > /etc/ops-readonly/k8s-ca.pem
```

```yaml
connections:
  - {name: k8s, type: http, base: "https://127.0.0.1:6443", ca: /etc/ops-readonly/k8s-ca.pem, bearer_file: /etc/ops-readonly/k8s-token}
include: [/opt/doc2sop/deploy/templates/k8s-api.yaml]
```

- **续期**：令牌 90 天过期（`--duration` 还受 apiserver 的 `--service-account-max-token-expiration` 限制）。到期前重新签一个换上：
  kubectl 每次调用都现读 kubeconfig，`bearer_file` 也是每次现读，所以两种都只要在 `umask 077` 下写个临时文件再 `mv` 盖过去，不用重启。
  过期了 K8s 工具报 `Unauthorized`，别的工具不受影响。看还剩多久：令牌是 JWT，第二段 base64 解码后的 `exp`。
- **撤销**：`kubectl delete -f /opt/doc2sop/deploy/k8s-readonly.yaml`——ServiceAccount 一删，它签出的令牌立即失效。
- **退回**原来的 kubeconfig：把 `/etc/ops-readonly.env` 换回改之前的备份，`systemctl restart ops-readonly`。

## 和演示形态并存

同一台机器上可以再跑一套 compose 演示站（比如给人看最新 main）：在另一个目录 clone，那份 `.env` 里设
`APP_CONTAINER=demo-app OPS_CONTAINER=demo-ops APP_IMAGE=demo-app:latest OPS_IMAGE=demo-ops:latest APP_PORT=8766 APP_MEM_LIMIT=700m`
（演示主机还可以设 `HOST_CONTAINER=demo-host HOST_IMAGE=demo-host:latest`），
`LLM_BASE_URL` 指向宿主机上的网关时写 `http://host.docker.internal:14000/v1`（compose 里两个服务都带了 `host.docker.internal`），然后 `docker compose --profile demo up -d --build`。
容器名、镜像名、网络、卷互不干扰；正式站继续由 `release.sh` 管。演示主机（kb-host）只跑在演示站的 compose 网络里，不发布端口，碰不到正式站。

## 常见问题

| 现象 | 处理 |
|---|---|
| 第一次发版很慢 | 在构建 `kb-app:base-<哈希>`，2 核机器约 10 分钟；只发生在首次和 `requirements.txt` / base 阶段变化时。构建在切换之前，服务不中断 |
| `docker build` 拉不到 `python:3.12-slim` | 设 `BASE_IMAGE=docker.m.daocloud.io/library/python:3.12-slim`（本地已有该镜像则不会去拉） |
| pip 卡住 | 设 `PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple`；换源会改变哈希，重建一次 base |
| 脚本说「片段总数不一致」并回滚了 | 新版本启动后向量库读不到或读到的和之前不一样——看它打印的新容器日志；常见原因是 `DATA_DIR` 指错、`.env` 里换了 `EMBED_MODEL`（换向量模型会触发重建索引） |
| 脚本说已存在 `kb-app-prev` | 上次发版中途被打断。当前 `kb-app` 正常就 `docker rm -f kb-app-prev`；想回到旧的就 `docker rm -f kb-app && docker rename kb-app-prev kb-app && docker start kb-app` |
| 想看生产跑的是哪个提交 | `docker inspect kb-app --format '{{index .Config.Labels "doc2sop.commit"}}'` |
| 沙箱服务起不来 | `journalctl -u doc2sop-sandbox -n 20`：「没有注册 runsc」是第 1 步没做完或 reload 没生效；「本机没有镜像」就按第 2 步构建 |
| 模型说「计算沙箱不可用：沙箱正忙」 | 同时有别的执行在跑、排队也没轮到；偶发正常，经常出现再考虑 `SANDBOX_CONCURRENCY=2`（内存够的话） |
