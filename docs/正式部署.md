# 正式部署：宿主机 host 网络 + `deploy/release.sh`

一键演示（`docker compose up`）是给陌生人五分钟跑通用的单机形态。正式用时推荐这份文档的形态：
应用容器跑在 **host 网络**，工具服务 `deploy/ops_readonly.py` 以 systemd 跑在宿主机上、只监听 `127.0.0.1`，
模型网关（LiteLLM）或到网关的 SSH 隧道同样只绑 `127.0.0.1`——容器用 host 网络才能直接访问它们，所以这条路径**不走 compose**，
用 `deploy/release.sh` 构建、切换、校验、回滚。

| | 一键演示（compose） | 正式部署（本文） |
|---|---|---|
| 网络 | bridge；应用发布到 `127.0.0.1:APP_PORT`，工具是 sidecar 容器 | host；应用监听 `PORT`（默认 8765），工具和网关都在宿主机 `127.0.0.1` 上 |
| 构建 | `docker compose up --build`，依赖每次走构建缓存 | 依赖预烘焙成 `kb-app:base-<哈希>`，发版只 COPY 代码，几秒钟 |
| 切换 | compose 重建容器 | 停旧 → 起新 → 等就绪 → **比对片段总数** → 不一致自动回滚 |
| 工具 | 来自场景包，`OPS_URL=http://kb-ops:8799` | 宿主机 `ops_readonly.py`，`OPS_URL=http://127.0.0.1:8799`，`include` 场景包的 tools.yaml |
| 配置文件 | 仓库目录里的 `.env` | 任意位置，例如 `/opt/kb-app/.env`，用 `ENV_FILE=` 指给脚本 |

两种形态跑的是同一份代码和同一个 `Dockerfile`（compose 构建它的末尾 `app` 阶段，发版脚本单独用 `base` 阶段）。

## 宿主机布局（推荐）

```
/opt/doc2sop/                 代码：git clone，升级就是 git pull；脚本、文档、场景包都在这里
/opt/kb-app/.env              应用配置（含密钥，0600）；容器的 --env-file
/opt/kb-app/data/             知识库数据：向量库、SQLite、原件；挂到容器 /data
/opt/kb-app/backups/          每日备份包（deploy/backup.sh）
/opt/ops/ops_readonly.py      工具服务（deploy/ 下同名文件的拷贝）
/opt/ops/ops_exec.py          执行核心（deploy/ 下同名文件的拷贝），必须和 ops_readonly.py 放在同一个目录
/opt/ops/ops_tools.yaml       工具定义的唯一真相源；旁路文件 overrides / pending / trust / mcp / known_hosts 在同目录
/opt/ops/ops_tools.page.*     页面「主机与数据源」上加的连接、远程 MCP server、对外开放、主机（page.yaml），它们的 host key（page.known_hosts）、
                              配置变更记录（page.log）；page-bundles/ 是页面上加的主机的安装包。都由工具服务写（0644）
/opt/ops/mcp/                 可选：MCP server（如 holiday_mcp.py）
/opt/ops/vendor/              可选：数据库驱动（pip install --target），属 root、组和其他用户不可写，见下文「接数据库」
/etc/ops-readonly.env         工具服务的环境：OPS_TOKEN、OPS_SECRET_*、KUBECONFIG、OPS_PAGE_CONFIG（0600）
/etc/ops-readonly/            审批口令的哈希；页面上输入的凭据（page-secrets.json）和页面上加的主机的私钥（page-hosts/）；可选：连远程主机的私钥、
                              K8s 只读账号的 kubeconfig / 令牌 / CA（0600，属工具服务的运行账号；ProtectHome=yes 时不能放 /root）
/opt/doc2sop-sandbox/         可选：计算沙箱服务（deploy/sandbox/ 下同名文件的拷贝），见下文「计算沙箱」
/etc/doc2sop-sandbox.env      沙箱服务的令牌 SANDBOX_TOKEN（0600）
```

目录名随意，脚本全部参数化；下面的命令按这个布局写。

## 首次安装

```bash
git clone https://github.com/wangyd1988/doc2sop.git /opt/doc2sop
mkdir -p /opt/kb-app/data && cp /opt/doc2sop/.env.example /opt/kb-app/.env && chmod 600 /opt/kb-app/.env
# 编辑 /opt/kb-app/.env：WEB_PASSWORD、模型地址与 key；COMPOSE_PROFILES 留空；
# OPS_URL=http://127.0.0.1:8799、OPS_TOKEN 与下面 /etc/ops-readonly.env 里的一致。文件保持 LF、无 BOM。
```

工具服务（systemd，模板见 [`deploy/ops-readonly.service.example`](../deploy/ops-readonly.service.example)）：

```bash
mkdir -p /opt/ops && cp /opt/doc2sop/deploy/ops_readonly.py /opt/doc2sop/deploy/ops_exec.py /opt/doc2sop/deploy/ops_tools.yaml /opt/ops/
install -d -m 700 /etc/ops-readonly      # 审批口令的哈希放这里；页面上设口令时工具服务要写它（单元文件的 ReadWritePaths 里有它）
printf 'OPS_TOKEN=%s\n' "$(openssl rand -hex 24)" > /etc/ops-readonly.env && chmod 600 /etc/ops-readonly.env
# 需要「模型网关」组工具就再加 OPS_SECRET_GATEWAY_URL / OPS_SECRET_GATEWAY_KEY；K8s 工具加 KUBECONFIG（用只读账号，见下文「K8s 只读账号」）
cp /opt/doc2sop/deploy/ops-readonly.service.example /etc/systemd/system/ops-readonly.service   # 核对 ExecStart 和 ReadWritePaths 里的路径
systemctl daemon-reload && systemctl enable --now ops-readonly
curl -s -H "X-Ops-Token: $(sed -n 's/^OPS_TOKEN=//p' /etc/ops-readonly.env)" http://127.0.0.1:8799/health
```

要用场景包的工具，在 `/opt/ops/ops_tools.yaml` 顶层加一行 `include: [/opt/doc2sop/packs/leave-planning/tools.yaml]`，改完即时生效。

页面上批准工具要另输的**审批口令**，**部署好之后马上设**：打开页面「设置 → 审批口令」，新口令输两遍（工作台「待处理」里也有一项
「还没设审批口令」）。设好之前，拿到网页密码的人能抢先设——设好后看一眼卡片上的设置时间和来源是不是你。也可以在宿主机上设，
见下文「页面审批：审批口令」：

```bash
python3 /opt/ops/ops_readonly.py set-approval-passphrase      # root；交互输入两次，不回显，至少 12 个字符
```

发版（第一次会先构建依赖镜像，2 核机器约 10 分钟；之后每次只 COPY 代码）：

```bash
cd /opt/doc2sop
ENV_FILE=/opt/kb-app/.env DATA_DIR=/opt/kb-app/data bash deploy/release.sh
```

国内网络：Docker Hub 不通就 `BASE_IMAGE=docker.m.daocloud.io/library/python:3.12-slim`，PyPI 慢就
`PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple`——两者都可以写进 `/opt/kb-app/.env`（脚本会读），也可以当环境变量传。

脚本结束会打印运行中的镜像、切换前后片段数和回滚命令。核对：

```bash
docker ps --filter name=kb-app --format '{{.Names}} {{.Image}} {{.Status}}'
curl -s -u admin:'密码' http://127.0.0.1:8765/api/tools | head -c 300     # 列出宿主机工具
```

## 脚本参数

`bash deploy/release.sh --help` 有全文。要点：

| 变量 / 选项 | 含义 | 默认 |
|---|---|---|
| `ENV_FILE` | 容器的 `--env-file`，也从这里读 `PORT`、`WEB_USER`、`WEB_PASSWORD` 和下面的 `APP_*` | `<仓库>/.env` |
| `DATA_DIR` | 挂到容器 `/data` | `<仓库>/data` |
| `APP_CONTAINER` | 容器名；container-guard、监控引用的就是它 | `kb-app` |
| `APP_IMAGE` | 镜像名；冒号前作为仓库名，时间戳 tag 与 `base-<哈希>` 都打在它上 | `kb-app:latest` |
| `APP_MEM_LIMIT` / `APP_CPUS` | `--memory` / `--cpus` | `900m` / `1.5` |
| `APP_PORT` | 探活端口；host 网络下等于 `.env` 的 `PORT` | `.env` 的 `PORT`，再默认 8765 |
| `BASE_IMAGE` / `PIP_INDEX_URL` | 构建依赖镜像用的基础镜像 / pip 源 | `python:3.12-slim` / 官方源 |
| `KEEP_IMAGES` / `START_TIMEOUT` | 保留几个时间戳镜像 / 等新容器就绪多少秒 | `2` / `120` |
| `TLS_DIR` | 内置 TLS 的证书目录，只读挂到容器的 `/tls`（见「HTTPS 与对外放开」）；切换前用新镜像跑 `app.serve --check` 预检 | 不挂 |
| `--image kb-app:<tag>` | 不构建，直接切到一个已有镜像（回滚） | |
| `--rebuild-base` | 强制重建依赖镜像 | |
| `--backup` | 切换前先跑 `deploy/backup.sh`（备份目录 `BACKUP_DIR`，默认 `<DATA_DIR 上级>/backups`） | |
| `--print-config` | 只打印解析后的配置，不碰 docker | |

优先级：环境变量 > `ENV_FILE` 里的同名键 > 默认值。密钥只从环境文件读进内存，探活用的 Basic 凭据经 curl 的 stdin 配置传入，不进命令行，也不打印。
默认值适合「在仓库 clone 目录里直接跑」：`bash deploy/release.sh` 就用 `./.env` 和 `./data`。在仓库任意路径下调用都行，脚本按自己的位置找仓库根。

## 升级

```bash
cd /opt/doc2sop && git pull && ENV_FILE=/opt/kb-app/.env DATA_DIR=/opt/kb-app/data bash deploy/release.sh
```

把 `ENV_FILE`、`DATA_DIR` 写进 `/opt/kb-app/.env`？不行——它们决定去哪儿找这个文件；但 `APP_*`、`BASE_IMAGE`、`PIP_INDEX_URL` 可以写在里面，命令就短成 `ENV_FILE=/opt/kb-app/.env DATA_DIR=/opt/kb-app/data bash deploy/release.sh`。

脚本做的事和失败时的行为：

1. `requirements.txt`、`Dockerfile` 的 base 阶段、`BASE_IMAGE`、`PIP_INDEX_URL` 一起算哈希；`kb-app:base-<哈希>` 不存在才 `docker build --target base`。
2. 用 [`deploy/Dockerfile.release`](../deploy/Dockerfile.release) 在 base 上只 COPY `app/` `packs/`，打 `kb-app:<yyyymmddHHMMSS>`，带 `doc2sop.commit` 标签（`docker inspect` 能看到跑的是哪个提交）。
3. 记下当前片段总数（`/api/documents`）→ `docker stop -t 60` → 改名为 `kb-app-prev` → `docker run -d --network host --env-file … -v DATA_DIR:/data --memory --cpus`。
4. 等 `/api/documents` 返回 200（最多 `START_TIMEOUT` 秒）→ 再读片段总数 → **和切换前不一致、起不来或超时：打印新容器最后 40 行日志，删掉它，把 `kb-app-prev` 改回 `kb-app` 并启动**，退出码 1。
5. 成功：删 `kb-app-prev`，只保留最近 `KEEP_IMAGES` 个时间戳镜像和当前 base，打印回滚命令。

中断约 30–60 秒（停旧容器 + 新容器加载向量库）。如果发现 `kb-app-prev` 残留（上次发版中途被杀），脚本会拒绝开始并给出两条收尾命令。

ops 服务不在镜像里，升级它要单独做（改了 `deploy/ops_readonly.py` 或 `deploy/ops_exec.py` 才需要）。两个文件一起换、一起备份——
`ops_readonly.py` 启动时加载同目录的 `ops_exec.py`，缺了它服务起不来：

```bash
STAMP=$(date +%Y%m%d%H%M%S)
for f in ops_readonly.py ops_exec.py; do
  cmp -s /opt/doc2sop/deploy/$f /opt/ops/$f && continue
  [ -f /opt/ops/$f ] && cp -a /opt/ops/$f /opt/ops/$f.bak-$STAMP
  cp /opt/doc2sop/deploy/$f /opt/ops/ && CHANGED=1
done
[ -n "${CHANGED:-}" ] && systemctl restart ops-readonly && sleep 2 && \
  curl -s -H "X-Ops-Token: $(sed -n 's/^OPS_TOKEN=//p' /etc/ops-readonly.env)" http://127.0.0.1:8799/health
```

`/health` 返回的工具数应与升级前一致；`/opt/ops/ops_tools.yaml` 是你的配置，升级不会动它。回滚：把 `.bak-$STAMP` 两个文件拷回去再重启。
接入了远程主机（受控模式）时，`ops_exec.py` 有改动还要 `ops_readonly.py push` 一遍，主机上的执行器跟着换。
页面审批要新版工具服务：应用已经升级、工具服务还是旧的时，「待审批」里能看、能拒绝，批准按钮不可用并写明「工具服务版本较旧」。
「主机与数据源」也一样：工具服务是旧的时页面照旧只读，写明「工具服务版本较旧」。**升级到能在页面上配置主机与数据源的版本以后，
设了审批口令的部署马上就能在页面上加连接、主机**；不想要，在 `/etc/ops-readonly.env` 里加一行 `OPS_PAGE_CONFIG=off` 再重启
（见下文「页面上配置主机与数据源」）。

**场景包和工具服务要一起升级。** 场景包的 `tools.yaml` 会用到工具服务新支持的写法（比如 `impl: {type: builtin}`）。
如果 `/opt/ops/ops_tools.yaml` 直接 include 了 `/opt/doc2sop/packs/...`，`git pull` 之后旧版工具服务会热加载到新写法的条目，
把它们当坏条目跳过（日志里有原因），直到按上面的命令换上新的 `ops_readonly.py`。所以 `git pull` 之后紧接着升级工具服务。

## 备份

[`deploy/backup.sh`](../deploy/backup.sh)：SQLite（会话、SOP、图谱（含执行记录、定时计划、告警规则）、Agent 记忆、对外接入的令牌与审计）在线一致性复制 + 向量库 + 原件 + 页面上填的自动执行设置 `automation.page.json`（不含密钥）+ `/opt/ops/ops_tools*.yaml`（含页面上加的 `ops_tools.page.yaml`）、两份 known_hosts、页面配置变更记录 `ops_tools.page.log`、云上协同、钉钉的 `chat.yaml` 和转接程序的 `targets.yaml` 打成一个 tgz，保留最近 7 份。
自动执行的授权码和告警令牌（`automation.page-secrets.json`、手写的 `automation.yaml`）不进备份包，见下面「自动执行」；页面上输入的凭据
（`/etc/ops-readonly/page-secrets.json`）和页面上加的主机的私钥（`/etc/ops-readonly/page-hosts/`）也不进，见下面「页面上配置主机与数据源」。

```bash
echo '30 3 * * * root KB_DATA=/opt/kb-app/data bash /opt/doc2sop/deploy/backup.sh /opt/kb-app/backups >> /var/log/kb-backup.log 2>&1' > /etc/cron.d/kb-backup
KB_DATA=/opt/kb-app/data bash /opt/doc2sop/deploy/backup.sh /opt/kb-app/backups      # 手动跑一次确认产出
```

恢复：`docker stop kb-app` → 把包里的 `data/` 解到 `/opt/kb-app/data`（`ops/` 下的工具配置按需放回 `/opt/ops`）→ `docker start kb-app`。

## 内存看护（可选）

2 GB 的机器上应用容器长时间运行后内存会缓慢爬升。[`deploy/container-guard.sh`](../deploy/container-guard.sh) 只在用量超过阈值时重启容器，配一个 systemd timer 每天凌晨跑一次：

```ini
# /etc/systemd/system/container-guard.service
[Unit]
Description=Restart kb-app when its memory creeps up
After=docker.service
Requires=docker.service
[Service]
Type=oneshot
ExecStart=/opt/doc2sop/deploy/container-guard.sh kb-app 600

# /etc/systemd/system/container-guard.timer
[Unit]
Description=Daily memory check for kb-app
[Timer]
OnCalendar=*-*-* 04:50:00
Persistent=true
RandomizedDelaySec=120
[Install]
WantedBy=timers.target
```

`systemctl enable --now container-guard.timer`。它引用的是容器名，所以发版脚本的 `APP_CONTAINER` 要和这里一致。

## 智能模式（页面上的第二个回答模式）

页面输入框上方有「知识库模式」「智能模式」两个 tab（区别见 [`工具.md` 的「知识库模式与智能模式」](工具.md#知识库模式与智能模式)）。
智能模式默认关，关着时页面上那个 tab 灰着并写明原因，问答和以前完全一样。它要 `KB_TOOLS=true`、`AGENT_MODE` 不是 `off`。

```bash
# 打开：先备份 .env（文件名带时间戳），再加一行、照常发版（带上 KEEP_IMAGES、PIP_INDEX_URL）
cp -a /opt/kb-app/.env /opt/kb-app/.env.bak-$(date +%Y%m%d%H%M%S)
grep -q '^KB_TOOLS=true' /opt/kb-app/.env || echo '没开 KB_TOOLS：智能模式要它'
echo 'SMART_MODE=true' >> /opt/kb-app/.env
# 验证：/api/documents 的 smart_mode 是 {"available": true, ...}
# 关掉：删掉这一行（或改成 false），再 release.sh --image <当前镜像>。已有对话里智能模式的回答照常回放，标记还在
```

演示站在 `/root/doc2sop-demo/.env` 里加同样的行（同样先备份），再 `docker compose --profile demo up -d`。

## HTTPS 与对外放开

什么都不配时，应用在 `0.0.0.0:PORT` 上跑明文 HTTP：网页密码（Basic）、审批口令、对外接入的令牌和返回内容都以明文经过网络。
所以默认只适合本机、经 SSH 隧道或可信内网使用，对外接入也建议先只放给本机（`MCP_CLIENTS=127.0.0.1,::1`）。
**要给别人从公网（或不可信的内网）直连，先上 HTTPS，再放开来源，令牌照样要。** 下面三种方式选一种，最后是「放开 MCP_CLIENTS」。

### 相关设置

| 设置 | 在哪 | 作用 |
|---|---|---|
| `TLS_CERT_FILE` / `TLS_KEY_FILE` | `.env` | 内置 TLS：两个都填，`PORT` 就说 HTTPS。填的是**容器里**的路径（正式部署是 `/tls/server.crt`、`/tls/server.key`）。证书文件可以带中间证书链（fullchain）。证书私钥不配对、读不了、**私钥对别的账号可读**时拒绝启动；过期、快到期（不到 30 天）只告警。**换证书要重启**（`docker restart kb-app`）。TLS 1.2 起。 |
| `TLS_DIR` | `.env` 或 `release.sh` 的环境变量 | 宿主机上放服务器证书和私钥的目录，`release.sh` 把它只读挂到容器的 `/tls`。目录 root 700，私钥 600。**CA 的私钥、acme.sh 的密钥不要放这里**，也不要放进 `DATA_DIR`（会进备份包）。 |
| `LOCAL_HTTP_PORT` | `.env` | 开了 TLS 时，另在 `127.0.0.1` 上留一个明文端口，给 SSH 隧道、本机探活和脚本用。明文端口只能在回环地址上，这一点不能配。同一个进程，定时任务只跑一份。 |
| `LISTEN_HOST` | `.env` | `PORT` 监听的地址：`0.0.0.0`（默认）或 `127.0.0.1`（应用只给本机的反向代理用）。 |
| `TRUSTED_PROXIES` | `.env` | 反向代理自己的地址（IP 或网段，逗号分隔，默认空）。只有从这些地址来的请求才认 `X-Forwarded-For`、`X-Forwarded-Proto`。不能写 `*`、`0.0.0.0/0`。**只登记代理自己的地址（最好是单个 IP），不要写成大网段**：`X-Forwarded-For` 里全是可信地址时取最左一项，网段写得太宽（比如整个 `10.0.0.0/8`），内网里的人直连应用、自己带一个 `X-Forwarded-For` 就能伪造来源。 |
| `FORWARDED_ALLOW_IPS` | — | 不再起作用：应用关掉了 uvicorn 自己的转发头处理。设了会**拒绝启动**，提示改用 `TRUSTED_PROXIES`。 |

`release.sh` 在**停旧容器之前**先用新镜像跑一遍 `python -m app.serve --check`（证书、私钥权限、`TRUSTED_PROXIES`、`FORWARDED_ALLOW_IPS`……），
不通过就退出，服务不中断。探活地址跟着环境文件走：有 `LOCAL_HTTP_PORT` 就连 `http://127.0.0.1:它`；只开了 TLS 就连
`https://127.0.0.1:PORT`（`curl -k`：只连回环，没有中间人可防，而公司证书一般不含 127.0.0.1）；都没配和以前一样。
回滚到不认这些设置的老镜像之前，先把环境文件里的 `TLS_*`、`LOCAL_HTTP_PORT`、`LISTEN_HOST`、`TRUSTED_PROXIES` 去掉（先备份）——
`release.sh --image` 发现老镜像没有启动器又配了这些，会直接退出、不切换。

### 来源地址：「只收本机」、MCP_CLIENTS、告警来源怎么算

应用用来源地址做好几件事：用密码安装主机、用账号密码添加机器只收本机来的请求（经 SSH 隧道）；`MCP_CLIENTS`、告警入口的来源名单；
按地址限频；审批记录里的「来自 …」。来源地址由 `app/peer.py` 统一算：

- **直连**（包括内置 TLS）：就是 TCP 对端。内置 TLS 不加任何中间层，这几道防线和以前完全一样。
- **经 `TRUSTED_PROXIES` 里的代理**：取它传来的 `X-Forwarded-For` 里从右往左第一个不是可信代理的地址；协议看 `X-Forwarded-Proto`。
  客户端自己伪造的那一段（左边）不算数。代理没带 `X-Forwarded-For` 的（本机对端、Host 是本机地址的除外，那是隧道）按来源不明处理。
- **经没登记的代理**：对端是本机（127.0.0.1、::1），却带着转发头，或者 Host 不是 `127.0.0.1`、`::1`、`localhost`——这多半是本机的反向代理
  忘了登记，或者 realm、stunnel 这类 TCP 转发把公网连接接到了应用端口。这种请求的来源一律记成 `untrusted-proxy`（不是 IP）：
  「只收本机」、`MCP_CLIENTS`、告警来源名单都不放行，日志里每分钟一行警告，「对外接入」页和「用账号密码添加机器」对话框里标红。
  靠 Host 识别只是发现配错，不是防线（Host 是客户端写的）：**不要用 TCP 转发把公网连接接到应用端口**，要转发就用 HTTP 反向代理并登记。
- 对端不是本机、也不在名单里，却带着转发头（客户端经公司的正向代理出网时很常见）：转发头不算数，照常用对端地址；
  对端是私网地址时页面上给一条提示（它要是你的反向代理，就登记进 `TRUSTED_PROXIES`）。

经 SSH 隧道（`ssh -L` 后开 `http://127.0.0.1:端口` 或 `http://localhost:端口`）、`release.sh` 的探活、在宿主机上 `curl 127.0.0.1:端口`
都还算本机，登记了本机的代理以后也一样。

### 方式甲：有域名

**国内服务器先看备案。** 域名解析到国内云服务器、用 80 / 443 提供网站，要有 ICP 备案，而且要在**服务器所在的云厂商**做接入备案
（域名在阿里云备过案、服务器在京东云，也要在京东云做接入）；没做的，云厂商会拦截 80 / 443 上这个域名的访问。
非标准端口（如 9443）一般不在拦截范围内，但以云厂商的规定为准。证书怎么签和备案无关：用下面的 DNS-01 不需要 80 / 443。

#### 甲一：acme.sh 走 DNS-01 + 内置 TLS（国内常见，不用 80 / 443）

Let's Encrypt 的免费证书 90 天一换。DNS-01 是让 acme.sh 调 DNS 服务商的接口加一条 TXT 记录来证明域名归你，不需要对外开 80 / 443。
下面以阿里云解析（`dns_ali`）为例，别的 DNS 服务商换成 acme.sh 对应的插件。

1. **建一个只能改解析的 RAM 子账号**（阿里云控制台 → RAM 访问控制）：用户只勾「OpenAPI 调用访问」，生成 AccessKey；
   给它授权一条自定义策略，只允许改这个域名的解析记录（`<主账号 ID>` 在控制台右上角头像里看）：

   ```json
   {"Version": "1", "Statement": [{"Effect": "Allow",
     "Action": ["alidns:AddDomainRecord", "alidns:DeleteDomainRecord", "alidns:DescribeDomainRecords"],
     "Resource": "acs:alidns:*:<主账号 ID>:domain/doc2sop.autos"}]}
   ```

   按域名限定在你的账号上不生效时，`Resource` 退回 `"*"`（仍然只有这三个动作），别直接给 `AliyunDNSFullAccess`。

2. **装 acme.sh**（root）。服务器访问不了 GitHub 时：
   - 首选：在自己能访问 GitHub 的电脑上取一个发布版本，拷到服务器：
     ```bash
     git clone --depth 1 --branch 3.1.6 https://github.com/acmesh-official/acme.sh.git   # 版本号以 GitHub 的 Releases 为准
     git -C acme.sh rev-parse HEAD     # 和 git ls-remote https://github.com/acmesh-official/acme.sh.git 'refs/tags/3.1.6^{}' 对得上
     tar czf acme.sh.tgz acme.sh && scp acme.sh.tgz root@服务器:/root/
     ```
   - 备选：国内镜像 `https://gitee.com/neilpang/acme.sh.git`（acme.sh 作者维护，版本可能落后几个），clone 某个标签以后，
     **在能访问 GitHub 的机器上核对同一个标签的提交哈希**（`git ls-remote` 两边对比），对不上就不要用。
   - 不要 `curl … | sh` 装来路不明的脚本。

   ```bash
   cd /root && tar xzf acme.sh.tgz && cd acme.sh
   ./acme.sh --install --home /root/.acme.sh --accountemail 你的邮箱     # 会加一条每天跑的 crontab
   /root/.acme.sh/acme.sh --set-default-ca --server letsencrypt
   ```

3. **AccessKey 只在服务器上填**，不进仓库、不进备份、不贴到聊天里。用 `read -s` 输入（不进 shell 历史）：

   ```bash
   read -rs -p 'Ali_Key: ' Ali_Key; echo; read -rs -p 'Ali_Secret: ' Ali_Secret; echo; export Ali_Key Ali_Secret
   /root/.acme.sh/acme.sh --issue --dns dns_ali -d doc2sop.autos --keylength ec-256
   unset Ali_Key Ali_Secret
   chmod 600 /root/.acme.sh/account.conf && ls -l /root/.acme.sh/account.conf    # acme.sh 把 AccessKey 存在这里，续期要用
   ```

   `/root/.acme.sh` 在 `DATA_DIR` 之外，`deploy/backup.sh` 不备份它。AccessKey 泄露了就在 RAM 里禁用、换一个。

4. **装到 TLS_DIR，续期后自动重启应用**：

   ```bash
   install -d -m 700 /opt/kb-app/tls
   /root/.acme.sh/acme.sh --install-cert -d doc2sop.autos --ecc \
     --key-file /opt/kb-app/tls/server.key --fullchain-file /opt/kb-app/tls/server.crt \
     --reloadcmd 'chmod 600 /opt/kb-app/tls/server.key && docker exec kb-app python -m app.serve --check && docker restart kb-app'
   ls -l /opt/kb-app/tls     # server.key 必须是 600，否则应用拒绝启动
   ```

   `--reloadcmd` 记在 acme.sh 的配置里，以后每次续期（到期前 30 天，crontab 每天检查）都会执行：先在运行中的容器里检查新证书
   （`/tls` 是挂载的，容器里看到的就是新文件），过了才重启；没过就不重启，旧证书照常用到过期，acme.sh 的日志里有 reload 失败。
   `docker restart` 只重启同一个镜像，几秒钟。第一次装时应用还没配 TLS，检查和重启都无害。想核对续期流程：
   `/root/.acme.sh/acme.sh --renew -d doc2sop.autos --ecc --force`（Let's Encrypt 对同一域名每周有签发次数限制，别反复试）。

5. **配应用**：环境文件（先备份）里加

   ```bash
   TLS_CERT_FILE=/tls/server.crt
   TLS_KEY_FILE=/tls/server.key
   TLS_DIR=/opt/kb-app/tls
   ```

   再照常发版。验证：`curl -sI https://doc2sop.autos:端口/ | head -1` 是 `401`（证书是公共 CA 签的，客户端不用导入什么）。

#### 甲二：反向代理（Caddy 或 nginx）

已经有 nginx、负载均衡，或者想让代理自动续证书（Caddy 用 HTTP-01 时要 80 端口能从公网访问），就让代理做 TLS：

- 应用设 `LISTEN_HOST=127.0.0.1`（应用端口不再对外，别人绕不过代理直连明文端口）；代理和应用在同一台机器时 `TRUSTED_PROXIES=127.0.0.1,::1`。
- 代理**必须**传 `X-Forwarded-For`、`X-Forwarded-Proto`，并原样转发 `Host`（防跨站检查比对它）。没登记、或者不传 `X-Forwarded-For` 的，
  应用把它转来的请求当成来源不明（见上面「来源地址」），对外接入页标红。
- `/mcp` 用 SSE 推流：关掉代理的缓冲、放长读超时。

```nginx
limit_req_zone $binary_remote_addr zone=mcp:10m rate=5r/s;
server {
    listen 443 ssl;
    server_name kb.example.com;
    ssl_certificate     /etc/ssl/kb.example.com.fullchain.pem;
    ssl_certificate_key /etc/ssl/kb.example.com.key;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    location /mcp {
        limit_req zone=mcp burst=20 nodelay;
        proxy_pass http://127.0.0.1:8765;
        proxy_http_version 1.1;
        proxy_buffering off;              # SSE：事件要立刻推给客户端
        proxy_read_timeout 3600s;         # 2025 版客户端的通知流是长连接
    }
    location / { proxy_pass http://127.0.0.1:8765; }
}
```

```caddyfile
kb.example.com {
    reverse_proxy 127.0.0.1:8765 {
        flush_interval -1                 # SSE
    }
}
```

Caddy 默认就传 `X-Forwarded-For`、`X-Forwarded-Proto` 和原样的 Host，并自动申请、续期证书。多级代理（负载均衡 → nginx → 应用）时，
**每一跳**的地址都写进 `TRUSTED_PROXIES`——只写这几台代理自己的地址，不要图省事写整个内网网段（理由见上面「相关设置」）。

### 方式乙：公司自己的 CA

- **内置 TLS**：拿公司 CA 签的服务器证书（带中间证书的 fullchain）和私钥放进 `TLS_DIR`，同甲一第 5 步。证书一般一年一换，换完 `docker restart kb-app`；
  对外接入页和启动日志显示到期日，不到 30 天标黄。员工电脑上一般已经信任公司 CA，什么都不用导入。
- **前面已有 nginx / 负载均衡**：同甲二，把每一跳登记进 `TRUSTED_PROXIES`、应用 `LISTEN_HOST=127.0.0.1`（或用防火墙只让代理连应用端口）。

### 方式丙：没有域名（私有 CA + 带 IP 的证书）

没有域名就拿不到公共 CA 的证书。**不要用「客户端跳过证书校验」凑合**——那样谁都能冒充服务器，拿走网页密码和令牌。
做法是自己当一个小 CA：生成一个私有 CA，用它签服务器证书，使用的人只导入 CA 证书。

```bash
# 在服务器上（root；要 openssl 和 python3）。CA 目录和 TLS_DIR 分开放，CA 私钥不进容器、不进备份
bash deploy/make-tls-certs.sh --ca-dir /root/doc2sop-ca --out /opt/kb-app/tls --ip 服务器公网IP
# 有内网地址、内网名字也一起给：--ip 10.0.0.5 --dns kb.internal（以后要加就得换 CA）
```

- CA（`ca.crt`，10 年）带**名字约束**：只能给你给的 IP、名字和 `127.0.0.1`、`::1`、`localhost` 签证书。导入了它的电脑，万一 CA 私钥泄露，
  也只会被拿来冒充这几个地址，冒充不了别的网站。实测 curl（OpenSSL 3）、Python（ssl）、Node 24 都按约束校验：证书上的名字能连，
  CA 硬签出来的约束以外的名字被拒（`permitted subtree violation`）。浏览器（Chrome / Edge / Firefox、Windows / macOS 的证书库）都支持名字约束，没有逐一实测。
- 服务器证书 825 天（苹果设备不认更长的），EC P-256，名字总带 `127.0.0.1`、`localhost`：经隧道开 `https://127.0.0.1:端口` 也不报错。
  续期：再跑一次同样的命令（CA 不动，使用的人不用重新导入），然后 `docker exec kb-app python -m app.serve --check && docker restart kb-app`。
- 脚本最后打印 CA 的 SHA256 指纹：把 `ca.crt` 发给使用的人，让对方导入前核对这串指纹（经另一个渠道告诉他）。
- 配应用：同甲一第 5 步。

**使用的人怎么信任这个 CA**（只导入 `ca.crt`，任何情况下都不要关掉证书校验，也不要设 `NODE_TLS_REJECT_UNAUTHORIZED=0`）：

| 客户端 | 做法 |
|---|---|
| Windows 的 Chrome / Edge | `certutil -user -addstore Root ca.crt`（弹窗确认指纹），或双击 `ca.crt` →「安装证书」→ 当前用户 →「受信任的根证书颁发机构」 |
| macOS 的 Safari / Chrome | `security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db ca.crt` |
| Linux（Debian / Ubuntu 系统级） | `cp ca.crt /usr/local/share/ca-certificates/doc2sop-ca.crt && update-ca-certificates` |
| Firefox | 设置 → 隐私与安全 → 证书 → 查看证书 → 证书颁发机构 → 导入，勾「信任由此证书颁发机构来标识网站」 |
| Claude Code、Cursor、VS Code 等 Node 系客户端 | 启动前设环境变量 `NODE_EXTRA_CA_CERTS=/路径/ca.crt`（只加信任、不替换系统证书）；VS Code 也读系统证书库 |
| Claude Desktop | 「连接器」里加的远程 MCP 是从 Anthropic 的服务器去连的，私有 CA、只在内网能到的地址都用不了；改用本机桥接 `mcp-remote`：`claude_desktop_config.json` 里 `"command": "npx", "args": ["mcp-remote", "https://IP:端口/mcp", "--header", "Authorization:${AUTH_HEADER}"], "env": {"AUTH_HEADER": "Bearer <令牌>", "NODE_EXTRA_CA_CERTS": "/路径/ca.crt"}` |
| Python（MCP SDK、httpx、requests） | `ssl.create_default_context(cafile="ca.crt")` 传给 `httpx.Client(verify=…)`；requests 用 `verify="ca.crt"`；不改代码时设 `SSL_CERT_FILE=/路径/ca.crt`（只信这一个 CA，别的 https 会连不上，单独给这个进程设） |

### 放开 MCP_CLIENTS（上了 HTTPS 之后）

1. `MCP_ALLOWED_HOSTS` 填对外用的名字或 IP（不带端口就是任意端口），隧道还要用就留着本机：`MCP_ALLOWED_HOSTS=kb.example.com,127.0.0.1,localhost`。
   它防的是 DNS 重绑定，不是访问控制。
2. `MCP_CLIENTS` 建议仍写来源名单：同事的出口 IP、公司网段、调用方系统的地址，再加上 `127.0.0.1,::1`（隧道）。
   经反向代理时名单比对的是代理转来的真实地址（`TRUSTED_PROXIES` 配对了的前提下）。
3. 确实要对全公网开放（使用的人出口地址不固定），就删掉 `MCP_CLIENTS`。风险要想清楚：令牌成了唯一的门，会被扫描、被试；
   每枚令牌按 `MCP_RATE_PER_MINUTE` 限流、可以设过期时间和分类白名单，丢了马上在页面上吊销；数据工具（`export`）开放得越少越好；
   页面上的总开关随时能关。前面有代理时再在代理上加一道限流（上面 nginx 片段的 `limit_req`）。
4. 发版后打开「对外接入」页核对：连接是 HTTPS、证书的名字和到期日对、没有红色提示；签发令牌，客户端用 `https://…/mcp` 连。

对外接入页上：明文、又对本机以外开放 `/mcp`（`MCP_CLIENTS` 为空或含非回环地址）时标红；应用端口明文监听所有地址、只靠前面的代理加密时也标红
（别人能绕过代理直连明文端口）；经没登记的代理转来的请求标红。

### 例：本项目的生产机（doc2sop.autos）

国内云服务器（京东云，Ubuntu 24.04），应用 host 网络、`release.sh` 发版；域名 `doc2sop.autos` 在阿里云注册和解析、在阿里云做了 ICP 备案，
**京东云还没做接入备案**，所以 80 / 443 不能用于这个域名；443 被 realm、8443 被 haproxy 占着（都是别的服务，不要动），9443 空着。
现状：`0.0.0.0:8765` 明文 HTTP，`MCP_CLIENTS=127.0.0.1,::1`（只走 SSH 隧道）。打算的做法（**每一步都要先问过用户**）：

1. 阿里云解析加 A 记录 `doc2sop.autos → 服务器公网 IP`；京东云安全组放行入站 TCP 9443（8765 的入站规则可以随后删掉）。
2. 按甲一签 `doc2sop.autos` 的证书，装到 `/opt/kb-app/tls`（RAM 子账号、AccessKey 由用户自己在服务器上填）。
3. 环境文件先备份，再改成：

   ```bash
   PORT=9443                     # HTTPS，对外
   LOCAL_HTTP_PORT=8765          # 明文只留在 127.0.0.1：隧道、探活、各期的基线命令照旧用 http://127.0.0.1:8765
   TLS_CERT_FILE=/tls/server.crt
   TLS_KEY_FILE=/tls/server.key
   TLS_DIR=/opt/kb-app/tls
   MCP_ALLOWED_HOSTS=doc2sop.autos,127.0.0.1,localhost
   # MCP_CLIENTS 放给谁由用户决定（同事出口 IP / 全公网），没定之前保持 127.0.0.1,::1
   ```

   再照常发版（命令不变，`release.sh` 从环境文件读 `TLS_DIR`；预检不过不会切换）。
4. 影响：`http://服务器IP:8765` 从公网打不开了（8765 只听 127.0.0.1）；浏览器改用 `https://doc2sop.autos:9443`，经隧道的书签不变。
   自动执行的「报告链接」可以改成 `https://doc2sop.autos:9443`（https 的链接聊天里才给）。审批口令可以在 HTTPS 页面上输了。
5. 回滚：恢复环境文件的备份，再 `release.sh --image <上一个镜像>`（老镜像不认这些设置，`release.sh` 会拦住没恢复环境文件的回滚）。
   只想关掉 HTTPS、保留新代码：恢复环境文件备份后 `release.sh --image <当前镜像>`。

**以后在京东云做完接入备案、443 腾出来了**（realm 挪走——那是用户的其他服务，由用户安排）：环境文件里 `PORT=443`，安全组放行 443，
`release.sh --image <当前镜像>`；证书、`MCP_ALLOWED_HOSTS`（不带端口）都不用动，客户端的地址改成 `https://doc2sop.autos/mcp`。
想两个端口都留一阵子过渡，就用 iptables 的 `PREROUTING … REDIRECT --to-ports 9443` 把 443 转过去（只改目的端口，来源地址不变），别用 TCP 转发程序转到 127.0.0.1。

## 对外接入（MCP）

让同事的 Claude Code、GitHub Copilot、Cursor 接进来查知识库、按 SOP 排查（能开放什么、令牌、审计见
[`工具.md` 的「对外 MCP 出口」](工具.md#对外-mcp-出口让-claude-codecopilotcursor-用上知识库和-sop)）。默认关，打开分三步：

1. **打开出口**：`/opt/kb-app/.env` 里 `MCP_ENABLED=true`，照常发版。验证：
   `curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8765/mcp` 返回 401（关着时是 404）。
2. **签发令牌**：左侧导航「对外接入」→ 签发，每个客户端一枚；明文只显示一次，页面同时给出 Claude Code、VS Code、Cursor 的配置片段。
   要开放数据工具，先在 `/opt/ops/ops_tools.yaml` 里标 `export`（见上面链接），工具服务热加载，不用重启。
3. **网络**：不配 HTTPS 时应用在 `0.0.0.0:PORT` 上跑明文 HTTP，令牌和返回内容都是明文。按使用范围选一种：
   - **只在本机或经 SSH 隧道用**（最省事，不用域名和证书）：`.env` 里设 `MCP_CLIENTS=127.0.0.1,::1`，发版；
     使用的人开 `ssh -N -L 8765:127.0.0.1:8765 用户@宿主机`，客户端连 `http://127.0.0.1:8765/mcp`，
     令牌也在隧道开着时从 `http://127.0.0.1:8765` 打开「对外接入」页签发（页面给的接入地址取自浏览器地址栏）。
     `MCP_CLIENTS` 查的是来源地址：经隧道进来的连接对端是本机，公网来的一律 403，带着有效令牌也一样，令牌库都不碰。
   - **给公网或内网的同事、别的系统直连**：先按上面「HTTPS 与对外放开」上 HTTPS，再按那一节最后的「放开 MCP_CLIENTS」做。

**Host 检查不是访问控制。** `MCP_ALLOWED_HOSTS` 防的是 DNS 重绑定（恶意网页借浏览器打本机端口）和客户端误填地址；
Host 头由客户端随便写，拿到令牌的人带上 `Host: 127.0.0.1:8765` 照样能从公网连。要限制谁能连，用 `MCP_CLIENTS`
（来源 IP 或网段）、安全组或反向代理。来源地址由应用自己算：前面有反向代理时只认 `TRUSTED_PROXIES` 里的代理传来的
`X-Forwarded-For`，公网来的连接伪造这个头改不了来源；`FORWARDED_ALLOW_IPS` 不再起作用（设了会拒绝启动）。

令牌丢了就在页面上吊销重签（库里只存哈希，找不回明文）。吊销后下一个请求就失败，它还连着的通知流当场断开、开着的会话一并关掉。
吊销了、过期了的令牌可以「删除」记录，调用记录照样留着。

**页面上的总开关**：`.env` 的 `MCP_ENABLED=true` 是上限，「对外接入」页最上面还有一个开关（存在 `access.db`，没改过就是开）。
关不要口令，所有连接当场断开，之后 `/mcp` 对谁都回 403（`disabled`），令牌照常管理；重新打开要审批口令，
工具服务较旧或 `OPS_PAGE_CONFIG=off` 时打不开。清除调用记录（全部、N 天以前、某枚令牌的）也要口令，每次开关、删令牌、清除都在页面的
「操作记录」里留一条（谁、什么时候、从哪个地址、清了多少条），这张表页面上删不掉。

- **逃生口**：工具服务坏了又关着时，在宿主机上 `docker exec kb-app python -m app.access open`（`status` 只看）。它不要口令，
  因为能执行它的人已经有宿主机的 root——和直接改 `.env`、改 `access.db` 一样。打开记一条 `user=cli` 的操作记录，运行中的应用不用重启。
- **回滚注意**：旧镜像（b16c4f6 及以前）不认这个开关，**回滚以后按 `.env` 重新打开**——页面上关过的，回滚后又对令牌开放。
  只想关掉又要回滚时，先把 `.env` 的 `MCP_ENABLED` 改成 `false` 再回滚。`access.db` 里的 `mcp_state`、`access_changes` 两张表留着，
  升级回来照旧生效。
- 验证（只读，不改开关）：经本机不带令牌 `POST /mcp` 回 401（开着、挂着）；关着时回 403 `{"error": "disabled", …}`；
  不带口令 `POST /api/mcp/switch {"on": true}` 回 400「没有输入审批口令」，不消耗口令次数。

## 自动执行（定时、告警、邮件）

执行记录、知识库缺口发版后就有，不用配；定时计划在页面「SOP → 自动执行」里建（能做什么见 [`自动执行.md`](自动执行.md)）。
邮件和告警入口的设置（发件邮箱和授权码、收件组、报告链接、告警令牌和来源地址）**在页面上填，或在服务器上写**：

- **页面上填**：「SOP → 自动执行」的「邮件」「告警入口」两张卡片。扩大能力的改动（新设或修改发件设置、加收件组或收件人、改报告链接、
  生成告警令牌、加来源地址）要**审批口令**，由工具服务核对（`POST /tools/approval/verify`：只核对、不写，和批准工具共用输错计数和锁定）。
  所以**工具服务要升级到这一版**（`ops_readonly.py`；`ops_exec.py` 没变就不用换）：老工具服务没有这个接口，页面上只读，写明「工具服务较旧」。
  缩小能力的（删收件人、删收件组、删令牌、清除发件设置）只要网页密码。工具服务上 `OPS_PAGE_CONFIG=off` 时这里也只读。
  **审批口令等同工具服务那台机器的 root**（见下面「页面审批：审批口令」的残余风险），只经 SSH 隧道打开页面再输：
  `ssh -N -L 8765:127.0.0.1:8765 root@宿主机`，浏览器开 `http://127.0.0.1:8765`。
  页面上填的存在 `/opt/kb-app/data/automation.page.json`（不含密钥，进备份包）和 `automation.page-secrets.json`（授权码、告警令牌，
  只写不读，**不进备份包**），都由应用写、`0600`，改完立即生效。
- **在服务器上写**：要用内网自签证书、改超时，或者不想在页面上管，就写一个文件。**两边都写了的以这个文件为准**，在页面上只读（标「在服务器上配置」）：

  ```bash
  f=/opt/kb-app/data/automation.yaml                        # 容器里是 /data/automation.yaml
  [ -e "$f" ] && cp -a "$f" "$f.bak-$(date +%Y%m%d%H%M%S)"   # 改之前留一份（cp -a 保留 600）
  touch "$f" && chmod 600 "$f" && vi "$f"                   # 格式见 docs/自动执行.md「服务器上的配置文件」；保存即生效，不用重启
  ```

验证：

1. 页面「SOP → 自动执行」顶上是「✓ 邮件已配置」「✓ 告警入口已打开」；写错了，这里列出哪里不对（不带密钥）。
2. 「邮件」卡片里选一个收件组，点「发一封测试邮件」。没收到就看 `docker logs kb-app 2>&1 | grep -i mail`：写了失败原因，不带 SMTP 主机和授权码。
3. 告警入口：`curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8765/api/alerts/hook` 返回 401（没有令牌时是 404）。
   Alertmanager 那边的配置见 [`自动执行.md` 的「告警触发」](自动执行.md#告警触发)。
4. 页面上的每次改动：`docker logs kb-app 2>&1 | grep 'automation settings'` 一行（谁、从哪里、改了什么，不记授权码和令牌）；
   每次核对口令在工具服务的日志里：`journalctl -u ops-readonly | grep '\[approval\]'`（`[approval] 邮件设置 发件服务器 smtp.qq.com:465：口令正确 caller=…`）。

**网络**：告警入口和页面在同一个端口上，是明文 HTTP。监控和应用在同一台机器或同一个可信内网时，配上来源地址
（页面上「告警入口」的来源地址，或文件里的 `alerts.clients`，写 Alertmanager 的地址）；跨网络时前面放 TLS 反向代理（同上面「对外接入」）。

**关掉**：页面上删掉告警令牌（或删掉文件里的 `alerts` 段），告警入口马上变回 404；清除发件设置（或删掉 `mail` 段），计划照常执行、只是不发邮件；
计划在页面上暂停或删除。都不用重启。

**备份和回滚**：计划、告警规则、执行记录在 `graph.db` 里，`automation.page.json` 也照常进备份包；授权码和令牌（`automation.page-secrets.json`、
`automation.yaml`）**不进备份包**：恢复以后在页面上重输授权码、重新生成令牌，`automation.yaml` 自己另存一份。
只回滚应用到不认识页面设置的版本：它只读 `automation.yaml`，页面上填的邮件、收件组、令牌都不生效，告警入口回 404；文件都留着，升级回来就恢复。
只回滚工具服务：页面上只读（「工具服务较旧」），已经存好的设置照常生效。
回滚到没有自动执行功能的版本时，旧版本不认识这几张表、也不碰它们：计划不再执行，告警入口变回 404
（Alertmanager 那边会看到发送失败）。再升级回来，计划接着跑，中间到点的各记一条「错过」（选了收件组的会收到邮件）。

演示站不用配；想在演示站上试，就在它自己的数据目录（compose 挂到容器 `/data` 的 `./data`）下写同样的文件，或者在演示站的页面上填。

## 云上协同（群聊机器人）

让大家在云上协同的群里 @ 机器人提问、私聊提问，计划和告警规则的结果推到群里（推送见
[`自动执行.md` 的「推送到云上协同」](自动执行.md#推送到云上协同)）。默认关，关着时问答和发给模型的提示词和以前一字不差。

- **两段**：宿主机上的转接程序 [`deploy/ccwork/ccwork_bridge.py`](../deploy/ccwork/ccwork_bridge.py)（systemd 服务 `doc2sop-ccwork`，
  系统账号 `doc2sop-ccwork`，不进 docker 组）用应用机器人的身份连云上协同的 MQTT 收消息、调开放平台接口发消息，
  本地接口只听 `127.0.0.1:8796`；kb-app 带令牌去长轮询它。kb-app 只加了登录后的页面接口，没有任何不经登录的路由，转接程序也不需要网页密码。
- **谁能用、能查什么**：kb-app 数据目录的 `chat.yaml`（格式见 [`app/chat_config.py`](../app/chat_config.py) 开头），按群、按人开通；
  群里默认只查文档、不联网、一个数据工具都不开。`categories` 同时收窄知识库和 SOP：来源文档在别的分类里的 SOP，
  这个群里看不到、也执行不了（手工创建的照常）。**推到哪**：转接程序的 `/etc/doc2sop-ccwork/targets.yaml`，页面上只能选名字。
- **`chat.yaml` 写错时一律往紧里算**，哪里不对列在「对外接入」页卡片的「要处理的」里：一个群或一个人的设置里有不认识的键
  （比如把 `categories` 拼成 `category`）、`categories` 写了却一个能用的分类都没有 → 这个群或这个人不开通；顶层有不认识的项、
  `paused` 或 `limits` 写得不对 → 整个暂停，开通的群和人只收到「暂停服务中」；整个文件读不了、YAML 写错 → 谁也没开通，也不回话。
- **群聊的对话**照常存进对话库，网页「对话」里看得到（带「💬 群名」，能按 全部 / 网页 / 云上协同 筛选），**网页上只读**。
  群聊记录**暂不自动删**（`chat.yaml` 的 `keep_days` 只是占位）。

**1. 装转接程序**（root；`CCWORK_ENABLED=false` 时不取凭据、不连 MQTT）：

```bash
ss -ltn | grep -q ':8796 ' && echo '8796 被占了，先别装'
apt install python3-paho-mqtt python3-cryptography python3-yaml
useradd --system --no-create-home --shell /usr/sbin/nologin doc2sop-ccwork
install -d -m 755 /opt/doc2sop-ccwork
install -m 644 /opt/doc2sop/deploy/ccwork/ccwork_bridge.py /opt/doc2sop-ccwork/
install -m 600 /opt/doc2sop/deploy/ccwork/ccwork.env.example /etc/doc2sop-ccwork.env
install -d -m 750 -g doc2sop-ccwork /etc/doc2sop-ccwork
install -m 640 -g doc2sop-ccwork /opt/doc2sop/deploy/ccwork/targets.yaml.example /etc/doc2sop-ccwork/targets.yaml
install -m 644 /opt/doc2sop/deploy/ccwork/doc2sop-ccwork.service.example /etc/systemd/system/doc2sop-ccwork.service
openssl rand -hex 32          # 本地接口的令牌：vi /etc/doc2sop-ccwork.env 填进 CHAT_BRIDGE_TOKEN
systemctl daemon-reload && systemctl enable --now doc2sop-ccwork
# 带令牌问转接程序：令牌经标准输入交给 curl（-K -），不出现在命令行里（命令行 ps 谁都看得到）
bridge() { sed -n 's/^CHAT_BRIDGE_TOKEN=\(.*\)$/header = "X-Chat-Bridge-Token: \1"\nheader = "X-Chat-Bridge-Protocol: 1"/p' \
             /etc/doc2sop-ccwork.env | curl -s -K - "http://127.0.0.1:8796$1"; echo; }
bridge /health
```

**2. 写凭据**：app-key、app-secret 由机器人的申请人自己在宿主机上写，不发给任何人：
`python3 /opt/doc2sop-ccwork/ccwork_bridge.py set-credentials`（从标准输入读、不回显，原子写入、600）。
它把旧文件留一份 `.bak-时间`，只留最近一份（更早的删掉，删了几份会打印出来）；那份里是旧凭据，确认新凭据能用以后也删掉。

**3. 只读握手**：换令牌、读机器人信息、查组织路由，对 broker 只做 TLS 握手，不发 MQTT 登录包、不发任何消息。
单元里的环境变量是 systemd 以 root 读进来的，服务账号自己读不到 `/etc/doc2sop-ccwork.env`，所以手工跑要 root、要带 `--env-file`：

```bash
python3 -I /opt/doc2sop-ccwork/ccwork_bridge.py check --env-file /etc/doc2sop-ccwork.env
```

打印机器人 ID 末 4 位、组织、broker 的主机和端口、证书校验结果、令牌有效期；不打印任何密钥。
没有可用的加密端口就停在这一步，向厂商要。

> **明文 broker 只能用来诊断**：`CCWORK_ALLOW_PLAINTEXT=diagnose` 时连得上、收得到、计数，但不交给 kb-app、不发任何东西。
> 这时 MQTT 登录用的 jwt 也是明文发出去的，有效期内被人截获就能冒充机器人连 broker。只在 broker 确实没有加密端口时用，
> 用测试机器人，查完马上改回空、`systemctl restart doc2sop-ccwork`。

**4. 一步一步打开**（每步看完再走下一步）：

1. **只收不发**：`/etc/doc2sop-ccwork.env` 里 `CCWORK_ENABLED=true`、`CCWORK_SEND=off`，`systemctl restart doc2sop-ccwork`。
   在测试群里 @ 它、不 @ 说几句，私聊它几句；`bridge /status`（第 1 步里的函数）看计数（收到、解开、群里没 @ 的、解不开的）。
2. **接上 kb-app**：先备份 `.env`（`cp -a /opt/kb-app/.env /opt/kb-app/.env.bak-$(date +%Y%m%d%H%M%S)`），
   `vi /opt/kb-app/.env` 加两行 `CHAT_BRIDGE_URL=http://127.0.0.1:8796`、`CHAT_BRIDGE_TOKEN=`（和转接程序同一个值），
   照常发版（`release.sh --image <当前镜像>`，带上 `KEEP_IMAGES`、`PIP_INDEX_URL`）。应用是 host 网络，容器里的 127.0.0.1 就是宿主机。
   地址只认字面的 `http://127.0.0.1:端口` 或 `http://[::1]:端口`，写错了不连，页面上写明。
3. **开通测试群**：写 `/opt/kb-app/data/chat.yaml`（容器里是 `/data/chat.yaml`；没有密钥，`chmod 644`，进备份），只开测试群和自己的私聊；
   群 ID、用户 ID 从「对外接入」页「云上协同」卡片的「最近 @ 过、还没开通的」里抄（那里给好了能直接粘的几行）。改了不用重启。
4. **能发**：`CCWORK_SEND=on`，`systemctl restart doc2sop-ccwork`。在测试群里 @ 它问一句、回「帮助」；卡片上「发一条测试消息」。
5. **开正式群**：先只开知识库，再按群逐个开数据工具（`tools` 逐个写工具名，以后批准的新工具不会自动进群）。

验证：「对外接入」页最下面的「云上协同」卡片——转接程序「已连接」、加密连接、能发消息；kb-app「正在取消息」；「要处理的」是空的。

**日志**：`journalctl -u doc2sop-ccwork` 一条消息一行元数据（会话、发送人只有 ID 末 4 位），不记内容和密钥；群里没 @ 它的只计数。
kb-app 一个问题一行：`docker logs kb-app 2>&1 | grep ' chat '`（群名是 `chat.yaml` 里起的名字，人名不进日志）。

**关掉、回滚**：

- 只想让它先别答（不用重启）：`chat.yaml` 写 `paused: true`，开通的群和人只收到「暂停服务中」。
- 断开云上协同：`systemctl disable --now doc2sop-ccwork`。
- kb-app 去掉这个功能：删 `.env` 里那两行，`release.sh --image <当前镜像>`。`chat.db` 里的几张新表留着无害；群聊的对话变回普通对话
  （没有标签，网页上能续问；以后再打开这个功能时，网页上续问过的那条不会被群里接着用，会另开一条）。
- 回滚到没有这个功能的镜像时同时停掉转接程序，免得群里 @ 它没反应。
- 转接程序回到上一版：`cp -a /opt/doc2sop-ccwork/ccwork_bridge.py.bak-<时间> /opt/doc2sop-ccwork/ccwork_bridge.py && systemctl restart doc2sop-ccwork`
  （升级时先这样留一份）。
- 整个撤掉：`systemctl disable --now doc2sop-ccwork`，删单元文件、`daemon-reload`；删 `/opt/doc2sop-ccwork`，
  `/etc/doc2sop-ccwork.env` 和 `/etc/doc2sop-ccwork/` 先备份再删；`userdel doc2sop-ccwork`；要的话 `apt remove python3-paho-mqtt`。

**备份**：`chat.db`（含群聊的几张表）、`chat.yaml`、`targets.yaml` 进备份包；`/etc/doc2sop-ccwork.env`（凭据）不进。

## 钉钉（群聊机器人）

和上一节云上协同同一套 kb-app 功能（白名单、命令、限频、推送、对话只读都一样），只是换一个转接程序：
[`deploy/dingtalk/dingtalk_bridge.py`](../deploy/dingtalk/dingtalk_bridge.py)（systemd 服务 `doc2sop-dingtalk`，系统账号
`doc2sop-dingtalk`，本地接口只听 `127.0.0.1:8795`）。**同一时刻 kb-app 只连一个转接程序**（`CHAT_BRIDGE_URL` 指哪个就是哪个），
两个转接程序不同时用。默认关，关着时问答和发给模型的提示词和以前一字不差。

- **怎么连**：钉钉企业内部应用的机器人，**Stream 模式**：转接程序主动连出去（`api.dingtalk.com` 取连接凭证，
  `wss-open-connection.dingtalk.com` 收消息），**不要公网地址、不开端口**。只订阅机器人消息，不订阅任何事件；
  群里只有 @ 机器人的消息才推过来，私聊全推。只连 `*.dingtalk.com` 的 443 端口，校验证书，不走代理环境变量、不跟重定向。
- **断线**：钉钉的机器人消息不补发，断线期间 @ 它的消息就没了（和云上协同一样）；重连自动，钉钉定期要求换连接时新旧两条并存、按消息 ID 去重。
  **同一个应用只在一处连**：两处都连着时钉钉会把消息随机分给其中一处。演示站、开发机都不接。
- **回复**：用消息里带的会话回复地址（约 90 分钟有效，群里能真 @ 提问人）；过期了改走机器人发消息接口（不能 @，第一行写「↪ 回复 某某」）。
  钉钉的普通消息不能边答边改，所以**每问最多两条**：3 秒内答完只发一条答案；慢的先发一条「🔎 正在查…」，答完再发答案。
- **数据去向**（「帮助」里按配置写出来）：问题和回答经**钉钉服务器**到 doc2sop 所在的服务器，再到模型网关和模型服务商；推送的巡检、告警结果也经钉钉服务器。
- **非文字**：图片、文件、语音不下载、不看，私聊里回一句「只能看文字」；图文混排只取文字。
- **`chat.yaml` 要写 `platform: dingtalk`**，群的键是 `cid` 开头的会话 ID（云上协同是数字）。`chat.yaml` 的 platform 和转接程序对不上时
  **不取消息、不推送**，卡片上写明：换平台时旧的白名单、推送设置不会被另一个平台「继承」（两边的用户 ID 都是普通字符串，推送目标按名字找）。
  换平台以前存的计划、告警推送设置不再推，表单里提示重新选。只推送、不问答也要写这个文件。
- 依赖：`apt install python3-websocket python3-yaml`（Ubuntu 24.04 里是 websocket-client 1.7）；**不用** pip、不用钉钉官方 SDK。

## 页面审批：审批口令

工具申请可以在页面「工具 → 待审批」里批准（能看到什么、风险提示怎么定的，见 [`工具.md` 的「审批」](工具.md#审批在页面上审批口令或在宿主机命令行上)）。
批准时要另输一个**审批口令**：它和网页登录密码无关，只以加盐的慢哈希存在工具服务这台机器上、由工具服务核对。发版脚本不替你设，也不生成。

**在页面上设（推荐）。** 「设置 → 审批口令」（「工具 → 主机与数据源」最下面是同一张卡片；「待审批」里有「现在设置」）：

- 还没设时直接设：新口令输两遍，至少 12 个字符，不能和网页登录密码相同。
- 设好之后要改，得先输旧口令；旧口令输错和批准输错算同一个计数（连续 5 次锁 15 分钟），锁定期间不能改。
- 页面上没有找回：**忘了只能在宿主机上重设**（下面的命令）。

**首次设置的风险：部署后到设好口令之前，拿到网页密码的人能抢先设一个**，之后就能在页面上批准工具。所以部署完马上设，设好后看一眼卡片上的
「已设置：11-01 11:30，在页面上设置（来自 127.0.0.1）」：时间和来源对不上，就说明不是你设的——马上在宿主机上用下面的命令重设，
再查 `journalctl -u ops-readonly | grep '\[approval\]'` 里是谁设的（`首次设置了审批口令 caller=web user=… ip=…`）。
来源是应用看到的对端地址：应用用 host 网络（`release.sh` 的做法）时，经 SSH 隧道打开是 `127.0.0.1`；docker compose 起的应用看到的是
Docker 网桥的网关地址；前面有反向代理时，是代理转发的客户端地址（代理登记在 `TRUSTED_PROXIES` 里）；经没登记的代理转来的请求记成
`untrusted-proxy`（见「HTTPS 与对外放开」）。

**在宿主机上设或重设**（root；第一次设、忘了重设都用它，不需要旧口令）：

```bash
# 交互输入两次，不回显，至少 12 个字符。正在运行的工具服务不用重启
python3 /opt/ops/ops_readonly.py set-approval-passphrase
ls -l /etc/ops-readonly/approval.hash        # -rw------- root root
# 从自己的电脑上远程设：ssh -t 才能交互输入
ssh -t root@宿主机 "python3 /opt/ops/ops_readonly.py set-approval-passphrase"
```

- 没设之前，页面上的批准按钮不可用；拒绝照常，命令行审批（`pending` / `approve` / `reject` / `trust`）照常。
- 文件要求：普通文件、不是符号链接、属 root、组和其他用户不能读写（`chmod 600`）。不满足就当作没设，`journalctl -u ops-readonly`
  里有一行 `[approval]` 写明原因，页面上也写着；这时页面上不能设也不能改、不会覆盖它，查明原因后用上面的命令重设。
  位置可以用环境变量 `OPS_APPROVAL_FILE` 改（写进 `/etc/ops-readonly.env`）。
- **页面上设口令时工具服务要写这个文件。** 用 [`deploy/ops-readonly.service.example`](../deploy/ops-readonly.service.example) 的
  `ProtectSystem=strict` 时，`ReadWritePaths` 里要有它所在的目录（模板里已经是 `/opt/ops -/etc/ops-readonly`），目录要先建好：
  `install -d -m 700 /etc/ops-readonly`。不然页面上设置会报「写不了口令文件」，命令行照常能设。改了 `OPS_APPROVAL_FILE` 就换成它的目录。
- **删掉口令文件等于回到「还没设」**：谁拿到网页密码谁就能在页面上设。不想用页面审批，就设一个谁也不知道的随机口令：
  `openssl rand -hex 32 | python3 /opt/ops/ops_readonly.py set-approval-passphrase`。
- **锁定**：连续输错 5 次，页面审批锁 15 分钟（批准、重新确认脚本、提交并立即批准、改口令，以及页面上改主机与数据源、自动执行的邮件设置，共用这个计数）。锁在内存里，急用就
  `systemctl restart ops-readonly`；锁定期间命令行照常。
- 每次尝试在工具服务的日志里记一行，只有结果和来源：`[approval] 批准 nginx_errors（a1b2c3d4）：口令错误（连续第 2 次） caller=web user=admin ip=…`；
  设置、修改记成 `[approval] 首次设置了审批口令 caller=…`、`[approval] 修改了审批口令 caller=…`。口令不进任何日志。

**残余风险：口令经明文 HTTP 传输。** 不配 HTTPS 时应用在 `0.0.0.0:PORT` 上跑明文 HTTP，网页密码和审批口令在网络上都是明文。审批口令挡住的是
「只拿到了网页密码」的人；能在路上抓包的人两个都拿得到——而**审批口令等同工具服务这台机器的 root**（能批准以 root 运行的命令，
读写这台机器上的任何文件，见下文「页面上配置主机与数据源」的残余风险）。所以审批只在 HTTPS 或经 SSH 隧道打开的页面上做：
`ssh -N -L 8765:127.0.0.1:8765 root@宿主机`，浏览器开 `http://127.0.0.1:8765`（页面既不是 https、又不是从本机地址打开时，
输口令的对话框里会提示一句，每页顶上也有一条红色横幅）；长期给别人用就按上面「HTTPS 与对外放开」上 HTTPS。

**防跨站请求伪造。** 页面用 Basic 认证，浏览器会自动带上凭据，所以应用拒绝别的网站发起的修改请求：`/api/` 下除 GET、HEAD 以外的请求，
Origin（没有就看 Referer）的主机和端口跟请求的 Host 对不上就 403。前面有反向代理时要原样转发 Host（`proxy_set_header Host $host;`，
「HTTPS 与对外放开」里的 nginx 片段已经写了），否则页面上的修改都会被当成跨站请求拒绝。curl、评测脚本不带这两个头，不受影响。

## 工具申请的自动检查与模型预审

审批页在风险提示下面多了「自动检查」（工具服务试探：能用 / 有问题 / 跑不了 / 没法自动判断）和「模型预审」（应用调对话模型，只供参考），
能看到什么、怎么防探测和提示注入见 [`工具.md` 的「自动检查与模型预审」](工具.md#自动检查与模型预审能不能用读得懂吗)。

- **自动检查不要开关**，但工具服务要升级：备份后把 `ops_readonly.py` 和 `ops_exec.py` 一起拷到 `/opt/ops`，`systemctl restart ops-readonly`。
  应用和工具服务一起升级、一起回滚；应用新、工具服务旧时，页面上写「工具服务版本较旧，没有自动检查」，「检查一下」「重新检查」回 501，
  别的照常。每次试探在工具服务的日志里一行：`journalctl -u ops-readonly | grep '\[precheck\]'`。
- kubectl 的权限检查用的是工具服务自己的 kubeconfig（和 kubectl 工具执行时同一个只读账号），只发 `kubectl auth can-i`；
  SQL 的 EXPLAIN 用连接里的只读账号，和工具真正执行时同一套只读事务、语句超时（最多 5 秒）。
- 所有真正的试探合起来每分钟最多 30 次（提交、审批页、工作台、「检查一下」、「重新检查」都算，命中缓存的不算），多的在后台排队，
  日志里会有 `[precheck] 试探太多，排队等了 …s`。要调就在 `/etc/ops-readonly.env` 里加 `OPS_PRECHECK_PER_MINUTE=<次数>`，再重启 ops-readonly。
- **模型预审默认关**。打开：先备份 `.env`（文件名带时间戳），加一行、照常发版（带上 `KEEP_IMAGES`、`PIP_INDEX_URL`）：

```bash
cp -a /opt/kb-app/.env /opt/kb-app/.env.bak-$(date +%Y%m%d%H%M%S)
echo 'TOOL_PREREVIEW=true' >> /opt/kb-app/.env
# 可选：TOOL_PREREVIEW_MODEL=另一个模型（留空用对话模型）
# 验证：/api/tools 的 prereview 是 true；提交一条申请后 docker logs kb-app 里有 tool prereview done: 申请 <编号> …
# 关掉：删掉这一行（或改成 false），再 release.sh --image <当前镜像>
```

  同时最多 2 个预审在调模型，同一份内容只跑一次（缓存在内存里，重启应用后打开审批页会补跑）。演示站在 `/root/doc2sop-demo/.env` 里
  加同样的行（同样先备份），再 `docker compose --profile demo up -d`。

## 页面上配置主机与数据源

「工具 → 主机与数据源」上能加连接（HTTP、PostgreSQL、MySQL）、远程 MCP server、远程主机，能开关工具的对外开放；主配置里已有的条目只读。
怎么用、有哪些限制见 [`工具.md` 的「在页面上配置主机与数据源」](工具.md#在页面上配置主机与数据源)。谁能改什么分三层：

| | 能做什么 |
|---|---|
| 网页密码 | 看；停用工具、关闭对外开放（只缩小能力）；检查主机连通、重新扫描 host key、生成和下载安装包；提交、拒绝工具申请 |
| 审批口令（工具服务核对；等同这台机器的 root，见下面「残余风险」） | 批准工具；在页面上加、改、删连接（含测试连接）、远程 MCP server、远程主机、K8s 集群（含测试连接）；核对 host key；用密码自动安装、用账号密码添加机器（只在经 SSH 隧道打开的页面上）；打开对外开放 |
| 只能在服务器上 | 主配置里已有的条目；本机 MCP server（stdio）、脚本；sqlite、自定义 CA、令牌文件；引用服务器上的 `${名字}` 凭据；把外部改标成内部；计算沙箱、联网搜索；`OPS_PAGE_CONFIG` |

- **开关 `OPS_PAGE_CONFIG`，默认开。** 升级到这个版本以后，**设了审批口令的部署马上就能在页面上配置**；没设口令时页面实际上只读。
  不想要，在 `/etc/ops-readonly.env` 里加一行再重启：

  ```bash
  cp -a /etc/ops-readonly.env /etc/ops-readonly.env.bak-$(date +%Y%m%d%H%M%S)
  echo 'OPS_PAGE_CONFIG=off' >> /etc/ops-readonly.env && systemctl restart ops-readonly
  journalctl -u ops-readonly -n 30 | grep OPS_PAGE_CONFIG     # 启动日志里有「页面配置主机与数据源：已关」
  ```

  关掉后页面上加、改、删、测试、打开对外开放、核对 host key、生成安装包都回 403，页面只读并写明原因；检查连通、重新扫描照常。
  已经在页面上加了的照常生效：要停用它们，先在页面上删掉再关。
- **文件**：工具服务要写 `/opt/ops`（`ops_tools.page.yaml`、`ops_tools.page.known_hosts`、`ops_tools.page.log`、`page-bundles/`）和
  `/etc/ops-readonly`（`page-secrets.json`、`page-hosts/`）。模板 [`deploy/ops-readonly.service.example`](../deploy/ops-readonly.service.example)
  的 `ReadWritePaths=/opt/ops -/etc/ops-readonly` 已经够了；私密目录可以用 `OPS_PRIVATE_DIR` 改（默认是审批口令文件所在的目录）。
  页面上加主机要工具服务那台机器有 OpenSSH 客户端（`ssh`、`ssh-keygen`、`ssh-keyscan`），和命令行 `enroll` 一样。
- **安装包的核对**：页面上加的主机，安装包经浏览器转交到目标主机。谨慎的话，在目标主机上执行之前，先 SSH 到工具服务那台机器上对照：

  ```bash
  sha256sum /opt/ops/page-bundles/<主机名>.tgz          # 和下载下来的那份、页面上显示的 sha256 一致
  python3 /opt/ops/ops_readonly.py host-info <主机名>     # 只读：authorized_keys 那一行、建账号的命令，和页面上一字不差
  ```

- **日志**：`journalctl -u ops-readonly | grep '\[page-config\]'`，每次改动一行：谁、从哪里、改了什么，不记凭据；口令的每次尝试照旧记 `[approval]`。
- **用密码自动安装**（页面上加的主机，核对 host key 以后）：输一次目标主机的账号和密码，工具服务登录一次，把建账号、放公钥、装执行器
  原样执行掉，密码用完即丢、不保存。细节和不支持的情况见 [`工具.md` 的「用密码自动安装」](工具.md#用密码自动安装密码只用一次)。部署上要知道的：
  - 工具服务那台机器要 OpenSSH 客户端 8.4 以上（`SSH_ASKPASS_REQUIRE`；Ubuntu 24.04 是 9.6，演示站的 demo-ops 也够），工具服务的
    `/tmp` 要能写（模板的 `PrivateTmp=yes` 是私有的 /tmp，正好）。核对：带令牌 `curl -s -H "X-Ops-Token: …" 127.0.0.1:8799/tools/config/host-install`
    回 `{"supported": true, "why": ""}`。
  - **只能经 SSH 隧道用**：应用对不是本机（`127.0.0.1`、`::1`）来的这个请求一律回 403，不转交、不消耗口令次数，页面上按钮灰掉。
    「本机」由 `app/peer.py` 判断：内置 TLS 不改变这一条；前面有反向代理时，代理必须登记在 `TRUSTED_PROXIES` 里并传 `X-Forwarded-For`，
    否则代理转来的请求一律按外部来源处理（见「HTTPS 与对外放开」）。**不要用 TCP 转发（realm、stunnel、iptables DNAT……）把公网连接
    接到应用端口**：那样进来的连接对端也是本机，应用只能靠 Host 头发现，而 Host 是客户端写的。演示站经 docker 端口映射访问，
    应用看到的是网桥地址，按钮总是灰的，这是预期的，不要把网桥地址加进白名单。
  - 普通账号走 sudo，用完执行 `sudo -k`；登录连续被拒 2 次这台主机锁 15 分钟，目标主机上的 fail2ban（我们三台是 10 分钟错 5 次）不会因此封掉工具服务的地址。
  - 记录：`[page-config] 用密码安装 <主机>：<账号>@<地址>:<端口>（root / sudo），成功 / 失败于…；密码已丢弃`，不记密码。
  - 回滚：旧工具服务没有这个接口，页面写「工具服务较旧」，照旧手工安装；已经装好的主机不受影响。
- **用账号密码添加机器**（一个对话框走完：保存、扫描、人核对指纹后登记、用密码安装、检查连通，审批口令只输一次）：细节见
  [`工具.md` 的「用账号密码添加机器」](工具.md#用账号密码添加机器一个对话框走完)。部署上要知道的：
  - 和用密码安装一样**只收本机来的请求**（`host-onboard`），判断同上。
    不是经隧道打开的页面，对话框里给出 `ssh -L` 的命令。
  - 口令只核对一次靠「添加流程的授权」：工具服务内存里只存它的 sha256，15 分钟、只限这台主机、只能登记 host key（一次）、用密码安装、
    只改出口地址；页面审批锁定期间不认；重启工具服务就全部作废（页面退回去要口令）。日志 `[approval] … 用添加流程的授权（口令在 hh:mm:ss 核对过）`。
  - 安装第 0 步核对目标主机看到的来源地址：不在出口地址里就什么都不改、停下，页面上由人确认后改成那个单个地址（`[page-config] 修改出口地址`）。
- **页面上的 K8s 集群**：名字、https 地址、CA 存 `ops_tools.page.yaml` 的 `clusters` 段（进备份）；只读令牌存 `page-secrets.json`
  的 `cluster:<名字>`（只写不读，**不进备份**）。用法、不支持的 kubeconfig 写法见 [`工具.md` 的「K8s 集群」](工具.md#k8s-集群)。部署上要知道的：
  - kubectl 工具填了 `cluster` 时，临时 kubeconfig 写在 `/dev/shm/doc2sop-kube-*`（没有 `/dev/shm` 就是私密目录下的 `kube-tmp/`），用完即删；
    工具服务那台机器要有 kubectl。服务器上原来的 `KUBECONFIG`（生产的只读 ServiceAccount）照旧是不填 `cluster` 时的默认。
  - 没在页面上加集群时，`/tools`、`/tools/full`、`/tools/config` 和以前逐字节相同；新接口 `GET /tools/config/clusters`。
  - 「测试连接」用 SelfSubjectAccessReview 问令牌能不能读 Secret、能不能写：只问权限、不读数据，集群里不留东西；能就标红，请换只读账号（见下文「K8s 只读账号」）。
  - 回滚：旧工具服务把 `clusters` 段当作不认识的部分忽略（`[config]` 日志里有一行），`cluster` 参数随之消失，kubectl 工具照旧用服务器上的 kubeconfig；
    文件和令牌都留着，升级回来就恢复。SOP 里写死了 `cluster` 的步骤在旧版上多出的参数被忽略，查的是服务器上的默认集群——回滚前看一眼。
- **备份**：`backup.sh` 带上 `ops_tools.page.yaml`、`ops_tools.page.known_hosts`、`ops_tools.page.log`；**页面上输入的凭据和页面上加的主机的私钥
  不进备份**（和自动执行的授权码、告警令牌一样）。在新机器上恢复以后，页面上的连接、MCP server 显示「未设置」，在页面上重新输入凭据；
  页面上加的主机没有私钥连不上，删掉重新加（生成新私钥，目标主机上换掉 authorized_keys 那一行）。整机搬迁时自己把 `/etc/ops-readonly`
  一起带过去，权限不变。
- **回滚**：旧版工具服务不认识这几个旁路文件：页面上加的连接、MCP server、主机、对外开放设置都不生效，用到它们的工具加载不了
  （工具列表里没有了，用到它们的 SOP 标「引用了当前不可用的工具」，原因写在 `[config]` 日志里），别的照常，不会崩；文件都留着，
  再升级回来就恢复。注意反方向的一处：主配置里写了 `export: true`、在页面上关掉的工具，回到旧版又对外开放了——
  回滚前先在主配置里删掉那一行。应用新、工具服务旧时，「主机与数据源」页写明「工具服务版本较旧」，只读；应用旧、工具服务新时是以前的只读页面。
- **残余风险：审批口令等同工具服务那台机器的 root。** 它本来就能批准以 root 运行的命令，读、写这台机器上的任何文件
  （批准一条 `cat /etc/ops-readonly.env` 或 `cat /etc/ops-readonly/page-secrets.json`，服务器上和页面上存的凭据就都拿到了），
  页面审批上线时就是这样；页面配置又让它多管了连接、MCP server、主机和对外开放，以及自动执行的发件邮箱、收件组、告警令牌。页面配置的两条硬规矩（页面上的连接引用不了
  服务器上的凭据；去向一变，存好的凭据作废）防的是在这条路上把凭据悄无声息地带到别处、配错和旁路文件被手改，**挡不住拿到口令的人**。
  所以像 root 密码一样对待它：
  - 只经 SSH 隧道输入：`ssh -N -L 8765:127.0.0.1:8765 root@宿主机`，浏览器开 `http://127.0.0.1:8765`；
  - 设置或输入时走过明文公网的，就当作可能已经泄露，经隧道改掉；
  - 应用被攻破时，下一次在页面上输入的口令会被截获：怀疑应用被攻破，就在宿主机上用 `set-approval-passphrase` 重设，别再在页面上输；
  - 时常看一眼「最近的配置变更」和 `[approval]` 日志。

  工具服务不保存目标主机的 root：页面上加的主机，执行器和白名单由人在目标主机上以 root 安装（安装包用上面的命令在 A 上核对），
  或者经 SSH 隧道在页面上用密码自动安装一次，密码用完即丢。

## 计算沙箱（python_exec）

让模型写一段 Python 把统计、比对算准（能读什么、返回什么、各项限制见 [`工具.md` 的「计算类与沙箱」](工具.md#计算类与沙箱python_exec)）。
应用不挂 `docker.sock`：起容器的是宿主机上的沙箱服务（systemd，只监听 `127.0.0.1:8797`），每次执行一个用完即弃的 gVisor 容器。
默认不装、应用里 `SANDBOX_URL` 留空。分三步，前两步不影响线上；第三步才让应用用上它。

**1. 装 gVisor（runsc）：只 reload docker，不要 restart。** `runtimes` 是 dockerd 收到 SIGHUP 就重新加载的配置项，
reload 不重启 daemon、不碰正在跑的容器；restart 会让所有容器重启（没开 live-restore 时）。

```bash
V=20261026.0; URL=https://storage.googleapis.com/gvisor/releases/release/$V/$(uname -m)
mkdir -p /root/gvisor-$V && cd /root/gvisor-$V
curl -fsSLO "$URL/gvisor.tar.zstd" && curl -fsSLO "$URL/gvisor.tar.zstd.sha512"
sha512sum -c gvisor.tar.zstd.sha512       # 再和 GitHub release 页的 SHA512SUMS 对一遍；宿主机下不动就在别处下好、核对后 scp 过来
tar --zstd -xf gvisor.tar.zstd -C /usr/local/bin     # runsc、containerd-shim-runsc-v1、gvisor-bin/（要和 runsc 放在一起）
/usr/local/bin/runsc --version

# daemon.json 只加 runtimes 这一项；先校验再换上，换之前留备份（原来没有这个文件就记下「没有」）
test -f /etc/docker/daemon.json && cp -a /etc/docker/daemon.json /etc/docker/daemon.json.bak-$(date +%Y%m%d%H%M%S)
python3 -c 'import json, os; p = "/etc/docker/daemon.json"; c = json.load(open(p)) if os.path.exists(p) else {}
c.setdefault("runtimes", {})["runsc"] = {"path": "/usr/local/bin/runsc"}; json.dump(c, open(p + ".new", "w"), indent=2)'
dockerd --validate --config-file /etc/docker/daemon.json.new && mv /etc/docker/daemon.json.new /etc/docker/daemon.json
docker inspect -f '{{.Name}} {{.State.StartedAt}}' $(docker ps -q) > /root/started-before-reload.txt
systemctl reload docker
docker info --format '{{json .Runtimes}}'                # 里面有 runsc
docker inspect -f '{{.Name}} {{.State.StartedAt}}' $(docker ps -q) | diff /root/started-before-reload.txt - && echo 没有容器被重启
docker run --rm --runtime=runsc --network=none --pull=never python:3.12-slim cat /proc/version   # gVisor 报的内核，不是宿主机的
```

**2. 构建镜像、装沙箱服务**（模板 [`deploy/sandbox/doc2sop-sandbox.service.example`](../deploy/sandbox/doc2sop-sandbox.service.example)）：

```bash
cd /opt/doc2sop
docker build --build-arg PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple \
  -t doc2sop-sandbox:$(git rev-parse --short HEAD) -t doc2sop-sandbox:latest deploy/sandbox
useradd --system --no-create-home --shell /usr/sbin/nologin doc2sop-sandbox    # docker 组只由单元文件给这个进程
install -d -m 755 /opt/doc2sop-sandbox
install -m 644 deploy/sandbox/sandbox_service.py deploy/sandbox/security_check.py /opt/doc2sop-sandbox/
(umask 077; printf 'SANDBOX_TOKEN=%s\n' "$(openssl rand -hex 24)" > /etc/doc2sop-sandbox.env)
cp deploy/sandbox/doc2sop-sandbox.service.example /etc/systemd/system/doc2sop-sandbox.service
systemctl daemon-reload && systemctl enable --now doc2sop-sandbox
curl -s http://127.0.0.1:8797/health
python3 /opt/doc2sop-sandbox/security_check.py      # 真实环境的安全用例：全部 PASS 才继续，有一条 FAIL 就按下面撤销
```

服务启动时自检：连不上 docker、没注册 `runsc`、本机没有镜像，都会直接退出并说明原因（`journalctl -u doc2sop-sandbox`）。
它只认 `SANDBOX_IMAGE`（默认 `doc2sop-sandbox:latest`）、`SANDBOX_CONCURRENCY`（默认 1，最多 2）、`SANDBOX_QUEUE_SECONDS`（默认 10），
都写在 `/etc/doc2sop-sandbox.env`；限制本身写死在代码里。内存：服务常驻约 20MB；每次执行时多出一个 `docker run` 客户端、
一个 containerd shim 和 gVisor 的沙箱进程，容器（含 gVisor 自己）封顶 256MB——2 核 2GB 的机器上并发保持 1。
发版脚本只清理 `kb-app` 的镜像，不碰 `doc2sop-sandbox`。

**3. 让应用用上它**：把令牌原样放进应用的 `.env`（不打印），再按当前镜像重启应用。

```bash
printf 'SANDBOX_URL=http://127.0.0.1:8797\n%s\n' "$(grep '^SANDBOX_TOKEN=' /etc/doc2sop-sandbox.env)" >> /opt/kb-app/.env
cd /opt/doc2sop && ENV_FILE=/opt/kb-app/.env DATA_DIR=/opt/kb-app/data bash deploy/release.sh \
  --image "$(docker inspect kb-app --format '{{.Config.Image}}')"
```

关掉：从 `.env` 删掉这两行，同样按当前镜像重启，`python_exec` 就不再绑定。

**升级**：`deploy/sandbox/sandbox_service.py` 改了才换（`cmp` → 备份 → 拷贝 → `systemctl restart doc2sop-sandbox`）；
`deploy/sandbox/Dockerfile`、`requirements.txt` 改了就按第 2 步重新构建，下一次执行起就用新镜像，不用重启服务。

**撤销**（全部拆掉，倒着来）：

```bash
# 先关掉应用侧（上面「关掉」），再停服务、清容器、删镜像和文件
systemctl disable --now doc2sop-sandbox && rm -f /etc/systemd/system/doc2sop-sandbox.service && systemctl daemon-reload
docker ps -aq --filter label=doc2sop.sandbox | xargs -r docker rm -f
docker images doc2sop-sandbox --format '{{.Repository}}:{{.Tag}}' | xargs -r docker rmi
rm -rf /opt/doc2sop-sandbox /var/lib/doc2sop-sandbox /etc/doc2sop-sandbox.env && userdel doc2sop-sandbox
# 去掉 runsc：daemon.json 换回第 1 步的备份（原来没有这个文件就直接删掉），再 reload，不要 restart
#   原来有：cp -a /etc/docker/daemon.json.bak-<时间> /etc/docker/daemon.json && dockerd --validate --config-file /etc/docker/daemon.json
#   原来没有：rm /etc/docker/daemon.json
systemctl reload docker
docker info --format '{{json .Runtimes}}'                # 没有 runsc 了
rm -rf /usr/local/bin/runsc /usr/local/bin/containerd-shim-runsc-v1 /usr/local/bin/gvisor-bin
```

## 接入一台主机（远程主机，受控模式）

工具服务所在的机器（下称 A）经 SSH 去另一台 Linux 主机（下称 B）上跑只读工具。不配 `hosts` 时什么都不变；配置与原理见
[`工具.md`](工具.md)「远程主机」。B 上要放的东西都归 root，执行账号只能启动执行器、只能跑白名单里的工具。
下面是在命令行上接入（写进主配置）；也可以在页面「工具 → 主机与数据源」上加（要审批口令，私钥由工具服务生成），见上文「页面上配置主机与数据源」。

1. **A：给工具服务一把专用私钥**（不设口令，靠文件权限保护；systemd 开了 `ProtectHome=yes` 时不能放在 `/root`）：

   ```bash
   install -d -m 0700 /etc/ops-readonly
   ssh-keygen -q -t ed25519 -N '' -C doc2sop-ops -f /etc/ops-readonly/id_ed25519      # 0600，属 root（工具服务的运行账号）
   echo 'OPS_SECRET_SSH_KEY=/etc/ops-readonly/id_ed25519' >> /etc/ops-readonly.env
   ```

2. **A：在 `/opt/ops/ops_tools.yaml` 顶层写主机清单**（改完即时生效；不写 `default` 时 `target` 不填就是 A 本机，现有工具和 SOP 照常）：

   ```yaml
   hosts:
     list:
       - {name: b, address: 150.109.244.82, user: opsread, key: "${ssh_key}", os: linux,
          tools: [list_containers, container_logs, container_stats, container_inspect, host_uptime, host_resources, host_disk]}
   ```

   `tools` 列出这台开放哪些工具；不写就是所有适用的命令型工具。

3. **A：登记 B 的 host key**。在 B 的控制台（不要经过这条网络）上看指纹：`for f in /etc/ssh/ssh_host_*_key.pub; do ssh-keygen -lf "$f"; done`，
   然后在 A 上：

   ```bash
   python3 /opt/ops/ops_readonly.py enroll b --from <A 连 B 的出口 IP> --env-file /etc/ops-readonly.env
   ```

   它列出 B 报上来的 host key，要你粘贴核对过的指纹，对上了才写进 `/opt/ops/ops_tools.known_hosts`，再打印 B 上要执行的安装片段。

4. **B：以 root 执行安装片段**：建执行账号（普通账号，不进 sudo；家目录也归 root、它写不了——家目录的主人能给 `~/.ssh` 改名、
   另放一把不带限制的公钥）、建 `/opt/ops-readonly`、写 `authorized_keys`
   （`restrict,from=…,command="/usr/bin/python3 -I /opt/ops-readonly/ops_exec.py --stdio"`，文件归 root，执行账号自己改不了；
   `-I` 是 Python 的隔离模式，不加载执行账号能写的 `~/.local`、不认 `PYTHON*` 环境变量，漏了它执行器拒绝启动）。
   要查容器，执行账号还要能读 docker，做法有三种：

   | 做法 | 好处 | 代价 |
   |---|---|---|
   | 把执行账号加进 `docker` 组 | 一行命令，现有容器工具原样可用 | docker 组约等于 root：一旦强制命令被绕开（比如有人给这个账号另放了一把不带限制的公钥），就是整台机器的 root。受控模式下账号只能启动执行器，风险收在白名单里 |
   | sudoers 只放行几条精确的 docker 命令 | 权限最小 | 执行器不支持 sudo（`sudo` 在解释器黑名单里），要另做改造；带参数的命令（容器名、行数）在 sudoers 里写不精确，通配符本身就是口子 |
   | 只读的 docker socket 代理（如 docker-socket-proxy，只放行 GET） | 账号拿不到写接口，绕开强制命令也写不了 | 主机上多一个常驻容器；工具模板要加 `-H unix:///…` 指向代理 |

5. **A：下发执行器和白名单**（用你自己的 SSH 身份，工具服务进程不持有能写 B 的凭据），然后核对：

   ```bash
   python3 /opt/ops/ops_readonly.py push --target b                   # 不能直接登录 B 的 root 时：--admin-user 你的账号 --sudo
   python3 /opt/ops/ops_readonly.py status --target b --env-file /etc/ops-readonly.env
   ```

   要走变更流程的，用 `push --target b --print --out /tmp/push` 导出 `allowlist.json`、`ops_exec.py`、`install.sh`，交给 Ansible 等去装。
   以后在 A 上改了工具定义、或升级了 `ops_exec.py`，再 `push` 一遍；没 push 之前，B 上对不上的工具会拒绝执行并提示「需要 push」。

**撤销一台主机**：

```bash
# B 上（root）：删账号的家目录（连同公钥）和执行器、再删账号。家目录归 root，userdel -r 不会删它
rm -r ~opsread /opt/ops-readonly && userdel opsread
# A 上：从 /opt/ops/ops_tools.yaml 的 hosts.list 删掉 b（即时生效），再删掉登记的 host key
sed -i '/^b /d' /opt/ops/ops_tools.known_hosts
```

只想暂停、不删东西：B 上把 `authorized_keys` 那一行注释掉即可，A 这边 b 会显示连不上。

**直连模式**（`mode: direct`）只要一个低权限账号和一行不带 `command=` 的公钥，不用 push；但「只读」完全靠账号权限，账号能做的事模型都能做，
页面上会标明。只在账号本身就只读、又装不了执行器的主机上用。

## 接数据库（SQL 工具）

SQL 工具的写法和三层只读见 [`工具.md` 的「SQL 工具」](工具.md#sql-工具按模板查只读数据库)。PostgreSQL、MySQL 的连接也可以在页面
「工具 → 主机与数据源」上加（要审批口令，密码在页面上输入），见上文「页面上配置主机与数据源」；只读账号照样要按第 1 步建。在服务器上配要做三件事：

1. **建只读账号**，只给要查的视图（SQL 见 `工具.md`）。密码只放工具服务的环境：在 `/etc/ops-readonly.env`（保持 0600）里加一行
   `OPS_SECRET_CMDB_PASSWORD=…`，配置里写 `${cmdb_password}`。
2. **装驱动**（sqlite 不用装）。不往系统 Python 里装——Debian 12、Ubuntu 23.04 起系统 pip 会报 `externally-managed-environment`（PEP 668），
   也不该为它动系统包。装进工具服务旁边的 `vendor/`，用到这种连接时才导入：

   ```bash
   python3 -m pip install --target /opt/ops/vendor 'psycopg[binary]>=3.1,<4'     # PostgreSQL
   python3 -m pip install --target /opt/ops/vendor 'PyMySQL>=1.2,<2'             # MySQL / MariaDB
   # 国内加 -i https://pypi.tuna.tsinghua.edu.cn/simple；--target 不受 PEP 668 限制
   chown -R root:root /opt/ops/vendor && chmod -R go-w /opt/ops/vendor
   ```

   `vendor/` 里的代码会以工具服务的身份导入，所以它必须是目录（不能是符号链接）、属于工具服务的运行账号、组和其他用户不可写，
   否则整个目录不用，工具页写明原因；位置可以用环境变量 `OPS_VENDOR_DIR` 改。机器上没有 pip 就先装 `python3-pip`（只用它的 `--target`）。
   工具服务的 Python 换了大版本，`psycopg[binary]` 要重装一遍。以前按 `PyMySQL>=1.1` 装过的，`tls: require / verify` 的 MySQL 连接
   要 1.2 以上才能用（更早的版本在服务器不支持加密时会改用明文，工具服务直接拒绝）：同一条命令加 `--upgrade` 重装，再重启。
3. **在 `/opt/ops/ops_tools.yaml` 建连接、写工具**，然后 `systemctl restart ops-readonly`（新装的驱动重启后才导入；之后只改配置不用重启）：

   ```yaml
   connections:
     - {name: cmdb, type: postgres, host: 10.0.0.12, database: cmdb, user: doc2sop_ro, password: "${cmdb_password}", tls: require}
   ```

核对：「工具 → 主机与数据源」页的连接表里有 `cmdb`（PostgreSQL，`10.0.0.12:5432/cmdb`），没有标「缺驱动」；用只读账号手工试一次写，
比如 `psql -h 10.0.0.12 -U doc2sop_ro cmdb -c 'create table t(x int)'`，应该报权限错误。
撤销：删掉配置里的工具和连接（即时生效），`/etc/ops-readonly.env` 里删掉密码，数据库里 `DROP ROLE doc2sop_ro`；不再用驱动就删掉 `/opt/ops/vendor` 再重启。

### 例：LiteLLM 网关的用量

[`deploy/templates/litellm-usage.sql`](../deploy/templates/litellm-usage.sql) 在 LiteLLM 自己的 Postgres 里建两个角色、schema `doc2sop`
和三个函数；[`litellm-usage.yaml`](../deploy/templates/litellm-usage.yaml) 是调它们的三个工具（`gateway_usage_by_model`、
`gateway_usage_by_key`、`gateway_recent_failures`，「模型网关」组）。函数只返回汇总：不含 key、请求和回答的正文，报错只给状态码和
错误类型。花费是 LiteLLM 按它的价格表估算的，没配价格的模型记为 0、不代表免费；两个用量工具的说明里写了这一点，回答花费问题时
模型会列出这些模型、说明实际花费不知道。用函数不用视图，是因为 LiteLLM 每次启动都跑 Prisma 迁移，视图会挡住它以后删列、改类型（详见 SQL 文件头）。
下面 A 是工具服务那台，B 是网关机；库在 B 的容器里，5432 没有发布到 B 的宿主机。

1. **B：建角色和函数。** 先查 LiteLLM 在用的库名（升级换过库的话不一定是 `POSTGRES_DB`），再以库的超级用户执行模板。
   `dbname` 必须和 `-d` 一致，对不上就什么都不改；等不到锁（5 秒）整个回滚，报出来就好，不要反复重试。可以重复执行：

   ```bash
   docker exec <LiteLLM 容器> sh -c 'echo "${DATABASE_URL##*/}"'        # 只打印库名，不打印密码
   docker exec -i <Postgres 容器> psql -X -v ON_ERROR_STOP=1 -v dbname=<库名> -U <超级用户> -d <库名> < litellm-usage.sql
   ```

2. **设密码，明文只在 A 上。** A 上生成密码写进 `/etc/ops-readonly.env`（先备份），只把 SCRAM-SHA-256 校验值交给 B：

   ```bash
   # A：追加 OPS_SECRET_LITELLM_DB_PASSWORD（不打印），只打印校验值（算法和 PostgreSQL 一样：PBKDF2-SHA256，4096 轮）
   python3 - <<'EOF'
   import base64, hashlib, hmac, os, secrets
   pw, salt = secrets.token_urlsafe(24), os.urandom(16)
   with open("/etc/ops-readonly.env", "a") as env:
       env.write(f"\nOPS_SECRET_LITELLM_DB_PASSWORD={pw}\n")
   salted = hashlib.pbkdf2_hmac("sha256", pw.encode(), salt, 4096)
   mac = lambda key: hmac.new(salted, key, hashlib.sha256).digest()
   b64 = lambda raw: base64.b64encode(raw).decode()
   print(f"SCRAM-SHA-256$4096:{b64(salt)}${b64(hashlib.sha256(mac(b'Client Key')).digest())}:{b64(mac(b'Server Key'))}")
   EOF
   # B：校验值经 stdin 交给 psql
   docker exec -i <Postgres 容器> psql -X -v ON_ERROR_STOP=1 -U <超级用户> -d <库名> <<'EOF'
   ALTER ROLE doc2sop_ro PASSWORD 'SCRAM-SHA-256$4096:…';
   EOF
   ```

3. **专用 SSH 隧道：A → B 上容器的 5432。** 不复用别的隧道，两头都用专用账号：
   - B：建一个只能转发的账号（nologin、没有密码；家目录、`.ssh`、`authorized_keys` 都归 root，同「接入一台主机」），公钥一行：
     `restrict,port-forwarding,permitopen="<容器 IP>:5432",permitlisten="127.0.0.1:1",from="<A 的出口 IP>",command="/bin/false" <公钥>`。
     只能转发到这一个地址；`permitlisten` 指向一个用不上的端口，等于不许反向转发；拿不到 shell。
     容器 IP：`docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}' <Postgres 容器>`。
   - A：建一个系统账号跑隧道，给它新生成一把 ed25519 密钥；`known_hosts` 只放核对过的 B 的 host key。systemd 单元的要点
     （目标地址放在 `/etc/default/<隧道服务>`：`PG_TARGET=<容器 IP>:5432`）：

     ```ini
     [Service]
     User=<隧道账号>
     EnvironmentFile=/etc/default/<隧道服务>
     ExecStart=/usr/bin/ssh -N -i <私钥> -o IdentitiesOnly=yes -o BatchMode=yes -o ExitOnForwardFailure=yes \
       -o StrictHostKeyChecking=yes -o UserKnownHostsFile=<known_hosts> -o ServerAliveInterval=30 \
       -L 127.0.0.1:15432:${PG_TARGET} <B 上的转发账号>@<B 的地址>
     Restart=always
     RestartSec=10
     ```

   连容器 IP，是因为把 5432 发布到宿主机要重建 Postgres 容器。**容器 IP 变了**（Postgres 容器重建、docker 重启之后可能变）：
   隧道照样连得上 B，但转发被 `permitopen` 拒绝，工具报「连不上数据库」。查出新 IP，改 B 上那一行的 `permitopen` 和 A 上的
   `PG_TARGET`，只重启这条隧道；LiteLLM 和别的隧道都不用动。

4. **工具服务。** 装 psycopg（见上面「接数据库」的第 2 步）；主配置按 yaml 文件头建连接 `litellm_db`，include 模板或把三个工具抄进主配置；
   `systemctl restart ops-readonly`。

核对：经隧道用 `doc2sop_ro` 连上去（A 上没有 psql 就用 vendor 里的 psycopg）试写（`create table t(x int)`）、直接读表
（`select count(*) from "LiteLLM_SpendLogs"`），都应该报权限错误；工具页里三个工具各试一次。

**LiteLLM 升级之后：**原地迁移不用管，迁移看不到这几个函数；迁移改了函数用到的列，工具会报「查询失败」，照新表结构改函数、
重新执行这份 SQL（函数返回的列变了，先 `DROP FUNCTION`）。**换了库**（新建一个库、迁移好再切过去）：角色是整个实例共用的，
还在；在新库里再执行一遍这份 SQL（`-v dbname=<新库> -d <新库>`），再把连接的 `database` 改成新库（即时生效）。

**撤销：**

```bash
# A：停掉并删除隧道；删掉主配置里的连接和三个工具、env 里的密码，重启工具服务
systemctl disable --now <隧道服务> && rm /etc/systemd/system/<隧道服务>.service /etc/default/<隧道服务> && systemctl daemon-reload
userdel <隧道账号> && rm -r <隧道账号的目录>
systemctl restart ops-readonly
# B：删转发账号（家目录归 root，userdel -r 不会删它）；在执行过 SQL 的每个库里删函数和授权，最后删角色
rm -r /home/<转发账号> && userdel <转发账号>
docker exec -i <Postgres 容器> psql -X -v ON_ERROR_STOP=1 -U <超级用户> -d <库名> <<'EOF'
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE usename = 'doc2sop_ro';
DROP SCHEMA doc2sop CASCADE;
DROP OWNED BY doc2sop_ro, doc2sop_definer;
DROP ROLE doc2sop_ro;
DROP ROLE doc2sop_definer;
EOF
```

## K8s 只读账号

工具服务查 K8s（kubectl 版的 `kube_*`，或 K8s API 模板）要用**只读的 ServiceAccount**，不用集群管理员的 kubeconfig：
凭据落在工具服务那台机器上，管理员证书一旦泄露就是整个集群。[`deploy/k8s-readonly.yaml`](../deploy/k8s-readonly.yaml) 是现成的 RBAC：

| 对象 | 作用 |
|---|---|
| 命名空间 `doc2sop`、ServiceAccount `ops-readonly` | 身份；`automountServiceAccountToken: false`，不挂进任何 Pod |
| ClusterRoleBinding → 内置的 `view` | 各命名空间里常见资源只读：Pod、Service、Ingress、EndpointSlice、事件、Pod 日志……**读不了 Secret**，也看不到 Role / RoleBinding |
| ClusterRole `doc2sop-ops-readonly-extra` | `view` 不含的集群级只读：节点、PV、StorageClass、IngressClass、CRD、Lease、Gateway API 各资源；Higress 的 WasmPlugin 只给 `list` |

WasmPlugin 只给 `list`：巡检 SOP 用 `kube_list`（`-o wide` 只出几列）看插件在不在、启没启用就够了；不给 `get`，`kube_yaml`、`kube_describe`
就读不到插件配置——那里面常有第三方服务的 key。集群里还有别的 CRD 要查，照样往 `extra` 里加；里面有凭据的资源只给 `list` 或干脆不给。

```bash
kubectl apply -f /opt/doc2sop/deploy/k8s-readonly.yaml          # 用管理员身份，在能管集群的机器上
kubectl auth can-i get secrets -A --as=system:serviceaccount:doc2sop:ops-readonly    # no
kubectl auth can-i list pods -A --as=system:serviceaccount:doc2sop:ops-readonly      # yes
```

**kubectl 版**（`deploy/ops_tools.yaml` 里的 `kube_*`）：签一个令牌，写一份只含它的 kubeconfig，`KUBECONFIG` 指过去：

```bash
umask 077
SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
CA=$(kubectl config view --minify --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}')
TOKEN=$(kubectl -n doc2sop create token ops-readonly --duration=2160h)       # 90 天
cat > /etc/ops-readonly/kubeconfig-readonly <<EOF
apiVersion: v1
kind: Config
clusters: [{name: cluster, cluster: {server: $SERVER, certificate-authority-data: $CA}}]
users: [{name: ops-readonly, user: {token: $TOKEN}}]
contexts: [{name: ops-readonly, context: {cluster: cluster, user: ops-readonly}}]
current-context: ops-readonly
EOF
unset TOKEN
cp -a /etc/ops-readonly.env /etc/ops-readonly.env.bak-$(date +%Y%m%d%H%M%S)
sed -i 's#^KUBECONFIG=.*#KUBECONFIG=/etc/ops-readonly/kubeconfig-readonly#' /etc/ops-readonly.env    # 没有这一行就追加
systemctl restart ops-readonly
```

管理员的 kubeconfig 不要留在工具服务读得到的地方（`/etc/ops-readonly/` 下原来那份移走）。

**页面上加**（不用登录服务器）：别的集群用同一套只读账号，在「工具 → 主机与数据源 → K8s 集群」里贴上面打印出的 kubeconfig，
或者逐项填地址、CA、令牌（要审批口令）；kubectl 工具多一个参数 `cluster` 选它。见上文「页面上配置主机与数据源」。

**API 模板**（[`deploy/templates/k8s-api.yaml`](../deploy/templates/k8s-api.yaml)）不需要 kubectl：令牌和 CA 各放一个文件，连接里用 `bearer_file`、`ca`：

```bash
umask 077
kubectl -n doc2sop create token ops-readonly --duration=2160h > /etc/ops-readonly/k8s-token
kubectl config view --minify --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d > /etc/ops-readonly/k8s-ca.pem
```

```yaml
connections:
  - {name: k8s, type: http, base: "https://127.0.0.1:6443", ca: /etc/ops-readonly/k8s-ca.pem, bearer_file: /etc/ops-readonly/k8s-token}
include: [/opt/doc2sop/deploy/templates/k8s-api.yaml]
```

- **续期**：令牌 90 天过期（`--duration` 还受 apiserver 的 `--service-account-max-token-expiration` 限制）。到期前重新签一个换上：
  kubectl 每次调用都现读 kubeconfig，`bearer_file` 也是每次现读，所以两种都只要在 `umask 077` 下写个临时文件再 `mv` 盖过去，不用重启。
  过期了 K8s 工具报 `Unauthorized`，别的工具不受影响。看还剩多久：令牌是 JWT，第二段 base64 解码后的 `exp`。
- **撤销**：`kubectl delete -f /opt/doc2sop/deploy/k8s-readonly.yaml`——ServiceAccount 一删，它签出的令牌立即失效。
- **退回**原来的 kubeconfig：把 `/etc/ops-readonly.env` 换回改之前的备份，`systemctl restart ops-readonly`。

## 和演示形态并存

同一台机器上可以再跑一套 compose 演示站（比如给人看最新 main）：在另一个目录 clone，那份 `.env` 里设
`APP_CONTAINER=demo-app OPS_CONTAINER=demo-ops APP_IMAGE=demo-app:latest OPS_IMAGE=demo-ops:latest APP_PORT=8766 APP_MEM_LIMIT=700m`
（演示主机还可以设 `HOST_CONTAINER=demo-host HOST_IMAGE=demo-host:latest`），
`LLM_BASE_URL` 指向宿主机上的网关时写 `http://host.docker.internal:14000/v1`（compose 里两个服务都带了 `host.docker.internal`），然后 `docker compose --profile demo up -d --build`。
容器名、镜像名、网络、卷互不干扰；正式站继续由 `release.sh` 管。演示主机（kb-host）只跑在演示站的 compose 网络里，不发布端口，碰不到正式站。

## 常见问题

| 现象 | 处理 |
|---|---|
| 第一次发版很慢 | 在构建 `kb-app:base-<哈希>`，2 核机器约 10 分钟；只发生在首次和 `requirements.txt` / base 阶段变化时。构建在切换之前，服务不中断 |
| `docker build` 拉不到 `python:3.12-slim` | 设 `BASE_IMAGE=docker.m.daocloud.io/library/python:3.12-slim`（本地已有该镜像则不会去拉） |
| pip 卡住 | 设 `PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple`；换源会改变哈希，重建一次 base |
| 脚本说「片段总数不一致」并回滚了 | 新版本启动后向量库读不到或读到的和之前不一样——看它打印的新容器日志；常见原因是 `DATA_DIR` 指错、`.env` 里换了 `EMBED_MODEL`（换向量模型会触发重建索引） |
| 脚本说已存在 `kb-app-prev` | 上次发版中途被打断。当前 `kb-app` 正常就 `docker rm -f kb-app-prev`；想回到旧的就 `docker rm -f kb-app && docker rename kb-app-prev kb-app && docker start kb-app` |
| 想看生产跑的是哪个提交 | `docker inspect kb-app --format '{{index .Config.Labels "doc2sop.commit"}}'` |
| 沙箱服务起不来 | `journalctl -u doc2sop-sandbox -n 20`：「没有注册 runsc」是第 1 步没做完或 reload 没生效；「本机没有镜像」就按第 2 步构建 |
| 模型说「计算沙箱不可用：沙箱正忙」 | 同时有别的执行在跑、排队也没轮到；偶发正常，经常出现再考虑 `SANDBOX_CONCURRENCY=2`（内存够的话） |
| 页面上申请、启停、批准工具报「Read-only file system」 | 工具服务的 systemd 单元里有 `ProtectSystem=strict` 却没有 `ReadWritePaths=/opt/ops`（老版本的模板就是这样）：补上这一行，`systemctl daemon-reload && systemctl restart ops-readonly` |
| 页面上设置审批口令报「写不了口令文件」 | 同上，口令文件的目录不在 `ReadWritePaths` 里，或者目录还没建：`install -d -m 700 /etc/ops-readonly`，`ReadWritePaths` 改成 `/opt/ops -/etc/ops-readonly`，再 `daemon-reload` 和 `restart`。等不及就在宿主机上用 `set-approval-passphrase` 设 |
