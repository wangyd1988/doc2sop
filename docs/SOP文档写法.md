# 怎么写一份能抽出 SOP 的文档

「从文档抽取 SOP」做的事很简单：模型读你的文档，把里面**按步骤查看、核对**的做法，
翻译成对现有工具的一串有序调用。文档写得越像一份操作清单，抽出来的 SOP 就越准。

这份指南讲清楚：抽取器在找什么、文档该怎么写、抽不出来时怎么办。

---

## 一、先搞清楚抽取器在找什么

抽取时模型拿到两样东西：**你的文档** 和 **当前可用的工具清单**（就是页面 🔧 工具面板里启用且可运行的那些）。
它的任务是输出最多 3 个 SOP，每个最多 6 步，每一步是：

```
用哪个工具 → 传什么参数 → 这一步看什么、怎么判断
```

所以文档里每一个「步骤」，模型都要回答三个问题：

| 模型要回答的问题 | 文档里对应的内容 | 没写会怎样 |
|---|---|---|
| 用哪个工具？ | 这一步**看什么**（磁盘、内存、容器列表、节假日…） | 匹配不到工具，这一步被丢掉 |
| 传什么参数？ | 看的是**哪个对象**（哪个容器、哪一年、哪个日期） | 留空，使用时由用户补 |
| 怎么判断？ | **阈值、标准、异常的样子** | 检查点变成空话「检查是否正常」 |

**抽取器只认「只读」的步骤**。文档里「重启容器」「清理日志」「扩容」这类操作会被直接忽略——
所有工具都是只读的，SOP 只能编排查看和核对。这是设计上的边界，不是缺陷。

还有两个硬限制：

- **只读文档前 6000 字**（约 3～4 页 A4）。步骤要放在前面，背景介绍放后面或另起一篇。
- **一篇文档最多抽 3 个 SOP，每个最多 6 步**。一份文档只写一件事，别把整本手册塞进一篇。

## 二、推荐结构

```markdown
# 标题：写清楚是「做什么」的规范/手册            ← 变成 SOP 名称的依据

一两句话：适用范围、什么时候做、只看不改。       ← 变成 trigger（什么时候用）

## 步骤

### 1. 看什么（名词）
一句话说明查看什么。
- 判断标准 1（带数字或明确状态）
- 判断标准 2

### 2. 看什么
...

## 结论格式（可选）
怎么汇总、分几级。
```

对照 `sample_kb/日常巡检规范.md`，它抽出来的结果是：

| 文档里 | 抽出的 SOP |
|---|---|
| 标题「单机 Docker 服务日常巡检规范」 | 名称「每日资源巡检」 |
| 「每天上班后执行一次」 | trigger：用户要求做日常巡检 |
| 「### 1. 宿主机磁盘 / 查看各挂载点使用率」 | tool: `host_disk` |
| 「根分区使用率超过 80% 记为告警，超过 90% 记为严重」 | checkpoint：根分区使用率 >80% 告警，>90% 严重 |
| 「### 4. 容器运行状态 / 列出所有容器」 | tool: `list_containers` |
| 「状态不是 running 的业务容器，记为严重」 | checkpoint：有非 running 的业务容器即严重 |

阈值是**原样**写进去的。你在文档里写得多具体，Agent 执行时判断就多具体。

## 三、六条写法规则

### 1. 一步一个「看什么」，用名词

每个小节标题就是这一步查看的对象。好的标题：`宿主机磁盘`、`当年节假日安排`、`可用模型列表`。
不好的标题：`准备工作`、`注意事项`、`第一阶段`——模型不知道该调哪个工具。

### 2. 每步必须有判断标准，带数字或明确状态

```
✅ 可用内存低于总量 15% 记为告警
✅ 状态不是 running 的业务容器，记为严重
✅ 返回的模型列表里没有你要调的模型名，说明这把 key 没被授权
✅ 当天是法定节假日或周末，不计入请假天数

❌ 检查内存是否充足
❌ 确认容器状态正常
❌ 看看模型对不对
```

没有标准的步骤抽出来也是空话，Agent 执行完不知道算过还是没过。

### 3. 先写步骤，再写背景

模型只读前 6000 字。「为什么要巡检」「历史事故回顾」「名词解释」放到步骤之后，或者单独成篇。
一个简单的判断：**打开文档第一屏，能不能直接看到「### 1.」**。

### 4. 写「看什么」，不写「敲什么命令」

```
✅ 查看各挂载点使用率
❌ 执行 df -h 查看磁盘
```

两种写法模型都能理解，但写命令有两个问题：一是命令和工具不一定对得上（工具可能是脚本或接口），
二是抽取器会**无视**任何命令行——它只能引用工具，不能定义命令。写清楚意图，让它去匹配工具。

### 5. 具体对象留给使用时填

文档里写「查看目标容器的日志」，而不是写死「查看 nginx 容器的日志」。
抽取器会把容器名这类参数留空，使用时由用户在提问里说明（「帮我排查 kb-app 容器」）。
如果某个值永远固定（比如固定查根分区），直接写进去，它会变成固定参数。

### 6. 只写查看和核对，操作另写

一份排障手册通常是「查 → 判断 → 处理」。前两段抽成 SOP，「处理」段模型会跳过。
建议在文档里把处理步骤单独放一节（例如「## 处理方式」），一来阅读清晰，
二来 Agent 回答时会把这一节作为知识库引用给用户看，而不是试图去执行。

## 四、三个岗位的写法示例

### 运维：排障手册

```markdown
# 容器反复重启排查手册

适用于单台 Docker 主机上某个容器状态出现 Restarting 的情况。排查只看不改。

## 排查步骤

### 1. 容器当前状态
查看目标容器的运行状态和重启次数。
- 重启次数在 5 分钟内超过 3 次，确认属于反复重启。

### 2. 容器最近日志
查看目标容器最近 100 行日志。
- 出现 OOMKilled / Killed，转第 3 步。
- 出现 connection refused / timeout，转第 4 步。
- 出现配置文件相关报错（config / parse / invalid），记为配置问题。

### 3. 容器内存占用
查看目标容器的内存上限和当前占用。
- 占用接近上限（>90%）说明是内存不足，需评估调大上限。

### 4. 宿主机端口占用
查看宿主机监听端口。
- 容器依赖的端口没有被监听，说明依赖服务没起来。

## 处理方式
（这一节不会被抽成 SOP，供人阅读）
- 内存不足：调整 compose 文件里的 mem_limit 后重新拉起。
- ...
```

### 研发：自查流程

```markdown
# 大模型调用失败自查

适用于通过网关调用模型时报错或无返回。先自查再找管理员。

## 自查步骤

### 1. 这把 key 可用的模型
查看当前 key 在网关上可用的模型列表。
- 列表里没有你调用的模型名，说明没被授权，直接找管理员加权限，后面不用查了。

### 2. key 的额度与限流
查看当前 key 的配额信息。
- 已用额度达到上限，或每分钟请求数超过限制，就是被限流。

### 3. 网关健康状态
查看网关整体健康状态。
- 上游不健康的模型会列出来，你调的模型在里面，就是上游故障，等恢复。
```

### 行政人事：核对流程

```markdown
# 请假拼假核对

员工请假前，先核对节假日和补班安排，算清实际占用的年假天数。

## 核对步骤

### 1. 当年节假日与补班安排
查看目标年份的法定节假日和调休补班日期。
- 请假区间内的法定节假日不计入请假天数。
- 调休补班日属于工作日，要计入。

### 2. 请假区间逐日核对
对请假区间内每一天确认星期几、是否工作日。
- 周末且非补班日不计入。
- 最终请假天数 = 区间内工作日数。
```

## 五、抽取后该做什么

抽出来的 SOP **默认停用**，需要人确认后再启用。确认时看三点：

1. **步骤顺序对不对**——模型偶尔会把文档里的并列步骤排成先后。
2. **工具选得对不对**——点开每一步，看工具名和你文档里「看什么」是否一致。
3. **检查点是不是你文档里的标准**——阈值数字被改了、被省略了，手动改回来。

页面上可以直接编辑名称、触发条件、每步的工具/参数/检查点，也可以增删步骤。
改完启用，然后在对话里按 trigger 的描述问一句，看 Agent 是不是按这个顺序调的工具。

## 六、抽不出来 / 抽得不对，怎么办

| 页面提示 | 原因 | 怎么改 |
|---|---|---|
| 这篇文档里没有能用现有工具按步骤查看、核对的做法 | 文档是概念介绍、规章制度、纯规则罗列，没有「步骤」 | 增加「## 步骤」一节，按「看什么 + 怎么判断」逐条写 |
| 这篇文档里的步骤需要当前没有的工具：xxx | 文档写的查看对象，目前没有对应工具 | 先在 🔧 工具面板申请新工具并由管理员批准，再抽取；或改写文档只用现有能力 |
| 已跳过需要以下工具的步骤：xxx | 部分步骤没有工具，其余已抽出 | 同上，缺的步骤批准工具后手动补进 SOP |
| 模型返回的内容无法解析 / 没有返回内容 | 模型输出不稳定（推理型模型思考过长） | 直接重试一次；仍失败可缩短文档、减少步骤数 |
| 抽出来了，但检查点写成「检查是否正常」 | 文档里没写判断标准 | 给每一步补上阈值或明确状态 |
| 抽出来了，但步骤顺序乱 | 文档用并列小节而非编号 | 小节标题加「1. 2. 3.」编号，并写明「转第 N 步」之类的流转 |
| 抽出来的 SOP 太多或混在一起 | 一篇文档写了多件事 | 一件事一篇，或用一级标题明确分开，每个一级标题下独立编号 |
| 后半部分的步骤没抽到 | 超过 6000 字被截断 | 步骤前移，背景后置，或拆篇 |

## 七、一分钟自查清单

上传前对着文档过一遍：

- [ ] 标题说清楚是「做什么」的规范/手册
- [ ] 开头一两句话写明什么时候用
- [ ] 第一屏就能看到带编号的步骤
- [ ] 每步标题是「看什么」的名词
- [ ] 每步至少一条带数字或明确状态的判断标准
- [ ] 没有「执行 xxx 命令」，写的是意图
- [ ] 具体对象（容器名/年份/日期）没写死，除非永远固定
- [ ] 修改、重启、删除类操作放在单独一节
- [ ] 步骤部分不超过 6 步、全文不超过 3～4 页
- [ ] 文档里提到要看的东西，🔧 工具面板里都有对应工具
