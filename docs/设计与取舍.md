## 多轮记忆：LangGraph 检查点

大模型本身不记事，「记忆」就是每次把历史重新发给它。关键在于存什么：

| | 只存最终回答（旧做法） | LangGraph 检查点（现在） |
|---|---|---|
| 保存内容 | 每轮回答的文字 | 整轮过程：工具调用、工具原始结果、搜索结果、回答 |
| 追问时 | 只能用回答里恰好写到的信息 | 能用当时查到的全部数据，不必重查 |

```
第 1 轮：kb-app 重启次数？只回答数字   → 调 container_inspect，回答「0」
第 2 轮：它挂载了哪些目录？网络模式？   → 不再调工具，直接用第 1 轮的原始结果
                                          「/opt/kb-app/data → /data，网络 host」
```

- 每个会话是一个 thread，存在 `data/agent_memory.db`（SqliteSaver）；删除会话时一并清除
- 知识库片段只在本轮临时拼进问题，**不写入记忆**，历史不会越滚越大
- 回放给模型时只带最近 4 轮，较早轮次的工具结果截断到 1500 字；记忆里保留完整结果（单条上限 8000 字）
- 每轮结束只保留最新检查点；中途中断留下的「有调用没结果」会在回放前清理，避免模型接口报错
- 升级前的老会话没有检查点，首次追问时用文字历史自动补种

`conversations.py`（chat.db）继续负责会话列表和界面回放，两者各管一摊。

## 知识库答不了时：判断 + 联网搜索（可选）

向量检索总会返回「最像」的几段，哪怕它们和问题毫不相干。更麻烦的是**相似度分数靠不住**——
实测中，问「下季度团建预算」召回了一段项目研发预算，相似度 0.545；问 Python 新特性召回了测试手册，0.555；
而真正相关的《休假管理制度》也才 0.631。用分数阈值区分不开，模型照着这些片段作答就会张冠李戴。

所以这里不靠阈值，而是让模型**看内容判断**片段是否真的回答了问题（相似度一并给它作参考）：

| 判断 | 怎么做 | 回答里怎么标 |
|---|---|---|
| 知识库能完整回答 | 只用知识库 | `[1]` `[2]` |
| 只能回答一部分 / 完全不相关 | 调用 `web_search` 补充 | `[W1]` `[W2]`，界面单独显示带链接的 🌐 卡片 |
| 问的是公司内部信息 | **不上网**，说明知识库里没有 | |
| 要的是真实数据 | 用对应工具，不上网 | |
| 联网关闭 / 网上也没有 | 直说没有；**也不用模型自己的训练知识凑答案** | |

搜索走 LiteLLM 网关的 `/v1/search`，所以内网只要能访问网关就能搜，搜索服务的 key 只放在网关上：

```yaml
# 网关 config.yaml：两个 key 同名即自动分流
search_tools:
  - search_tool_name: web-search
    litellm_params: {search_provider: tavily, api_key: os.environ/TAVILY_API_KEY}
```

```bash
# 应用 .env
WEB_SEARCH_TOOL=web-search
WEB_SEARCH_BLOCKLIST=内部项目名,内部系统名      # 这些词永远不会发往搜索引擎
```

**内部信息发不出去，靠代码而不只靠提示词**：搜索词里出现 IP、疑似密钥或令牌、邮箱、内网域名，
或命中 `WEB_SEARCH_BLOCKLIST`，请求在发出前就被拒绝。网页内容一律标注为「未经核实」，
其中的任何指令都被忽略；与知识库冲突时以知识库为准。每个问题最多搜索 2 次。
页面输入框旁有「🌐 联网」开关，**默认开启**，关掉后浏览器会记住。能默认开，是因为「发不发」不靠这个开关把关：
上面那套代码层拦截始终生效，知识库能答的也不会去搜。首次见到开着的开关会弹一次说明。
直接调 `/api/ask` 时 `web` 默认 `false`——程序调用不该默认外发任何东西，需要时显式传 `true`。

评测脚本默认**关闭**联网（搜索结果会随时间变化，数字无法复现），需要时加 `--web`。

### 搜到的答案可以存回知识库

联网回答下方有「📥 存入知识库」按钮。点开是一个**可编辑的预览**，人确认内容无误后才入库：

```
第一次问 PostgreSQL VACUUM 的区别：知识库最高相似度 0.49 → 联网搜索 → 回答
点「存入知识库」：生成《网络补充-…》文档，10 个片段
第二次问同一问题：知识库最高相似度 0.86 → 不再联网，直接从知识库回答
```

- **只能由人点按钮触发**，模型自己不能往知识库里写——否则一次被网页带偏的回答就会变成「团队知识」
- 存入的文档带「来源：网络搜索，某日由某人确认」的说明和原始链接，归到「网络补充」分类，删除方式与普通文档相同
- 回答里指向其他文档的 `[1]` 引用、开头那句「知识库里没有找到」会自动去掉，避免存进去后变成错误信息

## 页面上选模型

顶栏的模型下拉框列出**这把 key 在网关上有权使用的聊天模型**（来自网关 `/v1/models`，缓存 60 秒，向量模型不显示），也可以手动输入模型名。选择只影响回答模型；改写问题、分类、抽取 SOP 仍用默认模型。每条回答下面标注用的是哪个模型，历史回放也保留。

服务端会校验：不在列表里的模型名直接返回 400，不会发给网关，也不会留下会话记录。

### 管理页 · 模型设置

`/manage` → 模型设置：网关地址、API key、对话模型、向量模型、图片识别模型。`.env` 是启动默认值，页面保存的值覆盖它并立刻生效（客户端热重建，不重启）。

- **API key 只写不读**：页面只能填新 key，读回来的永远是 `••••••••末4位`；存于 `data/settings.json`，权限 600
- **测试连接**：保存前先试——列出这把 key 能用的模型、调一次对话模型、算一次向量并给出维度；维度和现有索引不一致会提示
- **换向量模型必须重建索引**：不同模型的向量不能比较，Chroma 也不接受维度不同的向量。保存时会拦下并要求勾选「同时重建索引」；重建从保存的原文件重新解析、向量化（图片识别走缓存），后台任务，页面显示进度
- **恢复 .env**：一键删掉页面上的全部覆盖
- **没有网关也行**：对话模型和向量模型可以来自不同厂商——「向量模型地址 / Key」留空就跟对话模型共用，填了就各走各的（例如对话用 DeepSeek 官方、向量用硅基流动的 bge-m3）。直连厂商通常没有 `/v1/models`，测试连接会提示「列不出模型」但不算失败；联网搜索依赖 LiteLLM 的 `/v1/search`，直连时不可用

**这和「凭据不进页面」矛盾吗？** 不矛盾，但要分清两种凭据：模型网关的 key 决定**数据发给谁**——问题、片段、图片本来就会发出去，这是产品设置，Dify / MaxKB 也都在后台配；工具凭据（`OPS_TOKEN`、`OPS_SECRET_*`）决定**宿主机执行什么**，那条线仍然只在宿主机，页面碰不到。

## 设计决策

**手写文档解析，而不是用现成 Loader。** 标准加载器会丢掉内嵌图片、演讲者备注、组合图形
和表格顺序，而这些是真实笔记里信息密度最高的部分。代价是解析逻辑要自己维护。

**Agent 的作用是路由和取数，不是让检索变聪明。** 早期版本是固定的「检索 → 生成」，因为只有一个数据源。
接入只读工具后，模型需要决定「这个问题要不要查真实数据、查哪个」，这才有了 LangGraph 的模型 ⇄ 工具循环。
只问规则的问题仍然不调工具，延迟和纯 RAG 一样。

**混合检索用 RRF 融合，而不是加权打分。** 向量相似度和 BM25 分数量纲不同，直接加权要调参；
倒数排名融合只看名次，两路都靠前的自然排最前。关键词路额外设了准入门槛（命中英文标识符、或余弦 ≥ 0.40），
否则「有几」「区别」这类常见双字会把无关片段带进来。

**重排只看前 8 条、每段前 256 token。** 交叉编码器要把问题和每段拼在一起过一遍模型，耗时与 token 数成正比，base 规格在 2 vCPU 上约 0.25 s/段：
8 条经网关 ≈ 1.7 s；看全文 512 token、30 条要 10 s 以上。判断「相关不相关」看前 250 来个 token 足够。融合排序已经把真正相关的大多放进了前 12，重排负责把它们排对、
并给出一个可信的「相关/无关」信号。量化版（int8，280 MB）跑在网关那台机器上；最初放在向量模型那台「经济型」实例上，
1.4 s/段，不可用。整条链路是 best-effort：重排超时或出错就退回融合排序，回答不会因此失败。

**BM25 不用分词词典。** 英文/数字串整体成一个词，中文按字二元组。对精确词匹配够用，零依赖、索引内存里重建不到一秒。

**片段 ID 按文件名生成，不按内容哈希。** 否则两个内容相同、文件名不同的文档会互相覆盖，
先上传的那份会静默消失（这个缺陷是写回归测试时发现的）。

**不默认下发 `reasoning_effort`。** 实测部分网关对该参数的处理是把思考内容并入正文，
导致回答开头出现大段英文推理。只在确认模型支持时才开启。

**相似度低于阈值的片段直接丢弃。** 否则打招呼这类闲聊也会召回一堆无关内容塞进上下文。
但阈值只用来去掉明显无关的（0.25），「相关不相关」交给模型看内容判断——实测无关片段 0.55、相关片段 0.63，阈值分不开。

**长工具输出先压缩再给模型。** 几千行日志大多重复，保留头 30 行、尾 30 行和含告警/错误关键字的行，
中间用「省略 N 行」标记。页面预览不受影响。

## 性能

通过 LangSmith 实测，单次提问的耗时构成：

| 环节 | 占比 |
|---|---|
| 问题改写 | 首轮跳过，多轮约 2 s |
| 向量化 + 检索 | < 10% |
| **模型生成** | **> 85%** |

结论：**瓶颈在模型，不在检索。** 把 `TOP_K` 从 8 调到 6 只能省不到 0.1 秒，
换掉会长时间「思考」的推理模型则让平均耗时从 33 s 降到 8 s。

向量检索本身对数据量不敏感——Chroma 用 HNSW 索引，实测 2 千条和 2 万条的检索耗时在同一量级。
真正的规模限制是内存：索引需常驻，2 GB 机器大约可容纳 5–10 万片段。

## 评测

两套评测集，方法与脚本见 [`eval/README.md`](../eval/README.md)。

**公开可复现**——上传 `sample_kb/` 下 6 篇示例文档即可得到相同结果：

```bash
python eval/run_eval.py --user admin --password '...' \
  --judge-model kb-chat --judge-base-url http://127.0.0.1:4000/v1 --judge-api-key "$LLM_API_KEY"
```

| 指标 | 结果 |
|---|---|
| 召回命中率 | 100%（19 条） |
| 要点覆盖率 | 100%（19 条） |
| 拒答正确率 | 100%（2 条） |
| 首字 P50 / P95 | 2.2s / 14.8s |

> 这组数字只能算冒烟测试：示例语料仅 16 个片段，而 `TOP_K=8`，等于每次检索都返回了半个知识库，
> 召回率必然满分。它验证的是链路正确性，不是检索质量。

**真实语料**——51 份技术文档、4969 个片段，同一套脚本、20 条同样结构的题目（题目与语料未公开）：

| 指标 | 结果 |
|---|---|
| 召回命中率 | **89%**（18 条） |
| 要点覆盖率 | **79%**（18 条） |
| 拒答正确率 | **100%**（2 条） |
| 首字 P50 / P95 | 4.6s / 17.2s |

分类型来看：概念题 93%、事实题 78%、跨文档题 62%。

**两个失败案例恰好印证了下面「已知不足」里写的问题**：问到具体配置字段名和具体服务名时，
检索召回了主题相近但内容无关的文档——这正是纯向量检索对专有名词不敏感的典型表现，
也是优先级最高的改进项。

## 已知不足

- **跨文档综合能力偏弱。** 真实语料上 `multi_hop` 类题目要点覆盖率 62%，明显低于概念题的 93%。
- **图片识别结果缓存不随文档删除。** 删除文档会清掉片段和原文件，但 OCR 缓存仍保留。
- **仅 HTTP Basic 鉴权，单账号。** 「查我自己的 key」「按岗位看到不同工具」都需要先接统一登录。
- **后台任务在内存里。** 服务重启时正在入库的文件会丢任务，需要重新上传（数据不会半写：入库最后一步才替换）。
- **可观测依赖 LangSmith（外部服务）。** 自托管 Langfuse 需要 Postgres + ClickHouse，2C2G 放不下；
  替代路径是在 LiteLLM 网关侧开 Langfuse 回调，待网关机器扩容后再做。
