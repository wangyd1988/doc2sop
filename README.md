# 小知 · 把团队文档变成 SOP 的工作助手

把团队的文档变成可提问的知识库；再让 Agent 照着文档里写的做法，**用你批准过的只读工具去查真实数据**，
对照后给出结论。不限岗位：运维查容器、研发查模型网关、行政人事查节假日，换一批工具就是换一个场景。

基于 LangChain 组件构建，跑在三台 2 核小规格云主机上，不需要 GPU。

---

## 它解决什么问题

1. **规则在文档里，数据在系统里，中间要靠人去对照。** 制度、手册、规范写得很细，
   真正用的时候还得自己翻文档、查系统、再比对——最费时间，也最容易出错。
2. **想让 AI 动手，又怕它乱动。** 给 Agent 任意执行权限太危险；只让它查文档，它又看不到真实情况。

这套系统的做法是：

- **知识库**：文档切块建向量索引，提问时按语义召回，模型**只依据这些片段**回答，每句结论都能点开看原文；
- **SOP**：从文档里自动抽出「按步骤查看、核对」的做法；
- **工具**：Agent 按 SOP 调用只读工具取真实数据，但工具只能由管理员定义和批准。

## 三个示例场景

| 场景 | 知识库里放 | 工具查什么 | 一句话提问 |
|---|---|---|---|
| 运维 | 《日常巡检规范》 | 磁盘、内存、负载、容器状态 | 「帮我做一次日常巡检」 |
| 研发 / 任何调模型的人 | 《大模型网关使用说明》 | 网关健康、可用模型、key 额度与限流 | 「我调 gpt-4o 报 404 是怎么回事」 |
| 行政 / 人事 / 全员 | 《休假管理制度》 | 法定节假日与补班安排、日期是星期几 | 「国庆想连休到 10 月 11 日要请几天年假」 |

三份文档都在 [`sample_kb/`](sample_kb/)，均为通用示例内容。

## 功能

| | |
|---|---|
| 多格式入库 | PDF / Word / PPT / Markdown / 纯文本 / 图片；**后台入库**，页面实时显示「识别图片 3/12 → 向量化 → 写入」 |
| 图片识别 | 文档内嵌的截图、架构图经多模态模型识别后**插回原文位置**，一并可检索 |
| **混合检索** | **向量 + BM25 关键词两路召回、RRF 融合：字段名、错误码、型号这类精确词也能找到；关键词命中的片段带「关键词」标记** |
| 多轮对话 | 追问时自动补全指代（「那它的上限呢」→ 补成完整问题再检索）；Agent 用 LangGraph 检查点记住**整轮过程**，追问能直接用上一轮工具和搜索返回的原始数据 |
| **查询真实数据** | **可选开启只读工具：命令、脚本、HTTP 接口三种，Agent 自行判断要不要查，并与知识库对照；调用卡片可展开看参数与返回，历史回放也保留** |
| **联网补充** | **模型判断知识库片段是否真的相关，答不了时经网关上网搜索；内部信息在代码层拦截，不会外发；搜到的答案经人确认可一键存回知识库，再次检索到时标注「网络补充」。默认关闭** |
| **SOP** | **从上传的文档里自动整理出「按步骤查看、核对」的标准作业流程，每步附文档原句供核对；页面可编排启停、一键「▶ 执行」；执行结果固定为「步骤 / 查看 / 实际数据 / 结论」表格** |
| **工具管理** | **页面查看、分组、搜索、启停、改名改说明；新增工具走宿主机审批，改完不用重启** |
| 选模型 | 顶栏下拉列出这把 key 有权用的模型，回答与回放标注所用模型；**管理页「模型设置」可改网关地址、API key（只写不读）、对话/向量/图片模型，保存即生效；换向量模型自动重建索引** |
| 来源可核对 | 回答中的 `[1]` 可点开，显示原文片段、来源文件、PDF 页码和相似度；未被引用的候选片段折叠 |
| 自动分类 | 上传时模型建议分类，可手工覆盖，侧栏按分类分组 |
| 原文下载 | 随时取回当初上传的原始文件 |
| 全链路追踪 | 接入 LangSmith，每次提问的各环节耗时与输入输出自动记录 |
| 备份 | `deploy/backup.sh`：SQLite 在线一致性复制 + 向量库 + 原件 + 工具配置打包，cron 每日一份、保留 7 天 |

## 知识库、SOP、工具三者的关系

```
📄 知识库（文档）          📋 SOP（步骤）              🔧 工具（执行）
《休假管理制度》         →  1. 查当年节假日     ───────→  holiday_calendar
  先查节假日和补班、         2. 逐日确认星期几   ───────→  date_info
  再逐日看是不是工作日……     3. 算要请几天                   
  人看的文字                 自动抽取、页面可调           管理员审过的只读能力
```

| | 来源 | 回答什么 | 谁能改 |
|---|---|---|---|
| 知识库 | 你上传的文档 | 规定是什么、应该怎么做 | 任何能上传文档的人 |
| SOP | 从文档自动抽取 | 按什么顺序、调哪个工具、每步看什么 | 页面可编辑、启停 |
| 工具 | 宿主机配置 | 实际执行哪条命令、调哪个接口 | 只有宿主机管理员 |

SOP 不限于某个岗位：故障排查、日常巡检、模型调用自查、请假拼假核对，凡是**按步骤查看、核对**的
做法都能从文档里学到。一句话：**Agent 读完你的文档就能照着 SOP 办事，但它永远只能用你批准过的工具。**

文档怎么写才能抽得准（结构模板、六条规则、三个岗位示例、抽不出来的排查表），见 [`docs/SOP文档写法.md`](docs/SOP文档写法.md)。

## 查询真实数据（可选）

开启后，Agent 会把知识库和真实数据对照起来，而不只是复述文档：

```
用户：我调用 gpt-4o 报 404 模型不存在，怎么回事？

  ① 检索知识库    → 《大模型网关使用说明》：404 先核对模型名
  ② 按 SOP 调工具  → gateway_health → gateway_models → gateway_key_status
  ③ 对照后判断    → 网关健康、额度正常，但这把 key 的可用模型里没有 gpt-4o
  ④ 给出建议      → 改用 github_copilot/gpt-5.4（前缀必须带上），或走工单申请授权
```

```
用户：demo-svc 一直在重启，帮我看看

  ① 检索知识库    → 得知要看重启次数、内存上限、日志
  ② 调用只读工具  → list_containers / container_inspect / container_logs
  ③ 对照后判断    → 退出码 137 + 上限仅 12MB → OOM
  ④ 指出矛盾      → 「知识库说应为 900MB，实际 12MB，差 75 倍」
```

**Agent 拿不到 shell，也拿不到任何凭据。** 它只能提交工具名和结构化参数，由宿主机上的只读接口
映射到固定模板执行：

```
Agent（容器内，无宿主机权限）
  │  HTTP + 令牌，只传工具名与参数
  ▼
只读工具接口（宿主机，仅监听 127.0.0.1）
  │  正则白名单校验 → 固定 argv / 固定 URL 模板 → 写动词黑名单
  ▼
只读命令 · 哈希锁定的脚本 · 只读 HTTP 接口（凭据只在宿主机环境变量里）
```

启用方式：

```bash
# 宿主机
OPS_TOKEN=$(openssl rand -hex 16) python3 deploy/ops_readonly.py --port 8799

# .env 里填上，然后重建容器
OPS_URL=http://127.0.0.1:8799
OPS_TOKEN=<同一个令牌>
```

不配置 `OPS_URL` 时工具自动关闭，退化为纯知识库问答。注入防护与轮次上限均有测试覆盖
（`tests/test_agent.py`）。

### 加一个工具

工具定义只有一份，就是宿主机上的 [`deploy/ops_tools.yaml`](deploy/ops_tools.yaml)。
应用侧不保存任何工具清单，而是每次提问从接口拉取描述与参数，动态生成模型看到的函数签名。
所以**加工具只改这个文件，不用重启服务，也不用重建镜像**：

```yaml
  - name: host_uptime
    desc: 查看宿主机已经开机多久、当前 1/5/15 分钟平均负载。
    binary: uptime
    argv: [uptime]
    params: {}
```

保存后下一次提问就能用上。带参数的工具这样写：

```yaml
  - name: container_logs
    desc: 查看指定容器最近的日志，用于定位报错原因。
    binary: docker
    argv: [docker, logs, --tail, "{lines}", "{name}"]
    params:
      name:  {type: str, pattern: name, required: true, desc: 容器名}
      lines: {type: int, default: 100, max: 500, desc: 查看最近多少行}
```

配置本身就是安全边界，所以加载时强制校验，不合规的条目会被跳过并记录原因：

| 约束 | 为什么 |
|---|---|
| 参数必须整个占据一个 argv 项（`"{name}"`） | 不允许 `--tail={lines}` 这种拼接，参数值永远变不成新的命令片段 |
| 字符串参数只能引用预置正则 | 不能自带正则，否则一个 `.*` 就把白名单废了 |
| `argv[0]` 必须等于 `binary` | 防止用 `binary: docker` 过检查、实际去跑 `bash` |
| `binary` 不能是解释器 | `bash`/`sh`/`python`/`env`/`xargs`/`find`/`ssh` 等能执行任意命令，一律拒绝 |
| 模板里不得出现写动词 | 与运行时黑名单双保险 |
| 非必填的字符串必须有合法默认值 | 否则运行时会往 argv 里塞空串 |

其中「`binary` 不能是解释器」堵的是最致命的一类：`binary: bash, argv: [bash, -c, "任意命令"]`。
`-c` 后面整段是一个 argv 项，写动词黑名单按词匹配根本挡不住它。所以这类 binary 直接禁，
要跑一段逻辑请用下面的**脚本工具**。

写坏了也不会让服务失去全部工具——加载失败时沿用上一份可用定义。
`enabled: false` 可以下线某个工具，它会立刻从模型的可用列表里消失，引用它的 SOP 也会标红。

### 页面上能改什么，不能改什么

界面上的 **🔧 工具** 面板能看到每个工具的完整命令模板、参数和启停状态。
但页面能改的范围是一条刻意划清的安全边界：

| 操作 | 在页面上 | 为什么 |
|---|---|---|
| 查看命令模板与参数 | ✅ | 一眼看清 Agent 到底能执行什么 |
| 启用 / 停用 | ✅ 立即生效 | 这是**缩权**方向 |
| 改描述、改中文显示名 | ✅ 立即生效 | 只影响人和模型怎么理解，不改变执行的命令 |
| 改 `argv` / `binary` | ❌ | 等于让页面定义宿主机执行什么 |
| 新增命令工具 | ⚠️ 只能提交申请 | 需要人在宿主机上批准后才写入配置 |
| 新增接口工具 | ⚠️ 只能提交申请，且不能带凭据 | 需要鉴权的接口只能由管理员在配置文件里写 |
| 新增脚本工具 | ⚠️ 只能引用已有脚本 | 脚本内容只有宿主机能放，页面只能选，且哈希锁定 |

这个边界靠**文件分权**落实，而不是靠接口自觉：

```
ops_tools.yaml             root 手写，唯一能定义命令的地方，页面无权写
ops_tools.overrides.yaml   页面可写，加载时只认 enabled / desc / label 三个字段
ops_tools.pending.yaml     页面可写，待审队列，永远不参与加载
ops_tools.trust.yaml       脚本哈希表，只有宿主机批准/trust 时写，页面无权写
scripts/                   脚本目录，只有宿主机能放文件，页面只能引用
```

即使覆盖层文件被完全控制，写进 `argv: [cat, /etc/shadow]` 也会被直接忽略——
加载时只读那两个字段。最坏情况是工具被全部停用或描述被改乱，**提不了权**。

申请新工具后，在宿主机上审批：

```bash
python3 deploy/ops_readonly.py pending      # 列出申请，重点看「命令」那一行
python3 deploy/ops_readonly.py approve <id> # 批准后写入主配置，下次提问即可用
python3 deploy/ops_readonly.py reject <id>
```

申请在批准前**完全惰性**：模型看不到，也调用不了。提交时就会跑一遍和正式配置
同样的校验，所以写错的申请当场被拒，而不是等到审批才发现：

```
填 datetime → 本机没有 datetime 这个命令，你是不是想用 date？（相近的还有：time）
填 dfh      → 本机没有 dfh 这个命令，你是不是想用 df？
```

### 工具名为什么只能用英文
工具名会作为函数名发给模型，function calling 的规范只允许字母、数字、下划线，
中文名会被接口拒绝。所以多了一个 `label` 字段专门放中文：

```yaml
  - name: host_disk        # 发给模型的函数名，只能英文
    label: 磁盘用量         # 界面上显示的名字，随便写
    desc: 查看宿主机各挂载点的磁盘使用率。容器写日志失败、镜像拉不下来时先看这个。
    binary: df
    argv: [df, -h]
    params: {}
```

`label` 只用于界面，不会进入发给模型的工具定义——模型拿到的始终是
`{desc, params}`，和英文函数名。`label` 和 `desc` 一样可以在页面上直接改。

### 脚本工具：把一串只读命令固化成一个工具

有时一个判断要跑好几条命令（先列容器、再逐个查重启次数、再挑出异常的）。
与其让模型自己拼，不如写成一个脚本，让它成为一个工具。但「页面能定义脚本内容」
就等于「上传可执行代码」——文档投毒那套风险会原样回来。所以这里的规矩是：

- **脚本内容只能由宿主机管理员放进 `scripts/` 目录**，页面碰不到内容
- 页面和申请都只能**从已有脚本里选一个来引用**
- 批准时登记脚本的 **SHA-256**；加载和执行前各校验一次，**内容一旦被改就自动停用**

```yaml
  - name: container_health
    label: 容器体检
    desc: 一眼看懂所有容器的状态和重启次数
    script: container_health.sh   # 只能是 scripts 目录下的文件名，不能带路径
    params: {}
```

```bash
# 宿主机放脚本（必须 LF 换行、可执行）
cp container_health.sh /opt/ops/scripts/ && chmod +x /opt/ops/scripts/container_health.sh
python3 deploy/ops_readonly.py scripts            # 列出脚本与信任状态
python3 deploy/ops_readonly.py approve <id>       # 批准引用它的申请，顺带登记哈希
python3 deploy/ops_readonly.py trust <脚本名>     # 合法更新脚本内容后，重新登记哈希
```

这和「SOP 只能引用已有工具」是同一个思路：**能力（脚本/工具）由宿主机掌控，
页面只能编排与引用，永远扩不了权。**

### 接口型工具：查任何系统的只读接口

不是所有数据都在命令行里。模型网关的 key 额度、节假日安排、工单状态，通常是 HTTP 接口。
接口型工具和命令型同一个原则——**模型只能填空，改不了去哪儿、带什么凭据**：

```yaml
  - name: gateway_key_status
    label: Key 额度与限制
    group: 模型网关
    desc: 查看当前网关 key 的已花费、预算上限、到期时间、限流和允许的模型。
    http:
      url: "${OPS_SECRET_GATEWAY_URL}/key/info"            # 地址来自宿主机环境变量
      headers: {Authorization: "Bearer ${OPS_SECRET_GATEWAY_KEY}"}
      pick: [info.spend, info.max_budget, info.models]    # 只把这几个字段交给模型
    params: {}

  - name: holiday_calendar
    label: 法定节假日
    group: 日历
    desc: 查询某一年的法定节假日与补班安排。
    http:
      url: "https://cdn.jsdelivr.net/gh/NateScarlet/holiday-cn@master/{year}.json"
    params:
      year: {type: int, default: 2026, min: 2007, max: 2035}
```

| 约束 | 挡住什么 |
|---|---|
| 只允许 GET | 接口型工具只能查，不能改 |
| 主机名写死，参数进不了主机名 | 模型无法把请求导向别的地址 |
| 参数只能落在路径段或 query 的值里，整体 URL 编码 | `../admin?x=` 之类拼不出新路径 |
| 请求头只能由管理员写，模型参数进不了请求头 | 模型无法伪造身份 |
| 凭据只能引用 `${OPS_SECRET_*}` 环境变量 | 不会误把服务自身的 `OPS_TOKEN` 发出去 |
| 返回内容里出现的凭据会被替换成 `***` | 接口回显密钥也到不了模型 |
| 不跟随 3xx 跳转 | 不会被一次重定向带去别的主机 |
| `pick` 只挑需要的字段 | 无关的敏感字段不进模型上下文 |
| 页面申请的接口不能带请求头、不能引用环境变量 | 一条申请没法把宿主机密钥发到任意地址 |

## 多轮记忆：LangGraph 检查点

大模型本身不记事，「记忆」就是每次把历史重新发给它。关键在于存什么：

| | 只存最终回答（旧做法） | LangGraph 检查点（现在） |
|---|---|---|
| 保存内容 | 每轮回答的文字 | 整轮过程：工具调用、工具原始结果、搜索结果、回答 |
| 追问时 | 只能用回答里恰好写到的信息 | 能用当时查到的全部数据，不必重查 |

```
第 1 轮：kb-app 重启次数？只回答数字   → 调 container_inspect，回答「0」
第 2 轮：它挂载了哪些目录？网络模式？   → 不再调工具，直接用第 1 轮的原始结果
                                          「/opt/kb-app/data → /data，网络 host」
```

- 每个会话是一个 thread，存在 `data/agent_memory.db`（SqliteSaver）；删除会话时一并清除
- 知识库片段只在本轮临时拼进问题，**不写入记忆**，历史不会越滚越大
- 回放给模型时只带最近 4 轮，较早轮次的工具结果截断到 1500 字；记忆里保留完整结果（单条上限 8000 字）
- 每轮结束只保留最新检查点；中途中断留下的「有调用没结果」会在回放前清理，避免模型接口报错
- 升级前的老会话没有检查点，首次追问时用文字历史自动补种

`conversations.py`（chat.db）继续负责会话列表和界面回放，两者各管一摊。

## 知识库答不了时：判断 + 联网搜索（可选）

向量检索总会返回「最像」的几段，哪怕它们和问题毫不相干。更麻烦的是**相似度分数靠不住**——
实测中，问「下季度团建预算」召回了一段项目研发预算，相似度 0.545；问 Python 新特性召回了测试手册，0.555；
而真正相关的《休假管理制度》也才 0.631。用分数阈值区分不开，模型照着这些片段作答就会张冠李戴。

所以这里不靠阈值，而是让模型**看内容判断**片段是否真的回答了问题（相似度一并给它作参考）：

| 判断 | 怎么做 | 回答里怎么标 |
|---|---|---|
| 知识库能完整回答 | 只用知识库 | `[1]` `[2]` |
| 只能回答一部分 / 完全不相关 | 调用 `web_search` 补充 | `[W1]` `[W2]`，界面单独显示带链接的 🌐 卡片 |
| 问的是公司内部信息 | **不上网**，说明知识库里没有 | |
| 要的是真实数据 | 用对应工具，不上网 | |
| 联网关闭 / 网上也没有 | 直说没有；**也不用模型自己的训练知识凑答案** | |

搜索走 LiteLLM 网关的 `/v1/search`，所以内网只要能访问网关就能搜，搜索服务的 key 只放在网关上：

```yaml
# 网关 config.yaml：两个 key 同名即自动分流
search_tools:
  - search_tool_name: web-search
    litellm_params: {search_provider: tavily, api_key: os.environ/TAVILY_API_KEY}
```

```bash
# 应用 .env
WEB_SEARCH_TOOL=web-search
WEB_SEARCH_BLOCKLIST=内部项目名,内部系统名      # 这些词永远不会发往搜索引擎
```

**内部信息发不出去，靠代码而不只靠提示词**：搜索词里出现 IP、疑似密钥或令牌、邮箱、内网域名，
或命中 `WEB_SEARCH_BLOCKLIST`，请求在发出前就被拒绝。网页内容一律标注为「未经核实」，
其中的任何指令都被忽略；与知识库冲突时以知识库为准。每个问题最多搜索 2 次。
页面输入框旁有「🌐 联网」开关，**默认关闭**——内部环境第一次用时不该默认外发任何东西；首次打开会弹一次说明。

评测脚本默认**关闭**联网（搜索结果会随时间变化，数字无法复现），需要时加 `--web`。

### 搜到的答案可以存回知识库

联网回答下方有「📥 存入知识库」按钮。点开是一个**可编辑的预览**，人确认内容无误后才入库：

```
第一次问 PostgreSQL VACUUM 的区别：知识库最高相似度 0.49 → 联网搜索 → 回答
点「存入知识库」：生成《网络补充-…》文档，10 个片段
第二次问同一问题：知识库最高相似度 0.86 → 不再联网，直接从知识库回答
```

- **只能由人点按钮触发**，模型自己不能往知识库里写——否则一次被网页带偏的回答就会变成「团队知识」
- 存入的文档带「来源：网络搜索，某日由某人确认」的说明和原始链接，归到「网络补充」分类，删除方式与普通文档相同
- 回答里指向其他文档的 `[1]` 引用、开头那句「知识库里没有找到」会自动去掉，避免存进去后变成错误信息

## 页面上选模型

顶栏的模型下拉框列出**这把 key 在网关上有权使用的聊天模型**（来自网关 `/v1/models`，缓存 60 秒，向量模型不显示），也可以手动输入模型名。选择只影响回答模型；改写问题、分类、抽取 SOP 仍用默认模型。每条回答下面标注用的是哪个模型，历史回放也保留。

服务端会校验：不在列表里的模型名直接返回 400，不会发给网关，也不会留下会话记录。

### 管理页 · 模型设置

`/manage` → 模型设置：网关地址、API key、对话模型、向量模型、图片识别模型。`.env` 是启动默认值，页面保存的值覆盖它并立刻生效（客户端热重建，不重启）。

- **API key 只写不读**：页面只能填新 key，读回来的永远是 `••••••••末4位`；存于 `data/settings.json`，权限 600
- **测试连接**：保存前先试——列出这把 key 能用的模型、调一次对话模型、算一次向量并给出维度；维度和现有索引不一致会提示
- **换向量模型必须重建索引**：不同模型的向量不能比较，Chroma 也不接受维度不同的向量。保存时会拦下并要求勾选「同时重建索引」；重建从保存的原文件重新解析、向量化（图片识别走缓存），后台任务，页面显示进度
- **恢复 .env**：一键删掉页面上的全部覆盖

**这和「凭据不进页面」矛盾吗？** 不矛盾，但要分清两种凭据：模型网关的 key 决定**数据发给谁**——问题、片段、图片本来就会发出去，这是产品设置，Dify / MaxKB 也都在后台配；工具凭据（`OPS_TOKEN`、`OPS_SECRET_*`）决定**宿主机执行什么**，那条线仍然只在宿主机，页面碰不到。

## 设计决策

**手写文档解析，而不是用现成 Loader。** 标准加载器会丢掉内嵌图片、演讲者备注、组合图形
和表格顺序，而这些是真实笔记里信息密度最高的部分。代价是解析逻辑要自己维护。

**Agent 的作用是路由和取数，不是让检索变聪明。** 早期版本是固定的「检索 → 生成」，因为只有一个数据源。
接入只读工具后，模型需要决定「这个问题要不要查真实数据、查哪个」，这才有了 LangGraph 的模型 ⇄ 工具循环。
只问规则的问题仍然不调工具，延迟和纯 RAG 一样。

**混合检索用 RRF 融合，而不是加权打分。** 向量相似度和 BM25 分数量纲不同，直接加权要调参；
倒数排名融合只看名次，两路都靠前的自然排最前。关键词路额外设了准入门槛（命中英文标识符、或余弦 ≥ 0.40），
否则「有几」「区别」这类常见双字会把无关片段带进来。

**BM25 不用分词词典。** 英文/数字串整体成一个词，中文按字二元组。对精确词匹配够用，零依赖、索引内存里重建不到一秒。

**片段 ID 按文件名生成，不按内容哈希。** 否则两个内容相同、文件名不同的文档会互相覆盖，
先上传的那份会静默消失（这个缺陷是写回归测试时发现的）。

**不默认下发 `reasoning_effort`。** 实测部分网关对该参数的处理是把思考内容并入正文，
导致回答开头出现大段英文推理。只在确认模型支持时才开启。

**相似度低于阈值的片段直接丢弃。** 否则打招呼这类闲聊也会召回一堆无关内容塞进上下文。
但阈值只用来去掉明显无关的（0.25），「相关不相关」交给模型看内容判断——实测无关片段 0.55、相关片段 0.63，阈值分不开。

**长工具输出先压缩再给模型。** 几千行日志大多重复，保留头 30 行、尾 30 行和含告警/错误关键字的行，
中间用「省略 N 行」标记。页面预览不受影响。

## 性能

通过 LangSmith 实测，单次提问的耗时构成：

| 环节 | 占比 |
|---|---|
| 问题改写 | 首轮跳过，多轮约 2 s |
| 向量化 + 检索 | < 10% |
| **模型生成** | **> 85%** |

结论：**瓶颈在模型，不在检索。** 把 `TOP_K` 从 8 调到 6 只能省不到 0.1 秒，
换掉会长时间「思考」的推理模型则让平均耗时从 33 s 降到 8 s。

向量检索本身对数据量不敏感——Chroma 用 HNSW 索引，实测 2 千条和 2 万条的检索耗时在同一量级。
真正的规模限制是内存：索引需常驻，2 GB 机器大约可容纳 5–10 万片段。

## 评测

两套评测集，方法与脚本见 [`eval/README.md`](eval/README.md)。

**公开可复现**——上传 `sample_kb/` 下 6 篇示例文档即可得到相同结果：

```bash
python eval/run_eval.py --user admin --password '...' \
  --judge-model kb-chat --judge-base-url http://127.0.0.1:4000/v1 --judge-api-key "$LLM_API_KEY"
```

| 指标 | 结果 |
|---|---|
| 召回命中率 | 100%（19 条） |
| 要点覆盖率 | 100%（19 条） |
| 拒答正确率 | 100%（2 条） |
| 首字 P50 / P95 | 2.2s / 14.8s |

> 这组数字只能算冒烟测试：示例语料仅 16 个片段，而 `TOP_K=8`，等于每次检索都返回了半个知识库，
> 召回率必然满分。它验证的是链路正确性，不是检索质量。

**真实语料**——51 份技术文档、4969 个片段，同一套脚本、20 条同样结构的题目（题目与语料未公开）：

| 指标 | 结果 |
|---|---|
| 召回命中率 | **89%**（18 条） |
| 要点覆盖率 | **79%**（18 条） |
| 拒答正确率 | **100%**（2 条） |
| 首字 P50 / P95 | 4.6s / 17.2s |

分类型来看：概念题 93%、事实题 78%、跨文档题 62%。

**两个失败案例恰好印证了下面「已知不足」里写的问题**：问到具体配置字段名和具体服务名时，
检索召回了主题相近但内容无关的文档——这正是纯向量检索对专有名词不敏感的典型表现，
也是优先级最高的改进项。

## 已知不足

- **未做重排序（rerank）。** 混合召回解决了「找不到」，但 30 条候选压到 8 条仍靠排名融合，没有交叉编码器精排。
- **跨文档综合能力偏弱。** 真实语料上 `multi_hop` 类题目要点覆盖率 62%，明显低于概念题的 93%。
- **图片识别结果缓存不随文档删除。** 删除文档会清掉片段和原文件，但 OCR 缓存仍保留。
- **仅 HTTP Basic 鉴权，单账号。** 「查我自己的 key」「按岗位看到不同工具」都需要先接统一登录。
- **后台任务在内存里。** 服务重启时正在入库的文件会丢任务，需要重新上传（数据不会半写：入库最后一步才替换）。
- **可观测依赖 LangSmith（外部服务）。** 自托管 Langfuse 需要 Postgres + ClickHouse，2C2G 放不下；
  替代路径是在 LiteLLM 网关侧开 Langfuse 回调，待网关机器扩容后再做。
