# 个人知识库问答系统

把自己的 PDF、Word、PPT、笔记和截图变成可提问的知识库：**先检索，再让大模型基于检索到的片段作答，并标注出处。**

基于 LangChain 组件构建，跑在三台 2 核小规格云主机上，不需要 GPU。

---

## 它解决什么问题

资料存了一堆，用的时候只记得「好像在哪看过」。直接把文档丢给大模型又受上下文长度和成本限制，
而且模型容易编造。

这套系统的做法是：把文档切成小块建立向量索引，提问时按语义召回最相关的几段，
再让模型**只依据这些片段**回答，每句结论都能点开看原文。

## 功能

| | |
|---|---|
| 多格式入库 | PDF / Word / PPT / Markdown / 纯文本 / 图片 |
| 图片识别 | 文档内嵌的截图、架构图经多模态模型识别后**插回原文位置**，一并可检索 |
| 多轮对话 | 追问时自动补全指代（「那它的上限呢」→ 补成完整问题再检索） |
| **现场排障** | **可选开启只读运维工具，Agent 自行决定是否查看环境实况，并与知识库对照** |
| **排查剧本** | **从上传的文档自动抽取排查步骤，页面上可编排启停，只能引用已有工具** |
| 来源可核对 | 回答中的 `[1]` 可点开，显示原文片段、来源文件、PDF 页码和相似度 |
| 自动分类 | 上传时模型建议分类，可手工覆盖，侧栏按分类分组 |
| 原文下载 | 随时取回当初上传的原始文件 |
| 全链路追踪 | 接入 LangSmith，每次提问的各环节耗时与输入输出自动记录 |

## 现场排障（可选）

开启后，Agent 会把知识库和环境实况对照起来，而不只是复述文档：

```
用户：demo-svc 一直在重启，帮我看看

  ① 检索知识库    → 得知要看重启次数、内存上限、日志
  ② 调用只读工具  → list_containers / container_inspect / container_logs
  ③ 对照后判断    → 退出码 137 + 上限仅 12MB → OOM
  ④ 指出矛盾      → 「知识库说应为 900MB，实际 12MB，差 75 倍」
```

**Agent 拿不到 shell。** 它只能提交工具名和结构化参数，由宿主机上的只读接口映射到
固定命令模板执行（`shell=False`）：

```
Agent（容器内，无宿主机权限）
  │  HTTP + 令牌，只传工具名与参数
  ▼
只读接口（宿主机，仅监听 127.0.0.1）
  │  正则白名单校验 → 固定 argv 模板 → 写动词黑名单
  ▼
docker / kubectl（只读动词）
```

启用方式：

```bash
# 宿主机
OPS_TOKEN=$(openssl rand -hex 16) python3 deploy/ops_readonly.py --port 8799

# .env 里填上，然后重建容器
OPS_URL=http://127.0.0.1:8799
OPS_TOKEN=<同一个令牌>
```

不配置 `OPS_URL` 时工具自动关闭，退化为纯知识库问答。注入防护与轮次上限均有测试覆盖
（`tests/test_agent.py`）。

### 加一个工具

工具定义只有一份，就是宿主机上的 [`deploy/ops_tools.yaml`](deploy/ops_tools.yaml)。
应用侧不保存任何工具清单，而是每次提问从接口拉取描述与参数，动态生成模型看到的函数签名。
所以**加工具只改这个文件，不用重启服务，也不用重建镜像**：

```yaml
  - name: host_uptime
    desc: 查看宿主机已经开机多久、当前 1/5/15 分钟平均负载。
    binary: uptime
    argv: [uptime]
    params: {}
```

保存后下一次提问就能用上。带参数的工具这样写：

```yaml
  - name: container_logs
    desc: 查看指定容器最近的日志，用于定位报错原因。
    binary: docker
    argv: [docker, logs, --tail, "{lines}", "{name}"]
    params:
      name:  {type: str, pattern: name, required: true, desc: 容器名}
      lines: {type: int, default: 100, max: 500, desc: 查看最近多少行}
```

配置本身就是安全边界，所以加载时强制校验，不合规的条目会被跳过并记录原因：

| 约束 | 为什么 |
|---|---|
| 参数必须整个占据一个 argv 项（`"{name}"`） | 不允许 `--tail={lines}` 这种拼接，参数值永远变不成新的命令片段 |
| 字符串参数只能引用预置正则 | 不能自带正则，否则一个 `.*` 就把白名单废了 |
| `argv[0]` 必须等于 `binary` | 防止用 `binary: docker` 过检查、实际去跑 `bash` |
| `binary` 不能是解释器 | `bash`/`sh`/`python`/`env`/`xargs`/`find`/`ssh` 等能执行任意命令，一律拒绝 |
| 模板里不得出现写动词 | 与运行时黑名单双保险 |
| 非必填的字符串必须有合法默认值 | 否则运行时会往 argv 里塞空串 |

其中「`binary` 不能是解释器」堵的是最致命的一类：`binary: bash, argv: [bash, -c, "任意命令"]`。
`-c` 后面整段是一个 argv 项，写动词黑名单按词匹配根本挡不住它。所以这类 binary 直接禁，
要跑一段逻辑请用下面的**脚本工具**。

写坏了也不会让服务失去全部工具——加载失败时沿用上一份可用定义。
`enabled: false` 可以下线某个工具，它会立刻从模型的可用列表里消失，引用它的剧本也会标红。

### 页面上能改什么，不能改什么

界面上的 **🔧 工具** 面板能看到每个工具的完整命令模板、参数和启停状态。
但页面能改的范围是一条刻意划清的安全边界：

| 操作 | 在页面上 | 为什么 |
|---|---|---|
| 查看命令模板与参数 | ✅ | 一眼看清 Agent 到底能执行什么 |
| 启用 / 停用 | ✅ 立即生效 | 这是**缩权**方向 |
| 改描述、改中文显示名 | ✅ 立即生效 | 只影响人和模型怎么理解，不改变执行的命令 |
| 改 `argv` / `binary` | ❌ | 等于让页面定义宿主机执行什么 |
| 新增命令工具 | ⚠️ 只能提交申请 | 需要人在宿主机上批准后才写入配置 |
| 新增脚本工具 | ⚠️ 只能引用已有脚本 | 脚本内容只有宿主机能放，页面只能选，且哈希锁定 |

这个边界靠**文件分权**落实，而不是靠接口自觉：

```
ops_tools.yaml             root 手写，唯一能定义命令的地方，页面无权写
ops_tools.overrides.yaml   页面可写，加载时只认 enabled / desc / label 三个字段
ops_tools.pending.yaml     页面可写，待审队列，永远不参与加载
ops_tools.trust.yaml       脚本哈希表，只有宿主机批准/trust 时写，页面无权写
scripts/                   脚本目录，只有宿主机能放文件，页面只能引用
```

即使覆盖层文件被完全控制，写进 `argv: [cat, /etc/shadow]` 也会被直接忽略——
加载时只读那两个字段。最坏情况是工具被全部停用或描述被改乱，**提不了权**。

申请新工具后，在宿主机上审批：

```bash
python3 deploy/ops_readonly.py pending      # 列出申请，重点看「命令」那一行
python3 deploy/ops_readonly.py approve <id> # 批准后写入主配置，下次提问即可用
python3 deploy/ops_readonly.py reject <id>
```

申请在批准前**完全惰性**：模型看不到，也调用不了。提交时就会跑一遍和正式配置
同样的校验，所以写错的申请当场被拒，而不是等到审批才发现：

```
填 datetime → 本机没有 datetime 这个命令，你是不是想用 date？（相近的还有：time）
填 dfh      → 本机没有 dfh 这个命令，你是不是想用 df？
```

### 工具名为什么只能用英文
工具名会作为函数名发给模型，function calling 的规范只允许字母、数字、下划线，
中文名会被接口拒绝。所以多了一个 `label` 字段专门放中文：

```yaml
  - name: host_disk        # 发给模型的函数名，只能英文
    label: 磁盘用量         # 界面上显示的名字，随便写
    desc: 查看宿主机各挂载点的磁盘使用率。容器写日志失败、镜像拉不下来时先看这个。
    binary: df
    argv: [df, -h]
    params: {}
```

`label` 只用于界面，不会进入发给模型的工具定义——模型拿到的始终是
`{desc, params}`，和英文函数名。`label` 和 `desc` 一样可以在页面上直接改。

### 脚本工具：把一串只读命令固化成一个工具

有时一个判断要跑好几条命令（先列容器、再逐个查重启次数、再挑出异常的）。
与其让模型自己拼，不如写成一个脚本，让它成为一个工具。但「页面能定义脚本内容」
就等于「上传可执行代码」——文档投毒那套风险会原样回来。所以这里的规矩是：

- **脚本内容只能由宿主机管理员放进 `scripts/` 目录**，页面碰不到内容
- 页面和申请都只能**从已有脚本里选一个来引用**
- 批准时登记脚本的 **SHA-256**；加载和执行前各校验一次，**内容一旦被改就自动停用**

```yaml
  - name: container_health
    label: 容器体检
    desc: 一眼看懂所有容器的状态和重启次数
    script: container_health.sh   # 只能是 scripts 目录下的文件名，不能带路径
    params: {}
```

```bash
# 宿主机放脚本（必须 LF 换行、可执行）
cp container_health.sh /opt/ops/scripts/ && chmod +x /opt/ops/scripts/container_health.sh
python3 deploy/ops_readonly.py scripts            # 列出脚本与信任状态
python3 deploy/ops_readonly.py approve <id>       # 批准引用它的申请，顺带登记哈希
python3 deploy/ops_readonly.py trust <脚本名>     # 合法更新脚本内容后，重新登记哈希
```

这和「剧本只能引用已有工具」是同一个思路：**能力（脚本/工具）由宿主机掌控，
页面只能编排与引用，永远扩不了权。**

## 快速开始

需要一个 OpenAI 兼容的模型网关（LiteLLM 配置样例见 [`litellm/config.yaml`](litellm/config.yaml)）。

```bash
cp .env.example .env
# 填入 LLM_BASE_URL、LLM_API_KEY、WEB_PASSWORD
docker compose up -d --build
```

打开 http://127.0.0.1:8765 ，用 `.env` 里的账号密码登录。
`sample_kb/` 下有两篇示例文档可以直接上传试用。

> `.env` 必须是 LF 换行且无 BOM；多余的 `\r` 会让容器里的每个值都悄悄出错。
> 另外改完 `.env` 要重建容器，`docker restart` 不会重新读取 `--env-file`。

## 设计决策

**手写文档解析，而不是用现成 Loader。** 标准加载器会丢掉内嵌图片、演讲者备注、组合图形
和表格顺序，而这些是真实笔记里信息密度最高的部分。代价是解析逻辑要自己维护。

**固定「检索 → 生成」流程，没有做成 Agent。** 当前只有一个数据源，所有问题都是查资料，
没有路由的必要。固定流程更稳、更省，延迟也可预测。等接入订单查询这类需要**精确匹配**的
数据源时，才需要让模型决定走哪条路——那时 Agent 的作用是路由，不是让检索变聪明。

**片段 ID 按文件名生成，不按内容哈希。** 否则两个内容相同、文件名不同的文档会互相覆盖，
先上传的那份会静默消失（这个缺陷是写回归测试时发现的）。

**不默认下发 `reasoning_effort`。** 实测部分网关对该参数的处理是把思考内容并入正文，
导致回答开头出现大段英文推理。只在确认模型支持时才开启。

**相似度低于阈值的片段直接丢弃。** 否则打招呼这类闲聊也会召回一堆无关内容塞进上下文。

## 性能

通过 LangSmith 实测，单次提问的耗时构成：

| 环节 | 占比 |
|---|---|
| 问题改写 | 首轮跳过，多轮约 2 s |
| 向量化 + 检索 | < 10% |
| **模型生成** | **> 85%** |

结论：**瓶颈在模型，不在检索。** 把 `TOP_K` 从 8 调到 6 只能省不到 0.1 秒，
换掉会长时间「思考」的推理模型则让平均耗时从 33 s 降到 8 s。

向量检索本身对数据量不敏感——Chroma 用 HNSW 索引，实测 2 千条和 2 万条的检索耗时在同一量级。
真正的规模限制是内存：索引需常驻，2 GB 机器大约可容纳 5–10 万片段。

## 评测

两套评测集，方法与脚本见 [`eval/README.md`](eval/README.md)。

**公开可复现**——上传 `sample_kb/` 下 6 篇示例文档即可得到相同结果：

```bash
python eval/run_eval.py --user admin --password '...' \
  --judge-model kb-chat --judge-base-url http://127.0.0.1:4000/v1 --judge-api-key "$LLM_API_KEY"
```

| 指标 | 结果 |
|---|---|
| 召回命中率 | 100%（19 条） |
| 要点覆盖率 | 100%（19 条） |
| 拒答正确率 | 100%（2 条） |
| 首字 P50 / P95 | 2.2s / 14.8s |

> 这组数字只能算冒烟测试：示例语料仅 16 个片段，而 `TOP_K=8`，等于每次检索都返回了半个知识库，
> 召回率必然满分。它验证的是链路正确性，不是检索质量。

**真实语料**——51 份技术文档、4969 个片段，同一套脚本、20 条同样结构的题目（题目与语料未公开）：

| 指标 | 结果 |
|---|---|
| 召回命中率 | **89%**（18 条） |
| 要点覆盖率 | **79%**（18 条） |
| 拒答正确率 | **100%**（2 条） |
| 首字 P50 / P95 | 4.6s / 17.2s |

分类型来看：概念题 93%、事实题 78%、跨文档题 62%。

**两个失败案例恰好印证了下面「已知不足」里写的问题**：问到具体配置字段名和具体服务名时，
检索召回了主题相近但内容无关的文档——这正是纯向量检索对专有名词不敏感的典型表现，
也是优先级最高的改进项。

## 已知不足

- **未做重排序（rerank）。** 文档量增长后，不同文档中语义相近的片段会互相挤占 `TOP_K` 名额。
  后续计划粗召回 30 条再精排到 8 条。
- **纯向量检索，缺少关键词召回。** 对专有名词、配置字段名、型号、错误码这类精确匹配场景不理想
  ——真实语料评测中两例召回失败都属于这一类。混合检索（BM25 + 向量）会更稳。
- **跨文档综合能力偏弱。** 真实语料上 `multi_hop` 类题目要点覆盖率 62%，明显低于概念题的 93%。
- **入库是同步的。** 含大量图片的文件要逐张识别，上传请求会等待较久，没有后台任务队列。
- **图片识别结果缓存不随文档删除。** 删除文档会清掉片段和原文件，但 OCR 缓存仍保留。
- **仅 HTTP Basic 鉴权。** 单用户自用够了，公网暴露需要配 HTTPS 与访问限制。
- **没有自动备份。** 向量库和对话记录需要自行定期打包。
